17.8 — C风格数组退化

● 机器译文 课程 17.8 查看英文原文

C风格数组传递的挑战

C语言的设计者曾面临一个问题。考虑以下简单程序：

#include <iostream>

void print(int val)
{
    std::cout << val;
}

int main()
{
    int x { 5 };
    print(x);

    return 0;
}

当 print(x) 被调用时，参数 x (5的值被复制到形参 val中。在函数体内， val (5的值被打印到控制台。由于 x 复制成本低，这里没有问题。

现在考虑以下类似的程序，它使用一个包含1000个元素的C风格int数组，而不是单个int：

#include <iostream>

void printElementZero(int arr[1000])
{
    std::cout << arr[0]; // // 打印第一个元素的值
}

int main()
{
    int x[1000] { 5 };   // // 定义一个包含1000个元素的数组，x[0]被初始化为5
    printElementZero(x);

    return 0;
}

这个程序也能编译并打印预期的值（5）到控制台。

虽然这个例子中的代码与前一个例子中的代码相似，但它的工作机制与你预期的略有不同（我们将在下面解释）。这是因为C语言设计者为了解决两个主要挑战而提出的解决方案。

首先，每次调用函数时复制一个包含1000个元素的数组代价高昂（如果元素是复制成本高的类型则更甚），因此我们希望避免这种情况。但如何避免？C语言没有引用，因此无法通过传引用来避免复制函数参数。

其次，我们希望编写一个能够接受不同长度数组参数的函数。理想情况下，上面例子中的 printElementZero() 函数应该能够接受任意长度的数组参数（因为元素0保证存在）。我们不想为每种可能的数组长度都编写一个不同的函数。但如何实现？C语言没有指定“任意长度”数组的语法，也不支持模板，而且一个长度的数组不能转换为另一个长度的数组（大概是因为这样做会涉及昂贵的复制）。

C语言的设计者提出了一个巧妙的解决方案（出于兼容性原因，C++继承了它），同时解决了这两个问题：

#include <iostream>

void printElementZero(int arr[1000]) // // 不进行复制
{
    std::cout << arr[0]; // // 打印第一个元素的值
}

int main()
{
    int x[7] { 5 };      // // 定义一个包含7个元素的数组
    printElementZero(x); // // 居然能工作！

    return 0;
}

不知何故，上面的例子将一个包含7个元素的数组传递给了一个期望包含1000个元素的函数，而没有进行任何复制。在本课中，我们将探讨这是如何工作的。

我们还将探讨为什么C语言设计者选择的解决方案是危险的，并且不适合在现代C++中使用。

但首先，我们需要介绍两个子主题。

数组到指针的转换（数组退化）

在大多数情况下，当C风格数组在表达式中使用时，数组会隐式转换为指向元素类型的指针，并用第一个元素（索引为0）的地址初始化。通俗地说，这称为 数组退化 （或简称 退化 （简称）。

你可以在以下程序中看到这一点：

数组退化解决了我们的C风格数组传递问题

数组退化解决了我们在课程开头遇到的两个挑战。

当将C风格数组作为参数传递时，数组退化为指针，持有数组第一个元素地址的指针被传递给函数。因此，虽然看起来我们是在按值传递C风格数组，但实际上我们是在按地址传递！这样就避免了复制C风格数组参数。

关键提示

C风格数组是按地址传递的，即使看起来是按值传递。

现在考虑两个具有相同元素类型但不同长度的不同数组（例如 int[5] 和 int[7]）。它们是不同的类型，彼此不兼容。然而，它们都会退化为相同的指针类型（例如 int*）。它们的退化版本是可互换的！从类型中丢弃长度信息允许我们传递不同长度的数组而不会出现类型不匹配。

关键提示

两个具有相同元素类型但不同长度的C风格数组将退化为相同的指针类型。

在下面的例子中，我们将说明两件事：

  • 我们可以将不同长度的数组传递给同一个函数（因为两者都退化为相同的指针类型）。
  • 接收数组的函数参数可以是数组元素类型的（const）指针。
#include <iostream>

void printElementZero(const int* arr) // // 通过常量地址传递
{
    std::cout << arr[0];
}

int main()
{
    const int prime[] { 2, 3, 5, 7, 11 };
    const int squares[] { 1, 4, 9, 25, 36, 49, 64, 81 };

    printElementZero(prime);   // // prime退化为const int*指针
    printElementZero(squares); // squares 退化为 const int* 指针

    return 0;
}

C风格数组函数参数语法

将函数参数声明为 int* arr 的一个问题是，不清楚 arr 应该是指向值数组的指针，而不是指向单个整数的指针。因此，在传递C风格数组时，最好使用替代声明形式 int arr[]：

#include <iostream>

void printElementZero(const int arr[]) // 与 const int* 相同处理
{
    std::cout << arr[0];
}

int main()
{
    const int prime[] { 2, 3, 5, 7, 11 };
    const int squares[] { 1, 4, 9, 25, 36, 49, 64, 81 };

    printElementZero(prime);  // prime 退化为指针
    printElementZero(squares); // squares 退化为指针

    return 0;
}

尽管数组退化是一种巧妙的解决方案，可以确保不同长度的C风格数组能够传递给函数而无需进行昂贵的复制，但数组长度信息的丢失使得几种类型的错误很容易发生。

首先， sizeof() 对于数组和退化数组将返回不同的值：

#include <iostream>

void printArraySize(int arr[])
{
    std::cout << sizeof(arr) << '\n'; // 打印 4（假设 32 位地址）
}

int main()
{
    int arr[]{ 3, 2, 1 };

    std::cout << sizeof(arr) << '\n'; // 打印 12（假设 4 字节 int）

    printArraySize(arr);

    return 0;
}

这意味着在C风格数组上使用 sizeof() 是潜在危险的，因为必须确保仅在能够访问实际数组对象时使用它，而不是退化后的数组或指针。

在上一课（17.7 -- C风格数组简介），我们提到过 sizeof(arr)/sizeof(*arr) 历史上曾被用作获取C风格数组大小的技巧。这个技巧很危险，因为如果 arr 已经退化， sizeof(arr) 将返回指针的大小而不是数组的大小，从而导致错误的数组长度，很可能导致程序出现故障。

幸运的是，C++17中更好的替代品 std::size() （以及C++20中的 std::ssize()）如果传入指针值将编译失败：

#include <iostream>

int printArrayLength(int arr[])
{
    std::cout << std::size(arr) << '\n'; // 编译错误：std::size() 不能用于指针
}

int main()
{
    int arr[]{ 3, 2, 1 };

    std::cout << std::size(arr) << '\n'; // 打印 3

    printArrayLength(arr);

    return 0;
}

其次，也许最重要的是，数组退化会使重构（将长函数分解为更短、更模块化的函数）变得困难。对于未退化的数组能正常工作的代码，当同样的代码使用退化数组时，可能无法编译（或者更糟，可能静默地出现故障）。

第三，缺少长度信息会带来若干编程挑战。没有长度信息，就很难对数组长度进行合理性检查。用户很容易传入比预期更短的数组（甚至是指向单个值的指针），这将在使用无效索引进行下标操作时导致未定义行为。

#include <iostream>

void printElement2(int arr[])
{
    // 如何确保 arr 至少有三个元素？
    std::cout << arr[2] << '\n';
}

int main()
{
    int a[]{ 3, 2, 1 };
    printElement2(a);  // ok

    int b[]{ 7, 6 };
    printElement2(b);  // 编译通过但产生未定义行为

    int c{ 9 };
    printElement2(&c); // 编译通过但产生未定义行为

    return 0;
}

缺少数组长度也会在遍历数组时带来挑战——我们如何知道何时到达了末尾？

这些问题有一些解决方案，但这些解决方案既增加了程序的复杂性，也增加了脆弱性。

解决数组长度问题的方法

历史上，程序员通过两种方法之一来解决数组长度信息的缺失。

第一种，我们可以将数组和数组长度作为单独的参数传入：

#include <cassert>
#include <iostream>

void printElement2(const int arr[], int length)
{
    assert(length > 2 && "printElement2: Array too short"); // 无法对长度进行 static_assert

    std::cout << arr[2] << '\n';
}

int main()
{
    constexpr int a[]{ 3, 2, 1 };
    printElement2(a, static_cast<int>(std::size(a)));  // ok

    constexpr int b[]{ 7, 6 };
    printElement2(b, static_cast<int>(std::size(b)));  // 将触发断言

    return 0;
}

然而，这仍然存在一些问题：

  • 调用者需要确保数组和数组长度是配对的——如果传入了错误的长度值，函数仍然会出错。
  • 如果使用 std::size() 的函数，可能存在符号转换问题。 std::size_t。
  • 运行时断言仅在运行时遇到时触发。如果我们的测试路径没有覆盖所有对函数的调用，就有可能将程序交付给客户，而客户在执行我们未明确测试的操作时会触发断言。在现代C++中，我们希望使用 static_assert 对constexpr数组的数组长度进行编译时验证，但没有简单的方法做到这一点（因为函数参数不能是constexpr，即使在constexpr或consteval函数中也不行！）。
  • 这种方法仅在显式函数调用时有效。如果函数调用是隐式的（例如，我们调用一个以数组为操作数的运算符），那么就没有机会传入长度。

第二种，如果存在一个在语义上无效的元素值（例如，测试分数为 -1），我们可以使用该值的元素来标记数组的结尾。这样，数组的长度可以通过计算从数组开头到该终止元素之间的元素数量来得到。数组也可以通过从开头迭代直到遇到终止元素来遍历。这种方法的好处是即使在隐式函数调用中也能工作。

关键提示

C风格字符串（即C风格数组）使用空终止符来标记字符串的结尾，这样即使它们已经退化，也能被遍历。

但这种方法也存在一些问题：

  • 如果终止元素不存在，遍历将直接越过数组末尾，导致未定义行为。
  • 遍历数组的函数需要特殊处理终止元素（例如，C风格字符串打印函数需要知道不打印终止元素）。
  • 实际数组长度与语义有效元素数量之间存在不匹配。如果使用了错误的长度，语义无效的终止元素可能会被“处理”。
  • 这种方法仅在存在语义无效的值时有效，而通常情况并非如此。

在大多数情况下应避免使用C风格数组

由于非标准的传递语义（使用按地址传递而非按值传递）以及退化数组丢失长度信息带来的风险，C风格数组通常已不再受欢迎。我们建议尽可能避免使用它们。

最佳实践

在实际可行时避免使用C风格数组。

  • 优先使用 std::string_view 用于只读字符串（字符串字面量符号常量和字符串参数）。
  • 优先使用 std::string 用于可修改字符串。
  • 优先使用 std::array 用于非全局constexpr数组。
  • 优先使用 std::vector 用于非 constexpr 数组。

对于全局constexpr数组，使用C风格数组是可以的。我们稍后会讨论这一点。

顺便说一句……

在C++中，数组可以通过引用传递，此时数组参数在传递给函数时不会退化（但数组的引用在求值时仍会退化）。然而，很容易忘记一致地应用这一点，一次遗漏的引用就会导致参数退化。此外，数组引用参数必须具有固定长度，这意味着该函数只能处理特定长度的数组。如果我们想要一个能处理不同长度数组的函数，那么还必须使用函数模板。但如果你打算同时做这两件事来“修复”C风格数组，那么还不如直接使用 std::array！

那么，在现代C++中，C风格数组何时使用？

在现代C++中，C风格数组通常用于两种情况：

  1. 存储constexpr全局（或constexpr静态局部）程序数据。由于此类数组可以直接从程序中的任何位置访问，我们无需传递数组，从而避免了与退化相关的问题。定义C风格数组的语法可能比 std::array稍微不那么别扭。更重要的是，对此类数组进行索引没有标准库容器类那样的符号转换问题。
  2. 作为函数或类的参数，这些函数或类希望直接处理非constexpr C风格字符串参数（而不是要求转换为 std::string_view）。这有两个可能的原因：首先，将非constexpr C风格字符串转换为 std::string_view 需要遍历C风格字符串以确定其长度。如果函数位于性能关键的代码段中，并且不需要长度（例如，因为函数无论如何都会遍历字符串），那么避免转换可能是有用的。其次，如果函数（或类）调用其他期望C风格字符串的函数，那么转换为 std::string_view 只是为了转换回来可能不是最优的（除非你有其他理由想要一个 std::string_view)。

小测验时间

问题 #1

什么是数组退化，为什么它是一个问题？

显示答案

当C风格数组被求值时，在大多数上下文中，它会隐式转换为指向数组元素类型的指针。

退化的数组丢失了其长度信息，这使得长度相关的错误更容易被引入程序中。

问题 #2

为什么C风格字符串（它们是C风格数组）使用空终止符？

显示答案

当C风格数组传递给函数时，它会退化并丢失其长度信息。如果C风格字符串没有空终止符，函数将无法确定字符串的长度。

问题 #3

额外加分：为什么C风格字符串使用空终止符，而不是要求将退化的C风格字符串和显式长度信息都传递给函数？

显示答案

这个问题可能有很多答案，但这里有一些：

  • 人体工程学将非常糟糕，因为到处都会有额外的参数和魔法数字（例如 printString("Hello", 5))。
  • 字符串和提供的字符串长度很容易不匹配。字符串长度本质上是字符串本身的一个不变量。依赖用户来维护这个不变量将不可避免地导致错误（例如 printString("Hello", 6))。

额外加分#2：即使C++想要实现必须传递显式长度信息，为什么它行不通？

显示提示

提示：考虑使用 std::cout。

显示答案

同时传递C风格字符串和显式长度信息只有在函数被显式调用时才可能。如果函数被隐式调用，则无法传递长度信息。

考虑一个语句如 std::cout << cstr。二元 operator<< 只能接受两个操作数： std::cout 和 cstr。没有办法传递另一个代表长度信息的参数。空终止符方法没有这个问题。
