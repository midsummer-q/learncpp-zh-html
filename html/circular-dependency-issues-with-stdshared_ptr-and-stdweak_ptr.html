22.7 — std::shared_ptr 的循环依赖问题与 std::weak_ptr

● 机器译文 课程 22.7 查看英文原文

在上一节课中，我们看到了 std::shared_ptr 如何允许多个智能指针共同拥有同一资源。然而，在某些情况下，这可能会带来问题。考虑以下情况，两个独立对象中的共享指针各自指向对方：

#include <iostream>
#include <memory> // for std::shared_ptr
#include <string>

class Person
{
	std::string m_name;
	std::shared_ptr<Person> m_partner; // 初始创建为空

public:
		
	Person(const std::string &name): m_name(name)
	{ 
		std::cout << m_name << " created\n";
	}
	~Person()
	{
		std::cout << m_name << " destroyed\n";
	}

	friend bool partnerUp(std::shared_ptr<Person> &p1, std::shared_ptr<Person> &p2)
	{
		if (!p1 || !p2)
			return false;

		p1->m_partner = p2;
		p2->m_partner = p1;

		std::cout << p1->m_name << " is now partnered with " << p2->m_name << '\n';

		return true;
	}
};

int main()
{
	auto lucy { std::make_shared<Person>("Lucy") }; // 创建一个名为 "Lucy" 的 Person
	auto ricky { std::make_shared<Person>("Ricky") }; // 创建一个名为 "Ricky" 的 Person

	partnerUp(lucy, ricky); // 让 "Lucy" 指向 "Ricky"，反之亦然

	return 0;
}

在上面的例子中，我们使用 make_shared() 动态分配了两个 Person 对象，“Lucy”和“Ricky”（以确保 lucy 和 ricky 在 main() 结束时被销毁）。然后我们让它们成为伙伴。这将“Lucy”内部的 std::shared_ptr 设置为指向“Ricky”，并将“Ricky”内部的 std::shared_ptr 设置为指向“Lucy”。共享指针本意就是共享的，所以 lucy 共享指针和 Rick 的 m_partner 共享指针都指向“Lucy”（反之亦然）是没问题的。

然而，这个程序并没有按预期执行：

Lucy created
Ricky created
Lucy is now partnered with Ricky

仅此而已。没有发生任何释放操作。哦不。发生了什么？

在调用 partnerUp() 之后，有两个共享指针指向“Ricky”（ricky 和 Lucy 的 m_partner），以及两个共享指针指向“Lucy”（lucy 和 Ricky 的 m_partner）。

在 main() 结束时，ricky 共享指针首先离开作用域。此时，ricky 检查是否有其他共享指针共同拥有 Person “Ricky”。确实有（Lucy 的 m_partner）。因此，它不会释放“Ricky”（如果释放了，Lucy 的 m_partner 就会变成悬空指针）。此时，我们有一个共享指针指向“Ricky”（Lucy 的 m_partner），以及两个共享指针指向“Lucy”（lucy 和 Ricky 的 m_partner）。

接下来，lucy 共享指针离开作用域，同样的事情发生了。共享指针 lucy 检查是否有其他共享指针共同拥有 Person “Lucy”。确实有（Ricky 的 m_partner），所以“Lucy”没有被释放。此时，有一个共享指针指向“Lucy”（Ricky 的 m_partner），以及一个共享指针指向“Ricky”（Lucy 的 m_partner）。

然后程序结束——Person “Lucy”和“Ricky”都没有被释放！本质上，“Lucy”阻止了“Ricky”被销毁，而“Ricky”也阻止了“Lucy”被销毁。

事实证明，只要共享指针形成循环引用，这种情况就可能发生。

循环引用

一个 循环引用 （也称为 循环引用 变为 循环）是一系列引用，其中每个对象引用下一个对象，最后一个对象又引用回第一个对象，形成一个引用循环。这些引用不一定是实际的 C++ 引用——它们可以是指针、唯一 ID 或任何其他标识特定对象的方式。

在共享指针的上下文中，这些引用将是指针。

这正是我们在上面看到的情况：“Lucy”指向“Ricky”，“Ricky”指向“Lucy”。对于三个指针，当 A 指向 B，B 指向 C，C 指向 A 时，也会出现同样的情况。共享指针形成循环的实际效果是，每个对象最终都会保持下一个对象存活——最后一个对象保持第一个对象存活。因此，系列中的任何对象都无法被释放，因为它们都认为其他对象仍然需要它！

一个简化的情况

事实证明，这种循环引用问题甚至可能发生在单个 std::shared_ptr 上——一个指向包含它的对象的 std::shared_ptr 仍然是一个循环（只是简化版）。尽管在实践中这种情况不太可能发生，但我们还是展示一下以加深理解：

#include <iostream>
#include <memory> // for std::shared_ptr

class Resource
{
public:
	std::shared_ptr<Resource> m_ptr {}; // 初始创建为空
	
	Resource() { std::cout << "Resource acquired\n"; }
	~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
	auto ptr1 { std::make_shared<Resource>() };

	ptr1->m_ptr = ptr1; // m_ptr 现在共享包含它的 Resource

	return 0;
}

在上面的例子中，当 ptr1 离开作用域时，Resource 没有被释放，因为 Resource 的 m_ptr 正在共享该 Resource。此时，释放 Resource 的唯一方法是将 m_ptr 设置为其他值（这样就没有任何东西再共享该 Resource）。但我们无法访问 m_ptr，因为 ptr1 已经离开作用域，所以我们无法再做到这一点。Resource 变成了内存泄漏。

因此，程序输出：

Resource acquired

仅此而已。

那么 std::weak_ptr 到底是用来做什么的？

std::weak_ptr 被设计用来解决上述的“循环所有权”问题。std::weak_ptr 是一个观察者——它可以观察和访问与 std::shared_ptr（或其他 std::weak_ptr）相同的对象，但它不被视为所有者。记住，当 std::shared_ptr 离开作用域时，它只考虑是否有其他 std::shared_ptr 共同拥有该对象。std::weak_ptr 不计入！

让我们使用 std::weak_ptr 来解决我们的 Person 问题：

#include <iostream>
#include <memory> // for std::shared_ptr and std::weak_ptr
#include <string>

class Person
{
	std::string m_name;
	std::weak_ptr<Person> m_partner; // 注意：现在这是一个 std::weak_ptr

public:
		
	Person(const std::string &name): m_name(name)
	{ 
		std::cout << m_name << " created\n";
	}
	~Person()
	{
		std::cout << m_name << " destroyed\n";
	}

	friend bool partnerUp(std::shared_ptr<Person> &p1, std::shared_ptr<Person> &p2)
	{
		if (!p1 || !p2)
			return false;

		p1->m_partner = p2;
		p2->m_partner = p1;

		std::cout << p1->m_name << " is now partnered with " << p2->m_name << '\n';

		return true;
	}
};

int main()
{
	auto lucy { std::make_shared<Person>("Lucy") };
	auto ricky { std::make_shared<Person>("Ricky") };

	partnerUp(lucy, ricky);

	return 0;
}

这段代码行为正确：

Lucy created
Ricky created
Lucy is now partnered with Ricky
Ricky destroyed
Lucy destroyed

从功能上讲，它几乎与有问题的例子相同。然而，现在当 ricky 离开作用域时，它看到没有其他 std::shared_ptr 指向“Ricky”（来自“Lucy”的 std::weak_ptr 不计入）。因此，它将释放“Ricky”。对于 lucy 也是如此。

使用 std::weak_ptr

std::weak_ptr 的一个缺点是 std::weak_ptr 不能直接使用（它们没有 operator->）。要使用 std::weak_ptr，必须首先将其转换为 std::shared_ptr。然后才能使用该 std::shared_ptr。要将 std::weak_ptr 转换为 std::shared_ptr，可以使用 lock() 成员函数。以下是上述示例的更新版本，展示了这一点：

#include <iostream>
#include <memory> // for std::shared_ptr and std::weak_ptr
#include <string>

class Person
{
	std::string m_name;
	std::weak_ptr<Person> m_partner; // 注意：现在这是一个 std::weak_ptr

public:

	Person(const std::string &name) : m_name(name)
	{
		std::cout << m_name << " created\n";
	}
	~Person()
	{
		std::cout << m_name << " destroyed\n";
	}

	friend bool partnerUp(std::shared_ptr<Person> &p1, std::shared_ptr<Person> &p2)
	{
		if (!p1 || !p2)
			return false;

		p1->m_partner = p2;
		p2->m_partner = p1;

		std::cout << p1->m_name << " is now partnered with " << p2->m_name << '\n';

		return true;
	}

	std::shared_ptr<Person> getPartner() const { return m_partner.lock(); } // 使用 lock() 将 weak_ptr 转换为 shared_ptr
	const std::string& getName() const { return m_name; }
};

int main()
{
	auto lucy { std::make_shared<Person>("Lucy") };
	auto ricky { std::make_shared<Person>("Ricky") };

	partnerUp(lucy, ricky);

	auto partner = ricky->getPartner(); // 获取指向 Ricky 伴侣的 shared_ptr
	std::cout << ricky->getName() << "'s partner is: " << partner->getName() << '\n';

	return 0;
}

这会打印：

Lucy created
Ricky created
Lucy is now partnered with Ricky
Ricky's partner is: Lucy
Ricky destroyed
Lucy destroyed

我们不必担心 std::shared_ptr 变量“partner”的循环依赖，因为它只是函数内的局部变量。它最终会在函数结束时离开作用域，引用计数将减 1。

使用 std::weak_ptr 避免悬空指针

考虑这样一种情况：一个普通的“裸”指针持有某个对象的地址，然后该对象被销毁。这样的指针是悬空的，解引用该指针将导致未定义行为。不幸的是，我们无法判断一个持有非空地址的指针是否悬空。这就是裸指针危险的主要原因之一。

由于 std::weak_ptr 不会保持所拥有的资源存活，因此 std::weak_ptr 有可能指向一个已被 std::shared_ptr 释放的资源。然而，std::weak_ptr 有一个巧妙的技巧——因为它可以访问对象的引用计数，所以它能判断自己是否指向一个有效的对象！如果引用计数非零，则资源仍然有效。如果引用计数为零，则资源已被销毁。

测试 std::weak_ptr 是否有效的最简单方法是使用 expired() 成员函数，如果 std::weak_ptr 指向无效对象，则返回 true ，如果指向有效对象，则返回 false 如果它是空指针，否则为

下面是一个简单的例子，展示了这种行为的差异：

// 感谢读者 Waldo 提供了这个例子的早期版本
#include <iostream>
#include <memory>

class Resource
{
public:
	Resource() { std::cerr << "Resource acquired\n"; }
	~Resource() { std::cerr << "Resource destroyed\n"; }
};

// 返回一个指向无效对象的 std::weak_ptr
std::weak_ptr<Resource> getWeakPtr()
{
	auto ptr{ std::make_shared<Resource>() };
	return std::weak_ptr<Resource>{ ptr };
} // ptr 离开作用域，Resource 被销毁

// 返回一个指向无效对象的裸指针
Resource* getDumbPtr()
{
	auto ptr{ std::make_unique<Resource>() };
	return ptr.get();
} // ptr 离开作用域，Resource 被销毁

int main()
{
	auto dumb{ getDumbPtr() };
	std::cout << "Our dumb ptr is: " << ((dumb == nullptr) ? "nullptr\n" : "non-null\n");

	auto weak{ getWeakPtr() };
	std::cout << "Our weak ptr is: " << ((weak.expired()) ? "expired\n" : "valid\n");

	return 0;
}

这会打印：

Resource acquired
Resource destroyed
Our dumb ptr is: non-null
Resource acquired
Resource destroyed
Our weak ptr is: expired

两者都 getDumbPtr() 和 getWeakPtr() 使用智能指针分配一个 Resource——这个智能指针确保分配的 Resource 在函数结束时被销毁。当 getDumbPtr() 返回一个 Resource* 时，它返回一个悬空指针（因为 std::unique_ptr 在函数结束时销毁了 Resource）。当 getWeakPtr() 返回一个 std::weak_ptr 时，该 std::weak_ptr 同样指向一个无效对象（因为 std::shared_ptr 在函数结束时销毁了 Resource）。

在 main() 内部，我们首先测试返回的裸指针是否为 nullptr。由于裸指针仍然持有已释放资源的地址，此测试失败。无法 main() 判断该指针是否悬空。在这种情况下，因为它是一个悬空指针，如果我们解引用该指针，将导致未定义行为。

接下来，我们测试 weak.expired() 等于 true。由于指向对象的引用计数 weak 等于 0 （因为指向的对象已被销毁），这解析为 true。因此，代码 main() 可以判断出 weak 指向一个无效对象，我们可以据此条件化我们的代码！

注意，如果 std::weak_ptr 已过期，则不应调用 lock() ，因为指向的对象已被销毁，没有对象可以共享。如果你确实在已过期的 std::weak_ptr 上调用 lock() ，它将返回一个指向 nullptr。

总结

std::shared_ptr 可用于需要多个智能指针共同拥有一个资源的情况。当最后一个 std::shared_ptr 离开作用域时，资源将被释放。std::weak_ptr 可用于需要一个智能指针来查看和使用共享资源，但不参与该资源的所有权的情况。
