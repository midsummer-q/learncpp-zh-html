27.8 — 异常的危险与缺点

● 机器译文 课程 27.8 查看英文原文

与几乎所有有好处的事物一样，异常也有一些潜在的缺点。本文并非面面俱到，只是指出使用异常（或决定是否使用异常）时应考虑的一些主要问题。

资源清理

新手程序员在使用异常时遇到的最大问题之一是在异常发生时清理资源。考虑以下示例：

#include <iostream>

try
{
    openFile(filename);
    writeFile(filename, data);
    closeFile(filename);
}
catch (const FileException& exception)
{
    std::cerr << "Failed to write to file: " << exception.what() << '\n';
}

如果 WriteFile() 失败并抛出 FileException 会发生什么？此时，我们已经打开了文件，现在控制流跳转到 FileException 处理程序，它打印错误并退出。注意文件从未被关闭！这个示例应该重写如下：

#include <iostream>

try
{
    openFile(filename);
    writeFile(filename, data);
}
catch (const FileException& exception)
{
    std::cerr << "Failed to write to file: " << exception.what() << '\n';
}

// 确保文件已关闭
closeFile(filename);

这种错误在处理动态分配内存时也常以另一种形式出现：

#include <iostream>

try
{
    auto* john { new Person{ "John", 18, PERSON_MALE } };
    processPerson(john);
    delete john;
}
catch (const PersonException& exception)
{
    std::cerr << "Failed to process person: " << exception.what() << '\n';
}

如果 processPerson() 抛出异常，控制流跳转到 catch 处理程序。结果，john 从未被释放！这个示例比前一个更棘手——因为 john 是 try 块的局部变量，当 try 块退出时它就会超出作用域。这意味着异常处理程序根本无法访问 john（它已经被销毁了），因此无法释放内存。

然而，有两种相对简单的方法可以解决这个问题。首先，将 john 声明在 try 块外部，这样当 try 块退出时它不会超出作用域：

#include <iostream>

Person* john{ nullptr };

try
{
    john = new Person("John", 18, PERSON_MALE);
    processPerson(john);
}
catch (const PersonException& exception)
{
    std::cerr << "Failed to process person: " << exception.what() << '\n';
}

delete john;

因为 john 声明在 try 块外部，它在 try 块和 catch 处理程序中都是可访问的。这意味着 catch 处理程序可以正确地进行清理。

第二种方法是使用一个知道如何在超出作用域时自行清理的类的局部变量（通常称为“智能指针”）。标准库提供了一个名为 std::unique_ptr 的类，可用于此目的。 std::unique_ptr 是一个模板类，它持有一个指针，并在超出作用域时释放它。

#include <iostream>
#include <memory> // for std::unique_ptr

try
{
    auto* john { new Person("John", 18, PERSON_MALE) };
    std::unique_ptr<Person> upJohn { john }; // upJohn 现在拥有 john

    ProcessPerson(john);

    // 当 upJohn 超出作用域时，它将删除 john
}
catch (const PersonException& exception)
{
    std::cerr << "Failed to process person: " << exception.what() << '\n';
}

相关内容

我们介绍 std::unique_ptr 在课程 22.5 -- std::unique_ptr。

最好的选择（只要可能）是优先在栈上分配实现 RAII 的对象（在构造时自动分配资源，在析构时释放资源）。这样，当管理资源的对象因任何原因超出作用域时，它会自动适当地释放资源，因此我们不必担心这类事情！

异常与析构函数

与构造函数不同（在构造函数中抛出异常可以有效地指示对象创建失败），异常应该 绝不 在析构函数中抛出。

问题发生在栈展开过程中从析构函数抛出异常时。如果发生这种情况，编译器会陷入两难境地，不知道是继续栈展开过程还是处理新异常。最终结果是程序会立即终止。

因此，最好的做法是完全避免在析构函数中使用异常。改为向日志文件写入消息。

规则

如果在栈展开期间从析构函数抛出异常，程序将被终止。

性能问题

异常确实会带来一点性能代价。它们会增加可执行文件的大小，并且由于需要执行额外的检查，也可能导致运行速度变慢。然而，异常的主要性能代价发生在实际抛出异常时。在这种情况下，必须展开栈并找到合适的异常处理程序，这是一个相对昂贵的操作。

值得注意的是，一些现代计算机体系结构支持一种称为零成本异常的异常模型。如果支持，零成本异常在非错误情况下没有额外的运行时成本（这是我们最关心性能的情况）。然而，在发现异常的情况下，它们会招致更大的代价。

那么我应该在什么时候使用异常？

异常处理最适合在满足以下所有条件时使用：

  • 所处理的错误可能只偶尔发生。
  • 错误很严重，否则执行无法继续。
  • 错误无法在发生的地方处理。
  • 没有好的替代方法将错误代码返回给调用者。

例如，考虑这样一种情况：你编写了一个函数，期望用户传入磁盘上的文件名。你的函数将打开这个文件，读取一些数据，关闭文件，并将一些结果返回给调用者。现在，假设用户传入了一个不存在的文件名或空字符串。这是异常的好候选吗？

在这种情况下，上面的前两点很容易满足——这不是经常发生的事情，而且当没有数据可处理时，你的函数无法计算结果。该函数也无法处理错误——重新提示用户输入新文件名不是该函数的职责，而且根据程序的设计方式，这可能根本不合适。第四点是关键——是否有好的替代方法将错误代码返回给调用者？这取决于程序的细节。如果有（例如，可以返回空指针或状态码指示失败），那可能是更好的选择。如果没有，那么使用异常是合理的。
