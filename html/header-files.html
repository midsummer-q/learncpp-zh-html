2.11 — 头文件

● 机器译文 课程 2.11 查看英文原文

在课程 2.8 -- 包含多个代码文件的程序，我们讨论了程序如何跨多个文件拆分。还讨论了如何使用前向声明让一个文件中的代码访问另一个文件中定义的内容。

当程序只包含几个小文件时，手动在每个文件顶部添加几个前向声明还算可以。但随着程序变得越来越大（使用了更多的文件和函数），不得不手动在每个文件顶部添加大量（可能不同的）前向声明就变得极其繁琐。例如，如果你有一个包含5个文件的程序，每个文件需要10个前向声明，你就得复制粘贴50个前向声明。现在考虑一个包含100个文件的情况，每个文件需要100个前向声明。这根本扩展不了！

为了解决这个问题，C++程序通常采用不同的方法。

头文件

C++代码文件（扩展名为.cpp）并不是C++程序中唯一常见的文件。另一种类型的文件称为 头文件。头文件通常有.h扩展名，但偶尔也会看到.hpp扩展名或者根本没有扩展名。

按照惯例，头文件用于将一组相关的前向声明传播到代码文件中。

关键提示

头文件允许我们将声明放在一个地方，然后在我们需要的地方导入它们。这可以在多文件程序中节省大量打字工作。

使用标准库头文件

考虑以下程序：

#include <iostream>

int main()
{
    std::cout << "Hello, world!";
    return 0;
}

这个程序使用 std::cout。然而，这个程序从未提供过 std::cout的定义或声明，那么编译器怎么知道 std::cout 是什么呢？

答案是 std::cout 已经在“iostream”头文件中进行了前向声明。当我们 #include <iostream>时，我们请求预处理器将所有内容（包括std::cout的前向声明）从名为“iostream”的文件复制到执行#include的文件中。

关键提示

当你 #include 一个文件时，被包含文件的内容会在包含点插入。这提供了一种从另一个文件引入声明的有用方式。

考虑一下如果 iostream 头文件不存在。无论你在哪里使用 std::cout，你都需要手动输入或复制所有与 std::cout 相关的声明到每个使用 std::cout！这将需要大量关于 std::cout 是如何声明的知识，并且工作量巨大。更糟糕的是，如果添加或更改了函数原型，我们就必须手动更新所有的前向声明。

更简单的做法就是 #include <iostream>！

使用头文件来传播前向声明

现在让我们回到之前课程中讨论的例子。上次我们说到，有两个文件， add.cpp 和 main.cpp，看起来像这样：

add.cpp:

int add(int x, int y)
{
    return x + y;
}

main.cpp:

#include <iostream>

int add(int x, int y); // 使用函数原型进行前向声明

int main()
{
    std::cout << "The sum of 3 and 4 is " << add(3, 4) << '\n';
    return 0;
}

（如果你从头开始重写这个例子，不要忘记添加 add.cpp 到你的项目中，以便它被编译进来）。

在这个例子中，我们使用了一个前向声明，这样编译器就能知道标识符 add 在编译 main.cpp时是什么。如前所述，手动为你想要使用的、位于另一个文件中的每个函数添加前向声明很快就会变得繁琐。

让我们编写一个头文件来减轻这个负担。编写头文件出奇地简单，因为头文件只由两部分组成：

  1. 一个 头文件守卫，我们将在下一课中更详细地讨论（2.12 -- 头文件守卫)。
  2. 头文件的实际内容，应该是我们希望其他文件能够看到的所有标识符的前向声明。

将头文件添加到项目中的操作类似于添加源文件（在课程 2.8 -- 包含多个代码文件的程序)。

如果使用IDE，按照相同步骤操作，并在提示时选择“Header”而不是“Source”。头文件应作为项目的一部分出现。

如果使用命令行，只需在你喜欢的编辑器中创建一个新文件，放在与源文件（.cpp）相同的目录下。与源文件不同，头文件不应 不是 添加到编译命令中（它们通过#include语句隐式包含，并作为源文件的一部分进行编译）。

最佳实践

命名头文件时优先使用.h后缀（除非你的项目已遵循其他约定）。

这是C++头文件长期以来的约定，大多数IDE仍默认使用.h而非其他选项。

头文件通常与代码文件配对，头文件为对应的代码文件提供前向声明。由于我们的头文件将包含对定义在 add.cpp，我们将新的头文件命名为 add.h。

最佳实践

如果头文件与代码文件配对（例如add.h与add.cpp），它们应具有相同的基本名称（add）。

这是我们完成的头文件：

add.h:

// 我们确实应该在这里添加头文件卫士，但为简化起见将其省略（我们将在下一课中介绍头文件卫士）

// 这是 .h 文件的内容，声明应放在这里
int add(int x, int y); // add.h 的函数原型 —— 不要忘记分号！

为了在main.cpp中使用这个头文件，我们必须#include它（使用双引号，而不是尖括号）。

main.cpp:

#include "add.h" // Insert contents of add.h at this point.  Note use of double quotes here.
#include <iostream>

int main()
{
    std::cout << "The sum of 3 and 4 is " << add(3, 4) << '\n';
    return 0;
}

add.cpp:

#include "add.h" // Insert contents of add.h at this point.  Note use of double quotes here.

int add(int x, int y)
{
    return x + y;
}

当预处理器处理 #include "add.h" 行时，它将add.h的内容复制到当前文件的该位置。因为我们的 add.h 包含函数的前向声明 add()，该前向声明将被复制到 main.cpp。最终得到的程序在功能上与手动在顶部添加前向声明的程序相同 main.cpp。

因此，我们的程序将正确编译和链接。

注意：在上图中，“Standard Runtime Library”应标记为“C++ Standard Library”。

在头文件中包含定义如何导致违反单一定义规则

目前，应避免在头文件中放置函数或变量定义。如果头文件被包含到多个源文件中，这样做通常会导致违反单一定义规则（ODR）。

相关内容

我们在第 2.7 -- 前向声明和定义。

我们来演示一下这是如何发生的：

add.h:

// 我们确实应该在这里添加头文件卫士，但为简化起见将其省略（我们将在下一课中介绍头文件卫士）

// 在头文件中定义 add() —— 不要这样做！
int add(int x, int y)
{
    return x + y;
}

main.cpp:

#include "add.h" // Contents of add.h copied here
#include <iostream>

int main()
{
    std::cout << "The sum of 3 and 4 is " << add(3, 4) << '\n';

    return 0;
}

add.cpp:

#include "add.h" // Contents of add.h copied here

当 main.cpp 被编译时， #include "add.h" 将被替换为 add.h 的内容，然后进行编译。因此，编译器将编译类似如下的内容：

main.cpp（预处理后）：

// 来自 add.h：
int add(int x, int y)
{
    return x + y;
}

// 此处为 iostream 头文件的内容

int main()
{
    std::cout << "The sum of 3 and 4 is " << add(3, 4) << '\n';

    return 0;
}

这可以正常编译。

当编译器编译 add.cpp， #include "add.h" 将被替换为 add.h 的内容，然后进行编译。因此，编译器将编译类似如下的内容：

add.cpp（预处理后）：

int add(int x, int y)
{
    return x + y;
}

这也可以正常编译。

最后，链接器将运行。链接器会发现现在有两个函数 add()的定义：一个在main.cpp中，另一个在add.cpp中。这违反了ODR的第2部分，即“在给定的程序中，变量或普通函数只能有一个定义”。

最佳实践

目前，不要在头文件中放置函数和变量定义。

如果在头文件中定义函数或变量，并且该头文件随后被#included到多个源（.cpp）文件中，通常会导致违反单一定义规则（ODR）。

作者注

在后续课程中，我们将遇到其他可以安全地在头文件中定义的定义类型（因为它们不受ODR约束）。这包括内联函数、内联变量、类型和模板的定义。我们在介绍这些内容时会进一步讨论。

源文件应包含其配对头文件

在C++中，最佳实践是让代码文件#include其配对头文件（如果存在）。这允许编译器在编译时而不是链接时捕获某些类型的错误。例如：

add.h:

// 我们确实应该在这里添加头文件卫士，但为简化起见将其省略（我们将在下一课中介绍头文件卫士）

int add(int x, int y);

main.cpp:

#include "add.h"
#include <iostream>

int main()
{
    std::cout << "The sum of 3 and 4 is " << add(3, 4) << '\n';
    return 0;
}

add.cpp:

#include "add.h"         // copies forward declaration from add.h here

double add(int x, int y) // 哎呀，返回类型是 double 而不是 int
{
    return x + y;
}

当 add.cpp 被编译时，前向声明 int add(int x, int y) 将被复制到 add.cpp 在 #include 的位置。当编译器遇到定义时 double add(int x, int y)，它会注意到前置声明和定义的返回类型不匹配。由于函数不能仅通过返回类型来区分，编译器将报错并立即终止编译。在大型项目中，这可以节省大量时间，并帮助定位问题所在。

顺便说一句……

不幸的是，如果问题是参数类型不同而非返回类型不同，则这种方法不起作用。这是因为 C++ 支持重载函数（同名但参数类型不同的函数），因此编译器会假设参数类型不匹配的函数是一个不同的重载。无法面面俱到。

如果 #include "add.h" 不存在，编译器将无法捕捉到问题，因为它看不到不匹配。我们必须等到链接时问题才会显现。

在未来的课程中，我们还会看到许多例子，其中源文件所需的内容定义在配对的头文件中。在这种情况下，包含头文件是必要的。

最佳实践

源文件应 #include 其配对的头文件（如果存在）。

不要 #include .cpp 文件

尽管预处理器会很乐意这样做，但通常不应 #include .cpp 文件。这些文件应添加到项目中并编译。

这样做有几个原因：

  • 这样做可能导致源文件之间的命名冲突。
  • 在大型项目中，很难避免单一定义规则（ODR）问题。
  • 对此类 .cpp 文件的任何更改都会导致该 .cpp 文件以及包含它的任何其他 .cpp 文件重新编译，这可能需要很长时间。头文件通常比源文件更改的频率低。
  • 这样做不符合常规。

最佳实践

避免 #include .cpp 文件。

提示

如果你的项目只有在 #include .cpp 文件时才能编译，这意味着那些 .cpp 文件并未作为项目的一部分被编译。将它们添加到你的项目或命令行中，以便它们被编译。

故障排除

如果你收到一个编译器错误，指出 add.h 找不到，请确保文件确实命名为 add.h。根据你创建和命名的方式，文件可能被命名为类似 add （无扩展名）或 add.h.txt 或 add.hpp。同时确保它与其他代码文件位于同一目录。

如果遇到关于函数 add 未定义的链接器错误，请确保已包含 add.cpp 到项目中，以便函数 add 的定义能够链接到程序中。

尖括号与双引号

你可能好奇为什么我们对 iostream使用尖括号，而对 add.h。可能存在多个目录中有同名的头文件。我们使用尖括号与双引号的区别有助于给预处理器一个提示，指示它应该在哪里查找头文件。

当我们使用尖括号时，是在告诉预处理器这个头文件不是我们自己编写的。预处理器将只在由 include directories。这些 include directories 作为项目/IDE设置/编译器设置的一部分进行配置，并且通常默认为包含编译器或操作系统自带的头文件的目录。预处理器不会在项目的源代码目录中搜索该头文件。

当我们使用双引号时，是在告诉预处理器这个头文件是我们自己编写的。预处理器将首先在当前目录中搜索该头文件。如果在那里找不到匹配的头文件，它将搜索 include directories。

规则

使用双引号包含你自己编写的或预期在当前目录中找到的头文件。使用尖括号包含来自编译器、操作系统或你在系统其他位置安装的第三方库的头文件。

为什么 iostream 没有 .h 扩展名？

另一个常见的问题是“为什么 iostream（或任何其他标准库头文件）没有 .h 扩展名？”答案是 iostream.h 是一个与...不同的头文件 iostream!要解释这个问题需要一段简短的历史课。

当C++最初创建时，标准库中的所有头文件都以 .h 后缀。这些头文件包括：

头文件类型命名约定示例命名空间中的标识符
C++专用<xxx.h>iostream.h全局命名空间
C兼容<xxx.h>stddef.h全局命名空间

原始版本的 cout 和 cin 声明于 iostream.h 在全局命名空间中。生活很一致，而且很好。

当该语言被ANSI委员会标准化时，他们决定将标准库中使用的所有名称移动到 std 命名空间有助于避免与用户声明的标识符发生命名冲突。然而，这带来了一个问题：如果他们将所有名称移入 std 命名空间，那么所有旧程序（包含 iostream.h 的）将无法再运行！

为了解决这个问题，C++ 引入了新的头文件，这些文件缺少 .h 扩展名。这些新头文件将所有名称声明在 std 命名空间。这样，旧程序包含 #include <iostream.h> 不需要重写，而新程序可以 #include <iostream>。

现代 C++ 现在包含 4 组头文件：

头文件类型命名约定示例命名空间中的标识符
C++ 专用（新）<xxx>iostreamstd 命名空间
C 兼容性（新）<cxxx>cstddefstd 命名空间（必需）
全局命名空间（可选）
C++ 专用（旧）<xxx.h>iostream.h全局命名空间
C 兼容性（旧）<xxx.h>stddef.h全局命名空间（必需）
std 命名空间（可选）

警告

新的 C 兼容性头文件 <cxxx> 可以选择在全局命名空间中声明名称，而旧的 C 兼容性头文件 <xxx.h> 可以选择在 std 命名空间。应避免在这些位置使用名称，因为这些名称在其他实现中可能未在这些位置声明。

最佳实践

使用不带 .h 扩展名的标准库头文件。用户自定义头文件应仍然使用 .h 扩展名。

从其他目录包含头文件

另一个常见问题是如何从其他目录包含头文件。

一种（不好的）做法是在 #include 行中包含要包含的头文件的相对路径。例如：

#include "headers/myHeader.h"
#include "../moreHeaders/myOtherHeader.h"

尽管这样可以编译（假设文件存在于那些相对目录中），但这种方法的缺点是需要你在代码中反映你的目录结构。如果你以后更新了目录结构，你的代码将不再有效。

更好的方法是告诉你的编译器或 IDE，你在某个其他位置有一堆头文件，这样当在当前目录找不到它们时，它会去那里查找。通常可以通过在 IDE 项目设置中设置 包含路径 或 搜索目录 来实现。

适用于 Visual Studio 用户

在 Solution Explorer中右键点击你的项目，然后选择 属性，接着选择 VC++ 目录 选项卡。在这里，你会看到一行名为 包含目录。在那里添加你希望编译器搜索额外头文件的目录。

对于 Code::Blocks 用户

在 Code::Blocks 中，转到 项目 菜单并选择 构建选项，接着选择 搜索目录 标签页。在此添加您希望编译器搜索额外头文件的目录。

对于 gcc 用户

使用g++时，您可以使用-I选项指定一个替代包含目录：
g++ -o main -I./source/includes main.cpp

之后没有空格 -I。对于完整路径（而非相对路径），移除 . 之后 -I。

对于 VS Code 用户

在您的 tasks.json 配置文件中，在 “Args” 部分：
"-I./source/includes",

之后没有空格 -I。对于完整路径（而非相对路径），移除 . 之后 -I。

这种方法的优点在于，如果将来更改目录结构，只需更改一个编译器或IDE设置，而无需更改每个代码文件。

头文件可以包含其他头文件

头文件的内容通常会使用其他头文件中声明（或定义）的内容。发生这种情况时，该头文件应#include包含其所需要声明（或定义）的其他头文件。

Foo.h：

#include <string_view> // required to use std::string_view

std::string_view getApplicationName(); // 此处使用了 std::string_view

传递性包含

当您的源(.cpp)文件#include一个头文件时，您也会获得该头文件所#include的任何其他头文件（以及这些头文件所包含的，依此类推）。这些额外的头文件有时被称为 传递性包含，因为它们是隐式包含而非显式包含的。

这些传递性包含的内容可在您的代码文件中使用。然而，通常不应依赖传递性包含的头文件中的内容（除非参考文档表明这些传递性包含是必需的）。头文件的实现可能随时间变化，或在不同系统上有所不同。如果发生这种情况，您的代码可能仅能在某些系统上编译，或者现在能编译但将来不能。通过显式包含代码文件所需的所有头文件，可以轻松避免这种情况。

最佳实践

每个文件应显式#include其编译所需的所有头文件。不要依赖从其他头文件传递性包含的头文件。

遗憾的是，没有简单的方法来检测您的代码文件是否意外依赖了由另一个头文件包含的头文件中的内容。

问：我没有包含<someheader>，但我的程序居然能运行！为什么？

这是本网站最常见的问题之一。答案是：它能运行很可能是因为你包含了其他头文件（例如 <iostream>），而该头文件本身又包含了 <someheader>。虽然你的程序能编译，但根据上述最佳实践，你不应依赖于此。在你机器上能编译的代码，在朋友的机器上可能无法编译。

头文件的包含顺序

如果你的头文件编写正确，并且 #include 了所有需要的内容，那么包含的顺序应该无关紧要。

现在考虑以下场景：假设头文件 A 需要头文件 B 中的声明，但忘记包含它。在我们的代码文件中，如果我们在头文件 A 之前包含头文件 B，代码仍然能编译！这是因为编译器会在编译依赖于这些声明的 A 代码之前，先编译 B 中的所有声明。

然而，如果我们先包含头文件 A，编译器就会报错，因为 A 的代码会在编译器看到 B 的声明之前被编译。这实际上更可取，因为错误暴露了出来，我们就可以修复它。

最佳实践

为了最大程度地让编译器标记出缺少的包含，请按以下顺序排列你的 #include（跳过任何不相关的）：

  • 本代码文件对应的配对头文件（例如， add.cpp 应该 #include "add.h")
  • 同一项目的其他头文件（例如， #include "mymath.h")
  • 第三方库头文件（例如， #include <boost/tuple/tuple.hpp>)
  • 标准库头文件（例如， #include <iostream>)

每个分组内的头文件应按字母顺序排序（除非第三方库的文档指示你另行排序）。

这样，如果你的一个用户定义头文件缺少对第三方库或标准库头文件的 #include，就更容易导致编译错误，以便你能修复它。

头文件最佳实践

以下是创建和使用头文件的更多建议。

  • 始终包含头文件保护（我们将在下一课中介绍）。
  • 不要在头文件中定义变量和函数（目前如此）。
  • 给头文件赋予与其关联的源文件相同的名称（例如， grades.h 与……配对使用 grades.cpp)。
  • 每个头文件应有特定的职责，并尽可能独立。例如，你可以将所有与功能A相关的声明放在A.h中，所有与功能B相关的声明放在B.h中。这样，如果你以后只关心A，就只需包含A.h，而不会获取任何与B相关的内容。
  • 注意需要在代码文件中显式包含哪些头文件以使用所需功能，避免无意中通过传递性包含。
  • 头文件应当 #include 任何包含其所需功能的其他头文件。这样的头文件在单独 #include 到一个 .cpp 文件中时应能成功编译。
  • 只 #include 你需要的内容（不要因为能包含就包含所有内容）。
  • 不要 #include .cpp 文件。
  • 优先将关于某个功能的作用或使用方法的文档放在头文件中。这样更容易被看到。描述工作原理的文档应保留在源文件中。
