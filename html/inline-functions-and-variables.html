7.9 — 内联函数与变量

● 机器译文 课程 7.9 查看英文原文

考虑这样一种情况：你需要编写一些代码来执行某个离散任务，比如从用户读取输入、向文件输出内容或计算某个特定值。在实现这些代码时，你基本上有两种选择：

  1. 将代码作为现有函数的一部分编写（称为“就地”或“内联”编写代码）。
  2. 创建一个新函数（可能还有子函数）来处理该任务。

将代码放入新函数提供了许多潜在的好处，因为小函数：

  • 在整体程序的上下文中更易于阅读和理解。
  • 更易于重用，因为函数天然是模块化的。
  • 更易于更新，因为代码只需在一个地方修改。

然而，使用新函数的一个缺点是每次调用函数时都会有一定的性能开销。考虑以下示例：

#include <iostream>

int min(int x, int y)
{
    return (x < y) ? x : y;
}

int main()
{
    std::cout << min(5, 6) << '\n';
    std::cout << min(3, 2) << '\n';
    return 0;
}

当遇到对 min() 的调用时，CPU 必须存储当前正在执行的指令的地址（以便稍后知道返回位置）以及各种 CPU 寄存器的值（以便返回时恢复）。然后参数 x 和 y 必须被实例化并初始化。然后执行路径必须跳转到 min() 函数中的代码。当函数结束时，程序必须跳回函数调用的位置，并且返回值必须被复制以便输出。每次函数调用都必须执行这些操作。
所有为了设置、促进或清理某个任务（此处为函数调用）而必须执行的额外工作称为 开销。

对于大型和/或执行复杂任务的函数，函数调用的开销通常与函数运行所需的时间相比微不足道。然而，对于小型函数（如上面的 min() ），开销成本可能比实际执行函数代码所需的时间还要大！如果一个小型函数被频繁调用，使用函数可能会导致比就地编写相同代码更显著的性能损失。

内联展开

幸运的是，C++ 编译器有一个技巧可以用来避免这种开销成本： 内联展开 是一个过程，其中函数调用被被调用函数定义中的代码替换。

例如，如果编译器展开上面示例中的 min() 调用，生成的代码将如下所示：

#include <iostream>

int main()
{
    std::cout << ((5 < 6) ? 5 : 6) << '\n';
    std::cout << ((3 < 2) ? 3 : 2) << '\n';
    return 0;
}

注意，对函数 min() 的两次调用已被替换为 min() 函数体中的代码（参数的值替换了形参）。这使我们能够避免这些调用的开销，同时保留代码的结果。

内联代码的性能

除了消除函数调用的成本外，内联展开还可以让编译器更有效地优化生成的代码——例如，因为表达式 ((5 < 6) ? 5 : 6) 现在是一个常量表达式，编译器可以进一步优化 main() 切换到 std::cout << 5 << '\n';。

中的第一个语句。然而，内联展开有其自身的潜在成本：如果被展开的函数体比被替换的函数调用需要更多指令，那么每次内联展开都会导致可执行文件变大。较大的可执行文件往往更慢（因为不能很好地适应内存缓存）。

关于函数是否适合内联（因为消除函数调用开销的收益是否超过可执行文件变大的成本）的决定并不简单。内联展开可能导致性能提升、性能下降或性能不变，具体取决于函数调用的相对成本、函数的大小以及可以执行的其他优化。

内联展开最适合简单、短小的函数（例如不超过几条语句），尤其是单个函数调用可能被执行多次的情况（例如循环内的函数调用）。

内联展开何时发生

每个函数都属于以下两类之一，其中对函数的调用：

  • 可能被展开（大多数函数属于此类）。
  • 不能被展开。

大多数函数属于“可能”类别：如果有利可图，它们的函数调用可以被展开。对于此类函数，现代编译器会评估每个函数和每个函数调用，以确定该特定函数调用是否受益于内联展开。编译器可能决定展开某个给定函数的零个、部分或全部函数调用。

提示

现代优化编译器决定何时应内联展开函数。

最常见的不能被内联展开的函数是其定义位于另一个翻译单元中的函数。由于编译器看不到该函数的定义，它不知道用什么来替换函数调用！

inline 关键字的历史

历史上，编译器要么没有能力确定内联展开是否有益，要么不太擅长。因此，C++ 提供了关键字 inline，它最初旨在作为对编译器的一个提示，表明某个函数（可能）会受益于内联展开。

使用 inline 关键字被称为 内联函数。

下面是一个使用 inline 关键字成为常量：

#include <iostream>

inline int min(int x, int y) // inline 关键字意味着这个函数是一个内联函数
{
    return (x < y) ? x : y;
}

int main()
{
    std::cout << min(5, 6) << '\n';
    std::cout << min(3, 2) << '\n';
    return 0;
}

然而，在现代C++中， inline 关键字不再用于请求函数内联展开。原因有很多：

  • 使用 inline 请求内联展开是一种过早优化，滥用反而可能损害性能。
  • 浮点类型的 inline 关键字只是帮助编译器决定在哪里进行内联展开的提示。编译器完全可以忽略这个请求，而且很可能这样做。编译器也可以在其正常的优化过程中，对没有使用 inline 关键字的函数进行内联展开。
  • 浮点类型的 inline 关键字的粒度定义有误。我们在函数定义上使用 inline 关键字，但内联展开实际上是针对每个函数调用决定的。展开某些函数调用可能有益，而展开其他调用可能有害，并且没有语法来影响这一点。

现代优化编译器通常擅长判断哪些函数调用应该内联——在大多数情况下比人类更擅长。因此，编译器可能会忽略或低估任何使用 inline 来请求函数内联展开的行为。

最佳实践

不要使用 inline 关键字来请求函数内联展开。

内联关键字，现代用法

在前面的章节中，我们提到不应该在头文件中实现函数（具有外部链接），因为当这些头文件被包含到多个 .cpp 文件中时，函数定义会被复制到多个 .cpp 文件中。这些文件随后会被编译，链接器会抛出错误，因为它会注意到你多次定义了同一个函数，这违反了单一定义规则。

在现代C++中，术语 inline 已经演变为“允许多个定义”。因此，内联函数是允许在多个翻译单元中定义的函数（而不违反ODR）。

内联函数有两个主要要求：

  • 编译器需要在每个使用该函数的翻译单元中看到内联函数的完整定义（仅前向声明是不够的）。每个翻译单元只能有一个这样的定义，否则会发生编译错误。
  • 如果同时提供了前向声明，定义可以出现在使用点之后。然而，编译器在看到定义之前可能无法进行内联展开（因此声明和定义之间的任何使用可能都不是内联展开的候选）。
  • 内联函数（具有外部链接，函数默认具有）的每个定义必须相同，否则会导致未定义行为。

规则

编译器需要在每个使用内联函数的地方看到其完整定义，并且内联函数（具有外部链接）的所有定义必须相同（否则会导致未定义行为）。

中介绍了外部链接。

下面是一个示例：

main.cpp:

#include <iostream>

double circumference(double radius); // // 前向声明

inline double pi() { return 3.14159; }

int main()
{
    std::cout << pi() << '\n';
    std::cout << circumference(2.0) << '\n';

    return 0;
}

math.cpp

inline double pi() { return 3.14159; }

double circumference(double radius)
{
    return 2.0 * pi() * radius;
}

注意，两个文件都有函数 pi() 的定义——然而，由于该函数被标记为 inline，这是可以接受的，链接器会去重。如果你从 inline 的两个定义中移除 pi()关键字，你会得到一个ODR违规（因为不允许非内联函数有重复定义）。

可选阅读

虽然内联的历史用途（进行内联展开）和现代用途（允许多个定义）看起来可能有些不相关，但它们高度关联。

历史上，假设我们有一些简单的函数，它是内联展开的绝佳候选，所以我们将其标记为 inline。为了实际对函数调用进行内联展开，编译器必须在每个使用该函数的翻译单元中看到该函数的完整定义——否则它不知道用什么替换每个函数调用。定义在另一个翻译单元中的函数无法在当前编译的翻译单元中内联展开。

简单的内联函数通常需要在多个翻译单元中使用。但一旦我们将函数定义复制到每个翻译单元（根据前面的要求），这就违反了ODR关于函数在整个程序中只能有一个定义的要求。解决这个问题的最佳方案就是让内联函数不受ODR中每个程序只能有一个定义的限制。

因此，历史上我们使用 inline 来请求内联展开，而ODR豁免是使这些函数在多个翻译单元中可内联展开所需的细节。现代我们使用 inline 来获得ODR豁免，并让编译器处理内联展开的事情。内联函数的工作机制没有改变，只是我们的关注点变了。

你可能想知道为什么内联函数被允许ODR豁免，而非内联函数仍然必须遵守ODR的这一部分。对于非内联函数，我们期望函数只定义一次（在一个翻译单元中）。如果链接器遇到非内联函数的多个定义，它会认为这是由于两个独立定义的函数之间的命名冲突。而对具有多个定义的非内联函数的任何调用都会导致关于哪个定义是正确的调用目标的潜在歧义。但对于内联函数，所有定义都被假定为同一个内联函数，因此该翻译单元内的函数调用可以被内联展开。如果函数调用没有被内联展开，那么多个定义中哪个是正确的匹配目标就没有歧义——任何一个都可以！

内联函数通常定义在头文件中，可以通过 #include 将它们包含到任何需要看到标识符完整定义的代码文件的顶部。这确保了标识符的所有内联定义都是相同的。

pi.h：

#ifndef PI_H
#define PI_H

inline double pi() { return 3.14159; }

#endif

main.cpp:

#include "pi.h" // will include a copy of pi() here
#include <iostream>

double circumference(double radius); // // 前向声明

int main()
{
    std::cout << pi() << '\n';
    std::cout << circumference(2.0) << '\n';

    return 0;
}

math.cpp

#include "pi.h" // will include a copy of pi() here

double circumference(double radius)
{
    return 2.0 * pi() * radius;
}

这对于 仅头文件库特别有用，它们是一个或多个实现某些功能的头文件（不包含 .cpp 文件）。仅头文件库很流行，因为使用它们不需要将源文件添加到项目中，也不需要链接任何东西。你只需 #include 仅头文件库，然后就可以使用它。

大多数情况下，你不应该将函数或变量标记为内联，除非你在头文件中定义它们（并且它们不是隐式内联的）。

最佳实践

避免使用 inline 关键字，除非你有具体且令人信服的理由（例如，你在头文件中定义这些函数或变量）。

为什么不把所有函数都设为内联并定义在头文件中？

主要是因为这样做会显著增加编译时间。

当一个包含内联函数的头文件被 #include 到源文件中时，该函数定义将作为该翻译单元的一部分被编译。一个内联函数被 #include 到 6 个翻译单元中，其定义将被编译 6 次（在链接器去重定义之前）。相反，定义在源文件中的函数，无论其前向声明被包含到多少个翻译单元中，其定义只会被编译一次。

其次，如果源文件中定义的函数发生更改，只需要重新编译该单个源文件。当头文件中的内联函数发生更改时，每个包含该头文件（直接或通过另一个头文件）的代码文件都需要重新编译。在大型项目中，这可能导致级联重新编译，产生巨大影响。

内联变量 C++17

在上面的例子中， pi() 被编写为一个返回常量值的函数。如果 pi 被实现为一个（const）变量会更直接。然而，在 C++17 之前，这样做存在一些障碍和低效之处。

C++17 引入了 内联变量，即允许在多个文件中定义的变量。内联变量的工作方式与内联函数类似，并且具有相同的要求（编译器必须在变量使用的每个地方看到相同的完整定义）。
