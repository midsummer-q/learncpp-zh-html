A.4 — C++ 常见问题解答

● 机器译文 课程 A.4 查看英文原文


有些问题总是被反复问及。本常见问题解答将尝试回答最常见的问题。

问题1：为什么我们不应该使用“using namespace std”？

语句 using namespace std; 我们还调用了 using 指令。using 指令允许在 using 指令语句的作用域内访问给定命名空间中的所有标识符。

你可能见过这样的代码：

#include <iostream>

using namespace std;

int main()
{
    cout << "Hello world!";

    return 0;
}

这允许我们使用来自 std 命名空间的名称，而无需反复显式输入 std:: 在上面的程序中，我们只需输入 cout 而不是 std::cout。听起来很棒，对吧？

然而，当编译器遇到 using namespace std时，它会使 std 命名空间中的每一个标识符在全局作用域中可用（因为 using 指令被放置在那里）。这引入了三个关键挑战：

  • 你选择的名称与 std 命名空间中已存在的名称发生命名冲突的可能性大大增加。
  • 标准库的新版本可能会破坏你当前工作的程序。这些未来版本可能引入导致新命名冲突的名称，或者在最坏的情况下，你的程序行为可能会无声无息地意外改变！
  • 缺少 std:: 前缀使得读者更难理解哪些是 std 库名称，哪些是用户定义的名称。

基于这些原因，我们建议完全避免使用 using namespace std （或任何其他 using 指令）。节省的那一点点打字时间不值得带来额外的麻烦和未来风险。

问题2：为什么我可以在没有包含声明某个函数或类型的头文件的情况下使用它？

例如，许多读者问为什么他们的程序使用了 std::string_view 需要 #include <string_view> ，即使没有 #include 也能正常工作。

头文件可以 #include 其他头文件。当你 #include 一个头文件时，你也会得到它所包含的所有其他头文件（以及这些头文件所包含的所有头文件）。所有你没有显式包含但随之而来的额外头文件被称为“传递包含”。

在您的 main.cpp 文件，你可能 #include <iostream>。在你的编译器上，如果你的 <iostream> 头文件包含了 <string_view> 头文件（供其自身使用），那么当你 #include <iostream> 时，你将得到 <string_view> 头文件的内容（以及 <iostream> 包含的任何其他头文件）。这意味着你的 main.cpp 将能够使用 std::string_view 类型，而无需显式包含 <string_view> 头文件。

尽管这可能在你的编译器上编译通过，但你不应依赖于此。现在能编译的代码，可能在另一个编译器上无法编译，甚至在你编译器的未来版本上也无法编译。

没有办法在发生这种情况时发出警告，也无法阻止它发生。你能做的最好的事情是注意显式包含你使用的所有内容的正确头文件。在几个不同的编译器上编译你的程序可能有助于识别在其他编译器上被传递包含的头文件。

问题3：我的代码产生了未定义行为，但似乎运行正常。这可以吗？

又名：“我做了你告诉我不要做的事情，但它成功了。那有什么问题？”

未定义行为发生在你执行一个 C++ 语言未定义其行为的操作时。实现未定义行为的代码可能表现出 任何 以下症状：

  • 你的程序每次运行时产生不同的结果。
  • 你的程序行为不一致（有时产生期望的结果，有时不）。
  • 你的程序始终产生相同的错误结果。
  • 你的程序最初似乎正常工作，但后来在程序中产生了一些不正确的结果。
  • 你的程序崩溃，无论是立即还是稍后。
  • 你的程序在某些编译器或平台上能工作，但在其他编译器或平台上不能。
  • 你的程序正常工作，直到你更改一些看似无关的代码。
  • 你的程序似乎无论如何都能产生期望的结果。

未定义行为最大的问题之一是程序表现出的行为可能随时因任何原因而改变。因此，尽管这样的代码现在可能看起来能工作，但无法保证以后再次运行时仍然如此。

Q4：为什么我的产生未定义行为的代码会生成某个特定的结果？

读者经常问，在他们的系统上发生了什么导致产生了特定的结果。在大多数情况下，很难说清楚，因为产生的结果可能取决于当前程序状态、编译器设置、编译器如何实现某个特性、计算机架构和/或操作系统。例如，如果你打印一个未初始化变量的值，你可能会得到垃圾值，或者总是得到某个特定的值。这取决于变量的类型、编译器如何在内存中布局变量，以及该内存之前的内容（这可能受到操作系统或程序在此之前状态的影响）。

虽然这样的答案在机制上可能很有趣，但通常没什么用（而且当任何其他东西改变时，它很可能会改变）。这就像问：“当我把安全带穿过方向盘并连接到油门上时，为什么在雨天我转头时车会向左偏？”最好的答案不是对正在发生的事情进行物理解释，而是“不要那样做”。

Q5：为什么当我尝试编译一个看起来应该能工作的示例时，却遇到了编译错误？

最常见的原因是你的项目使用了错误的语言标准进行编译。

C++ 在每个新的语言标准中都引入了许多新特性。如果我们的某个示例使用了 C++17 中引入的特性，但你的程序使用 C++14 语言标准编译，那么它可能无法编译，因为我们使用的特性不被所选的语言标准支持。

尝试将你的语言标准设置为编译器支持的最新版本，看看是否能解决问题。你也可以通过运行这里的程序来检查你的编译器是否正确配置为你期望的语言标准： 0.13 -- What language standard is my compiler using?。

Q6：为什么我应该从 foo.cpp 中 #include “foo.h”？

源文件（例如 foo.cpp）包含其配对的头文件（例如 foo.h）是一种最佳实践。在许多情况下，foo.h 包含 foo.cpp 正确编译所需的定义。

然而，即使 foo.cpp 在没有 foo.h 的情况下也能编译，包含配对的头文件可以让编译器发现两个文件之间某些类型的不一致（例如，当函数的返回类型与其前向声明的返回类型不匹配时）。如果不包含，可能会导致未定义行为。

#include 的成本可以忽略不计，因此包含头文件几乎没有缺点。

Q7：为什么我的项目只有在从 “main.cpp” 中 #include “foo.cpp” 时才能编译？

这几乎总是因为忘记将 foo.cpp 添加到你的项目和/或编译命令行中。更新你的项目和/或命令行以包含每个源（.cpp）文件。当你编译项目时，你应该看到每个源文件都被编译。

通常，在包含多个文件的项目中，编译器会单独编译每个源（.cpp）文件。所有源文件编译完成后，链接器将它们链接在一起并创建最终输出文件（例如可执行文件）。然而，如果你将代码拆分到两个或多个文件中（例如 main.cpp 和 foo.cpp），然后只编译 main.cpp，你可能会遇到编译错误或链接错误，因为项目所需的部分代码没有被编译。

新手程序员有时会发现，他们可以通过在 main.cpp 中添加 #include "foo.cpp" 而不是将 foo.cpp 添加到项目或编译命令行来使程序工作。这样做之后，当编译 main.cpp 时，预处理器会创建一个由 foo.cpp 和 main.cpp 的代码组成的翻译单元，然后被编译和链接。在较小的项目中，这可能会工作。那么为什么不这样做呢？

有几个原因：

  1. 它可能导致文件之间的命名冲突。
  2. 很难避免 ODR 违规。
  3. 任何对 .cpp 文件的更改都会导致整个项目被重新编译。这可能需要很长时间。

Q8：为什么我需要在 main 的末尾 return 0 ？

你不需要。 main() 函数是特殊的，如果你不提供 return 语句，它会隐式返回 0。

然而，任何其他返回值函数如果在到达函数体末尾时没有遇到 return 语句，将产生未定义行为。

为了保持一致性，我们建议从 main()中显式返回 0。但如果你为了简洁而倾向于省略 main() 中的 return 语句，也是可以的。只是不要错误地认为其他返回值函数也类似地工作。

Q9：当我编译本网站的一个示例时，我得到一个类似于“类模板 XXX 的参数列表缺失”的错误。为什么？

最可能的原因是示例使用了称为类模板参数推导（CTAD）的特性，这是 C++17 的特性。许多编译器默认使用 C++14，不支持此特性。

如果以下程序无法为你编译，那就是原因：

#include <utility> // for std::pair

int main()
{
    std::pair p2{ 1, 2 }; // 使用 CTAD 从初始化器推导出 std::pair<int, int>（C++17）

    return 0;
}

Q10：为什么我们在按值传递或返回时不将函数参数或返回类型设为 const？

我们通常不 const 按值函数参数，因为：

  • 将这样的参数设为 const 对函数的调用者没有提供有意义的价值，反而增加了函数接口的杂乱。
  • 我们通常不关心函数是否修改这些参数，因为它们只是副本，在函数结束时会被销毁。

我们不会对 const 按值返回的值使用 const，因为：

  • 如果返回类型是非类类型（例如基本类型），const 会被忽略。
  • 如果返回类型是类类型，const 可能会抑制某些优化（例如移动语义）。

注意： const 在按地址或按引用传递/返回时是相关的。

Q11: 为什么我应该使用 constexpr？

Constexpr 和其他编译时编程技术提供了许多好处，包括：

  • 更小更快的代码。
  • 我们可以让编译器检测某些类型的错误，并在它们发生时停止编译。
  • 编译时不允许未定义行为。
  • 能够在需要常量表达式的地方使用变量和函数。

最后一点可能是最不可避免的，因为某些 C++ 特性需要编译时已知的值。

Q12: 如果我知道一个函数在我的程序中只会在运行时被求值，为什么还要将其标记为 constexpr？

有几个原因你可能想这样做：

  1. 使用 constexpr 几乎没有缺点，即使在非编译时求值的上下文中，它也可能帮助编译器进行优化。
  2. 仅仅因为你目前没有在编译时可求值的上下文中调用该函数，并不意味着当你修改或扩展程序时你不会在这样的上下文中调用它。如果你还没有把函数设为 constexpr，当你开始在这样的上下文中调用它时，你可能不会想到要这样做，然后你就会错过性能提升。或者，当你需要在某个需要常量表达式的上下文中使用返回值时，你可能被迫以后才把它设为 constexpr。
  3. 重复有助于巩固最佳实践。

在一个非平凡的项目中，以函数将来可能被重用（或扩展）的心态来实现它们是一个好主意。每次修改现有函数时，你都有破坏它的风险，这意味着它需要重新测试，这需要时间和精力。花一两分钟“第一次就做对”通常是值得的，这样你以后就不必重做（并重新测试）了。

Q13: 为什么我不应该在同一个表达式中多次调用同一个输入函数？

在大多数情况下，C++ 标准没有指定操作数（包括函数参数）的求值顺序。运算符的优先级和结合性仅用于确定操作数如何与运算符分组，以及值计算的顺序。

例如，给定语句 std::cout << subtract(getUserInput(), getUserInput())，在函数调用 subtract() 中，左参数或右参数可能先被求值。假设用户输入了值 5 和 2。如果左参数先被求值，左参数将求值为 5，右参数将求值为 2。 5 - 2 等于 3。如果右参数先被求值，右参数将求值为 5，左参数将求值为 2。 2 - 5 等于 -3。因此，这个语句可能打印 3 或 -3。

可以通过将对 getUserInput() 的每次函数调用都作为单独的语句（这样顺序是确定的），并将返回值存储在变量中直到需要时使用，来消除歧义。

Q14: 测验不够多！我在哪里可以获得更多练习？

我们建议 https://www.codewars.com/，那里有大量的小型练习，可以帮助提高你的一般问题解决能力和 C++ 实现技能。而且很有趣！

一旦你有了解决方案，你可以将其与别人的答案进行比较，以了解替代方法，或者理解你自己的代码可以在哪些方面改进。

然而，由于一次性练习有一次性答案，解决这样的测验并不能真正鼓励编写高质量的代码，也不能展示不遵循最佳实践会发生什么。为此，没有什么比创建自己的项目更好的了。

从小的开始——一个简单的游戏或模拟。然后随着时间的推移逐步添加功能。随着项目复杂性的增加，你会开始看到代码中的各种缺陷显现出来。这将帮助你确定代码的哪些区域需要质量改进。
