9.4 — 检测和处理错误

● 机器译文 课程 9.4 查看英文原文

在课程 9.3 -- C++ 中常见的语义错误，我们介绍了许多 C++ 新手程序员常遇到的常见语义错误类型。如果错误是由于误用语言特性或逻辑错误导致的，那么只需纠正错误即可。

但程序中的大多数错误并非由于无意中误用语言特性而发生——相反，大多数错误是由于程序员做出了错误的假设和/或缺乏适当的错误检测/处理导致的。

例如，在一个用于查找学生成绩的函数中，你可能假设了：

  • 被查找的学生存在。
  • 所有学生姓名都是唯一的。
  • 班级使用字母评分（而非通过/不通过）。

如果这些假设中有任何一个不成立呢？如果程序员没有预料到这些情况，当这些情况发生时（通常是在未来的某个时刻，远在函数编写之后），程序很可能会发生故障或崩溃。

假设错误通常发生在三个关键地方：

  • 当函数返回时，程序员可能假设被调用的函数成功了，但实际上并未成功。
  • 当程序接收输入（来自用户或文件）时，程序员可能假设输入格式正确且在语义上有效，但实际上并非如此。
  • 当函数被调用时，程序员可能假设参数在语义上有效，但实际上并非如此。

许多新手程序员编写代码后只测试 快乐路径：即没有错误的情况。但你也应该规划并测试你的 悲伤路径，即事情可能出错的情况。在课程 3.10 -- 在问题变成麻烦之前发现它们中，我们定义了 防御性编程 ，即尝试预见软件可能被最终用户或开发者（程序员本人或他人）误用的所有方式。一旦你预见（或发现）了某些误用，下一步就是处理它。

在本课中，我们将讨论函数内部的错误处理策略（当出现问题时该怎么做）。在接下来的课程中，我们将讨论验证用户输入，然后介绍一个有用的工具来帮助记录和验证假设。

函数中的错误处理

函数可能因多种原因失败——调用者可能传入了无效值的参数，或者函数体内可能发生某些失败。例如，一个用于打开文件进行读取的函数可能会因为找不到文件而失败。

当这种情况发生时，你有多种选择。没有处理错误的最佳方法——这实际上取决于问题的性质以及问题是否可以修复。

有四种通用策略可以使用：

  • 在函数内部处理错误
  • 将错误传回给调用者处理
  • 终止程序
  • 抛出异常

在函数内部处理错误

如果可能，最好的策略是在发生错误的同一函数中从错误中恢复，这样错误可以被限制和纠正，而不会影响函数外部的任何代码。这里有两个选项：重试直到成功，或者取消正在执行的操作。

如果错误是由于程序无法控制的外部因素引起的，程序可以重试直到成功。例如，如果程序需要互联网连接，而用户断开了连接，程序可以显示警告，然后使用循环定期重新检查互联网连接。或者，如果用户输入了无效输入，程序可以要求用户重试，并循环直到用户成功输入有效输入。我们将在下一课中展示处理无效输入和使用循环重试的示例（9.5 -- std::cin与处理无效输入)。

另一种策略是忽略错误和/或取消操作。例如：

// 如果 y=0 则静默失败
void printIntDivision(int x, int y)
{
    if (y != 0)
        std::cout << x / y;
}

在上面的示例中，如果用户传入了无效的 y值，我们只是忽略打印除法操作结果的请求。这样做的主要挑战是调用者或用户无法知道出了问题。在这种情况下，打印错误消息可能会有所帮助：

void printIntDivision(int x, int y)
{
    if (y != 0)
        std::cout << x / y;
    else
        std::cout << "Error: Could not divide by zero\n";
}

然而，如果调用函数期望被调用函数产生返回值或一些有用的副作用，那么仅仅忽略错误可能不是一个选项。

将错误传回给调用者

在许多情况下，错误无法在检测到它的函数中合理处理。例如，考虑以下函数：

int doIntDivision(int x, int y)
{
    return x / y;
}

如果 y 等于 0，我们该怎么办？我们不能只是跳过程序逻辑，因为函数需要返回某个值。我们不应该要求用户为 y 因为这是一个计算函数，将输入例程引入其中可能适合也可能不适合调用该函数的程序。

在这种情况下，最佳选择可能是将错误传回给调用者，希望调用者能够处理它。

我们该怎么做呢？

如果函数有 void 返回类型，可以将其改为返回一个 bool 指示成功或失败。例如，不写成：

void printIntDivision(int x, int y)
{
    if (y != 0)
        std::cout << x / y;
    else
        std::cout << "Error: Could not divide by zero\n";
}

我们可以这样做：

bool printIntDivision(int x, int y)
{
    if (y == 0)
    {
        std::cout << "Error: could not divide by zero\n";
        return false;
    }
    
    std::cout << x / y;

    return true;
}

这样，调用者可以检查返回值，看函数是否因某种原因失败。

如果函数返回一个普通值，情况就稍微复杂一些。在某些情况下，返回值的全部范围并未被使用。在这种情况下，我们可以使用一个正常情况下不可能出现的返回值来表示错误。例如，考虑以下函数：

// x 的倒数是 1/x
double reciprocal(double x)
{
    return 1.0 / x;
}

某个数的倒数 x 定义为 1/x，一个数乘以它的倒数等于1。

然而，如果用户调用这个函数为 reciprocal(0.0)会发生什么？我们会得到一个 divide by zero 错误和程序崩溃，所以显然我们应该防范这种情况。但这个函数必须返回一个double值，那么我们应该返回什么值呢？事实证明，这个函数永远不会产生 0.0 作为合法结果，所以我们可以返回 0.0 来表示错误情况。

// x 的倒数是 1/x，如果 x=0 则返回 0.0
constexpr double error_no_reciprocal { 0.0 }; // 也可以放在命名空间中

double reciprocal(double x)
{
    if (x == 0.0)
       return error_no_reciprocal;

    return 1.0 / x;
}

一个 哨兵值 是一个在函数或算法上下文中具有特殊含义的值。在我们上面的 reciprocal() 函数中， 0.0 是一个哨兵值，表示函数失败。调用者可以测试返回值是否与哨兵值匹配——如果匹配，则调用者知道函数失败了。虽然函数通常直接返回哨兵值，但返回一个描述哨兵值的常量可以增加可读性。

然而，如果函数可以产生所有可能的返回值，那么使用哨兵值来表示错误就有问题（因为调用者无法判断返回值是有效值还是错误值）。

致命错误

如果错误严重到程序无法继续正常运行，这被称为 不可恢复 错误（也称为 致命错误）。在这种情况下，最好的做法是终止程序。如果你的代码在 main() 或一个直接从 main()调用的函数中，最好的做法是让 main() 返回一个非零状态码。然而，如果你深陷某个嵌套的子函数中，可能不方便或不可能将错误一直传播回 main()。在这种情况下，可以使用 halt statement （例如 std::exit()）。

例如：

double doIntDivision(int x, int y)
{
    if (y == 0)
    {
        std::cout << "Error: Could not divide by zero\n";
        std::exit(1);
    }
    return x / y;
}

异常

因为从函数向调用者返回错误很复杂（而且多种不同的方式会导致不一致，不一致又会导致错误），C++提供了一种完全不同的方式将错误传回给调用者： exceptions。

基本思想是，当错误发生时，会“抛出”一个异常。如果当前函数没有“捕获”该错误，调用该函数的函数有机会捕获它。如果调用者没有捕获错误，调用者的调用者有机会捕获错误。错误会逐步向上移动调用栈，直到它被捕获并处理（此时执行正常继续），或者直到main()未能处理错误（此时程序因异常错误而终止）。

何时使用 std::cout vs std::cerr 与日志记录

在课程 3.4 -- 基本调试策略中，我们介绍了 std::cerr。您可能想知道何时（或是否）应该使用 std::cerr vs std::cout 与记录到文本文件。

默认情况下， std::cout 和 std::cerr 都将文本打印到控制台。然而，现代操作系统提供了一种将输出流重定向到文件的方法，以便稍后可以捕获输出以供审查或自动处理。

对于这个讨论，区分两种类型的应用程序是有用的：

  • 交互式应用程序 是那些用户运行后会与之交互的应用程序。大多数独立应用程序，如游戏和音乐应用，都属于这一类。
  • 非交互式应用程序 是不需要用户交互即可运行的应用程序。这些程序的输出可能被用作另一个应用程序的输入。

在非交互式应用程序中，有两种类型：

  • 工具 是非交互式应用程序，通常启动以产生一些即时结果，然后在产生这样的结果后终止。一个例子是Unix的grep命令，它是一个搜索文本中匹配某种模式的行的实用程序。
  • 服务 是非交互式应用程序，通常静默地在后台运行以执行某些持续的功能。一个例子是病毒扫描程序。

以下是一些经验法则：

  • 使用 std::cout 用于所有常规的、面向用户的文本。
  • 对于交互式程序，使用 std::cout 用于正常的面向用户的错误消息（例如“您的输入无效”）。使用 std::cerr 或日志文件来记录状态和诊断信息，这些信息可能有助于诊断问题，但普通用户可能不感兴趣。这可以包括技术警告和错误（例如函数x的输入错误）、状态更新（例如成功打开文件x，无法连接到互联网服务x）、长时间任务的完成百分比（例如编码完成50%）等……
  • 对于非交互式程序（工具或服务），使用 std::cerr 仅用于错误输出（例如无法打开文件x）。这允许错误与正常输出分开显示或解析。
  • 对于任何事务性类型的应用程序（例如处理特定事件的应用程序，如交互式Web浏览器或非交互式Web服务器），使用日志文件来生成事件的事务日志，以便以后审查。这可以包括输出到日志文件正在处理的文件、完成百分比的更新、开始某些计算阶段的时间戳、警告和错误消息等……
