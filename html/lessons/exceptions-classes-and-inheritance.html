27.5 — 异常、类与继承

● 机器译文 课程 27.5 查看英文原文

异常与成员函数

在本教程中，到目前为止，你只看到异常在非成员函数中使用。然而，异常在成员函数中同样有用，甚至在重载运算符中更为有用。考虑以下作为简单整数数组类一部分的重载 [] 运算符：

int& IntArray::operator[](const int index)
{
    return m_data[index];
}

虽然只要 index 是有效的数组索引，这个函数就能很好地工作，但这个函数严重缺乏一些良好的错误检查。我们可以添加一个 assert 语句来确保索引有效：

int& IntArray::operator[](const int index)
{
    assert (index >= 0 && index < getLength());
    return m_data[index];
}

现在，如果用户传入无效索引，程序将导致断言错误。不幸的是，由于重载运算符对参数的数量和类型以及返回值有特定要求，无法灵活地返回错误码或布尔值给调用者处理。然而，由于异常不会改变函数的签名，它们在这里可以发挥很大作用。下面是一个例子：

int& IntArray::operator[](const int index)
{
    if (index < 0 || index >= getLength())
        throw index;

    return m_data[index];
}

现在，如果用户传入无效索引，operator[] 将抛出一个 int 异常。

当构造函数失败时

构造函数是类中异常非常有用的另一个领域。如果构造函数必须因某种原因失败（例如用户传入了无效输入），只需抛出一个异常来指示对象创建失败。在这种情况下，对象的构造被中止，并且所有类成员（它们已经在构造函数体执行之前被创建和初始化）会像往常一样被析构。

然而，类的析构函数永远不会被调用（因为对象从未完成构造）。由于析构函数从未执行，你不能依赖该析构函数来清理任何已经分配的资源。

这就引出了一个问题：如果我们在构造函数中分配了资源，然后在构造函数完成之前发生异常，我们该怎么办？我们如何确保已经分配的资源被正确清理？一种方法是将任何可能失败的代码包装在 try 块中，使用相应的 catch 块捕获异常并进行必要的清理，然后重新抛出异常（我们将在第 27.6 节 -- 重新抛出异常中讨论这个主题）。然而，这增加了大量杂乱代码，并且容易出错，特别是当你的类分配多个资源时。

幸运的是，有一种更好的方法。利用即使构造函数失败，类成员也会被析构的事实，如果你在类的成员内部（而不是在构造函数本身）进行资源分配，那么这些成员在被析构时可以自行清理。

下面是一个示例：

#include <iostream>

class Member
{
public:
	Member()
	{
		std::cerr << "Member allocated some resources\n";
	}

	~Member()
	{
		std::cerr << "Member cleaned up\n";
	}
};

class A
{
private:
	int m_x {};
	Member m_member;

public:
	A(int x) : m_x{x}
	{
		if (x <= 0)
			throw 1;
	}
	
	~A()
	{
		std::cerr << "~A\n"; // 不应被调用
	}
};


int main()
{
	try
	{
		A a{0};
	}
	catch (int)
	{
		std::cerr << "Oops\n";
	}

	return 0;
}

这会打印：

Member allocated some resources
Member cleaned up
Oops

在上面的程序中，当类 A 抛出异常时，A 的所有成员都被析构。m_member 的析构函数被调用，提供了清理它分配的任何资源的机会。

这就是 RAII（在第 ，增加了移动构造函数和移动赋值运算符。节中介绍）被高度提倡的部分原因——即使在异常情况下，实现 RAII 的类也能够自行清理。

然而，创建一个像 Member 这样的自定义类来管理资源分配并不高效。幸运的是，C++ 标准库提供了符合 RAII 的类来管理常见资源类型，例如文件（std::fstream，在第 28.6 节 -- 基本文件 I/O中介绍）和动态内存（std::unique_ptr 和其他智能指针，在第 22.1 -- 智能指针和移动语义简介)。

例如，不要这样：

class Foo
private:
    int* ptr; // Foo 将处理分配/释放

这样做：

class Foo
private:
    std::unique_ptr<int> ptr; // std::unique_ptr 将处理分配/释放

中介绍）。在前一种情况下，如果 Foo 的构造函数在 ptr 分配其动态内存后失败，Foo 将负责清理，这可能具有挑战性。在后一种情况下，如果 Foo 的构造函数在 ptr 分配其动态内存后失败，ptr 的析构函数将执行并将该内存返回给系统。当资源处理委托给符合 RAII 的成员时，Foo 不需要进行任何显式清理！

异常类

使用基本数据类型（如 int）作为异常类型的主要问题之一是它们本质上是模糊的。更大的问题是当 try 块中有多个语句或函数调用时，如何区分异常的含义。

// 使用上面的 IntArray 重载 operator[]

try
{
    int* value{ new int{ array[index1] + array[index2]} };
}
catch (int value)
{
    // 我们在这里捕获什么？
}

在这个例子中，如果我们捕获一个 int 异常，这实际上告诉我们什么？是数组索引越界？是 operator+ 导致整数溢出？还是 operator new 因为内存不足而失败？不幸的是，在这种情况下，没有简单的方法来区分。虽然我们可以抛出 const char* 异常来解决识别出了什么问题的问题，但这仍然不能让我们以不同的方式处理来自不同来源的异常。

解决这个问题的一种方法是使用异常类。一个 异常类 就是一个普通的类，专门设计用来作为异常抛出。让我们设计一个简单的异常类，用于我们的 IntArray 类：

#include <string>
#include <string_view>

class ArrayException
{
private:
	std::string m_error;

public:
	ArrayException(std::string_view error)
		: m_error{ error }
	{
	}

	const std::string& getError() const { return m_error; }
};

以下是使用这个类的完整程序：

#include <iostream>
#include <string>
#include <string_view>

class ArrayException
{
private:
	std::string m_error;

public:
	ArrayException(std::string_view error)
		: m_error{ error }
	{
	}

	const std::string& getError() const { return m_error; }
};

class IntArray
{
private:
	int m_data[3]{}; // 为简单起见，假设数组长度为 3

public:
	IntArray() {}

	int getLength() const { return 3; }

	int& operator[](const int index)
	{
		if (index < 0 || index >= getLength())
			throw ArrayException{ "Invalid index" };

		return m_data[index];
	}

};

int main()
{
	IntArray array;

	try
	{
		int value{ array[5] }; // 下标越界
	}
	catch (const ArrayException& exception)
	{
		std::cerr << "An array exception occurred (" << exception.getError() << ")\n";
	}
}

使用这样的类，我们可以让异常返回问题发生的描述，这提供了出错的上下文。而且由于 ArrayException 是它自己的独特类型，我们可以专门捕获由数组类抛出的异常，并在需要时将它们与其他异常区别对待。

注意，异常处理程序应该通过引用而不是值来捕获类异常对象。这可以防止编译器在捕获点复制异常，当异常是类对象时这可能很昂贵，并且可以防止处理派生异常类时的对象切片（我们稍后会讨论）。通常应避免通过指针捕获异常，除非你有特定的理由这样做。

最佳实践

基本类型的异常可以通过值捕获，因为它们复制成本低。
类类型的异常应该通过（const）引用捕获，以防止昂贵的复制和切片。

异常与继承

由于可以将类作为异常抛出，并且类可以从其他类派生，我们需要考虑当使用继承类作为异常时会发生什么。事实证明，异常处理程序不仅会匹配特定类型的类，还会匹配从该特定类型派生的类！考虑以下示例：

#include <iostream>

class Base
{
public:
    Base() {}
};

class Derived: public Base
{
public:
    Derived() {}
};

int main()
{
    try
    {
        throw Derived();
    }
    catch (const Base& base)
    {
        std::cerr << "caught Base";
    }
    catch (const Derived& derived)
    {
        std::cerr << "caught Derived";
    }

    return 0;
}

在上面的例子中，我们抛出了一个 Derived 类型的异常。然而，这个程序的输出是：

caught Base

发生了什么？

首先，如上所述，派生类会被基类型的处理程序捕获。因为 Derived 派生自 Base，Derived 是一种 Base（它们具有 is-a 关系）。其次，当 C++ 试图为引发的异常寻找处理程序时，它是顺序进行的。因此，C++ 做的第一件事是检查 Base 的异常处理程序是否匹配 Derived 异常。因为 Derived 是一种 Base，答案是肯定的，它执行 Base 类型的 catch 块！在这种情况下，Derived 的 catch 块甚至从未被测试。

为了使这个示例按预期工作，我们需要翻转 catch 块的顺序：

#include <iostream>

class Base
{
public:
    Base() {}
};

class Derived: public Base
{
public:
    Derived() {}
};

int main()
{
    try
    {
        throw Derived();
    }
    catch (const Derived& derived)
    {
        std::cerr << "caught Derived";
    }
    catch (const Base& base)
    {
        std::cerr << "caught Base";
    }

    return 0;
}

这样，Derived 处理程序将首先有机会捕获 Derived 类型的对象（在 Base 的处理程序之前）。Base 类型的对象不会匹配 Derived 处理程序（Derived 是一种 Base，但 Base 不是一种 Derived），因此会“落入”Base 处理程序。

规则

派生异常类的处理程序应该列在基类的处理程序之前。

使用基类的处理程序捕获派生类型异常的能力被证明是非常有用的。

std::exception

标准库中的许多类和运算符在失败时会抛出异常类。例如，如果 operator new 无法分配足够的内存，它会抛出 std::bad_alloc。失败的 dynamic_cast 会抛出 std::bad_cast。以此类推。截至 C++20，有 28 种不同的异常类可以被抛出，并且每个后续语言标准都会增加更多。

好消息是，所有这些异常类都派生自一个名为 std::exception （定义在 <exception> 头文件中）的类。std::exception 是一个小型接口类，旨在作为 C++ 标准库抛出的任何异常的基类。

很多时候，当标准库抛出异常时，我们并不关心它是 bad allocation、bad cast 还是其他什么。我们只关心发生了某种灾难性的错误，现在程序正在崩溃。多亏了 std::exception，我们可以设置一个异常处理程序来捕获 std::exception 类型的异常，这样我们就能在一个地方捕获 std::exception 及其所有派生异常。简单！

#include <cstddef> // for std::size_t
#include <exception> // for std::exception
#include <iostream>
#include <limits>
#include <string> // for this example

int main()
{
    try
    {
        // 你的使用标准库的代码放在这里
        // 为了示例，我们将故意触发其中一个异常
        std::string s;
        s.resize(std::numeric_limits<std::size_t>::max()); // 将触发 std::length_error 或分配异常
    }
    // 此处理程序将捕获 std::exception 及其所有派生异常
    catch (const std::exception& exception)
    {
        std::cerr << "Standard exception: " << exception.what() << '\n';
    }

    return 0;
}

在作者的机器上，上述程序打印：

Standard exception: string too long

上面的例子应该相当简单。有一点值得注意：std::exception 有一个名为 what() 的虚成员函数，它返回一个 C 风格字符串描述异常。大多数派生类会重写 what() 函数来更改消息。注意，此字符串仅用于描述性文本——不要用它进行比较，因为它不能保证在不同编译器之间相同。

有时我们想以不同的方式处理特定类型的异常。在这种情况下，我们可以为该特定类型添加一个处理程序，并让所有其他异常“落入”基类处理程序。考虑：

try
{
     // 使用标准库的代码放在这里
}
// 此处理程序将在此处捕获 std::length_error（及其派生异常）
catch (const std::length_error& exception)
{
    std::cerr << "You ran out of memory!" << '\n';
}
// 此处理程序将捕获 std::exception（及其派生异常），这些异常会
// 传递到这里
catch (const std::exception& exception)
{
    std::cerr << "Standard exception: " << exception.what() << '\n';
}

在这个例子中，std::length_error 类型的异常将被第一个处理程序捕获并处理。std::exception 类型及其所有其他派生类的异常将被第二个处理程序捕获。

这样的继承层次结构允许我们使用特定的处理程序来定位特定的派生异常类，或者使用基类处理程序来捕获整个异常层次结构。这使我们能够精细控制要处理的异常类型，同时确保我们不必做太多工作来捕获层次结构中的“其他所有异常”。

直接使用标准异常

没有任何东西直接抛出 std::exception，你也不应该这样做。但是，如果标准库中的其他标准异常类能够充分满足你的需求，你可以随意抛出它们。你可以在 cppreference。

std::runtime_error（作为 stdexcept 头文件的一部分）是一个流行的选择，因为它有一个通用的名称，并且它的构造函数接受一个可定制的消息：

#include <exception> // for std::exception
#include <iostream>
#include <stdexcept> // for std::runtime_error

int main()
{
	try
	{
		throw std::runtime_error("Bad things happened");
	}
	// 此处理程序将捕获 std::exception 及其所有派生异常
	catch (const std::exception& exception)
	{
		std::cerr << "Standard exception: " << exception.what() << '\n';
	}

	return 0;
}

这会打印：

Standard exception: Bad things happened

从 std::exception 或 std::runtime_error 派生自己的类

当然，你可以从 std::exception 派生自己的类，并重写虚函数 what() const。下面是相同的程序，其中 ArrayException 派生自 std::exception：

#include <exception> // for std::exception
#include <iostream>
#include <string>
#include <string_view>

class ArrayException : public std::exception
{
private:
	std::string m_error{}; // 处理我们自己的字符串

public:
	ArrayException(std::string_view error)
		: m_error{error}
	{
	}

	// std::exception::what() 返回 const char*，因此我们也必须如此
	const char* what() const noexcept override { return m_error.c_str(); }
};

class IntArray
{
private:
	int m_data[3] {}; // 为简单起见，假设数组长度为 3

public:
	IntArray() {}
	
	int getLength() const { return 3; }

	int& operator[](const int index)
	{
		if (index < 0 || index >= getLength())
			throw ArrayException("Invalid index");

		return m_data[index];
	}

};

int main()
{
	IntArray array;

	try
	{
		int value{ array[5] };
	}
	catch (const ArrayException& exception) // 派生 catch 块放在前面
	{
		std::cerr << "An array exception occurred (" << exception.what() << ")\n";
	}
	catch (const std::exception& exception)
	{
		std::cerr << "Some other std::exception occurred (" << exception.what() << ")\n";
	}
}

注意，虚函数 what() 具有说明符 noexcept（这意味着该函数承诺自身不会抛出异常）。因此，我们的重写也应该具有说明符 noexcept。

由于 std::runtime_error 已经具有字符串处理能力，它也是派生异常类的流行基类。std::runtime_error 可以接受 C 风格字符串参数或 const std::string& 参数之前被修改或销毁的风险。

下面是从 std::runtime_error 派生的相同示例：

#include <exception> // for std::exception
#include <iostream>
#include <stdexcept> // for std::runtime_error
#include <string>

class ArrayException : public std::runtime_error
{
public:
	// std::runtime_error 接受以空字符结尾的 const char* 或 const std::string&。
	// 我们将遵循其做法，接受 const std::string&
	ArrayException(const std::string& error)
		: std::runtime_error{ error } // std::runtime_error 将处理字符串
	{
	}


        // 无需重写 what()，因为我们可以直接使用 std::runtime_error::what()
};

class IntArray
{
private:
	int m_data[3]{}; // 为简单起见，假设数组长度为 3

public:
	IntArray() {}

	int getLength() const { return 3; }

	int& operator[](const int index)
	{
		if (index < 0 || index >= getLength())
			throw ArrayException("Invalid index");

		return m_data[index];
	}

};

int main()
{
	IntArray array;

	try
	{
		int value{ array[5] };
	}
	catch (const ArrayException& exception) // 派生 catch 块放在前面
	{
		std::cerr << "An array exception occurred (" << exception.what() << ")\n";
	}
	catch (const std::exception& exception)
	{
		std::cerr << "Some other std::exception occurred (" << exception.what() << ")\n";
	}
}

由你决定是创建自己的独立异常类、使用标准异常类，还是从 std::exception 或 std::runtime_error 派生自己的异常类。根据你的目标，所有方法都是有效的。

异常的生命周期

当抛出异常时，被抛出的对象通常是分配在栈上的临时变量或局部变量。然而，异常处理过程可能会展开函数，导致函数的所有局部变量被销毁。那么，被抛出的异常对象如何在栈展开中存活下来？

当抛出异常时，编译器会将异常对象复制到为处理异常保留的某些未指定内存（在调用栈之外）中。这样，无论栈被展开多少次，异常对象都会持久存在。异常保证存在直到异常被处理。

这意味着被抛出的对象通常需要是可复制的（即使栈实际上没有被展开）。智能编译器可能能够在特定情况下执行移动操作，或者完全省略复制。

提示

异常对象需要是可复制的。

下面是一个示例，展示了当我们尝试抛出一个不可复制的 Derived 对象时会发生什么：

#include <iostream>

class Base
{
public:
    Base() {}
};

class Derived : public Base
{
public:
    Derived() {}

    Derived(const Derived&) = delete; // 不可复制
};

int main()
{
    Derived d{};

    try
    {
        throw d; // 编译错误：Derived 的复制构造函数已被删除
    }
    catch (const Derived& derived)
    {
        std::cerr << "caught Derived";
    }
    catch (const Base& base)
    {
        std::cerr << "caught Base";
    }

    return 0;
}

当编译此程序时，编译器会抱怨 Derived 复制构造函数不可用，并停止编译。

异常对象不应保留指向栈分配对象的指针或引用。如果抛出的异常导致栈展开（导致栈分配对象被销毁），这些指针或引用可能会悬空。
