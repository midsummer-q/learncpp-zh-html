3.10 — 在问题变成麻烦之前发现它们

● 机器译文 课程 3.10 查看英文原文

当你犯了一个语义错误时，运行程序时可能不会立即注意到该错误。问题可能会在代码中潜伏很长时间，直到新引入的代码或环境的变化导致它表现为程序故障。错误在代码库中存在的时间越长，就越难找到，原本可能容易修复的问题变成了一场耗费时间和精力的调试冒险。

那么我们该怎么办呢？

不要犯错误

嗯，最好的办法是一开始就不犯错误。以下是一些有助于避免犯错的事项：

  • 遵循最佳实践。
  • 不要在疲倦或沮丧时编程。休息一下，稍后再回来。
  • 了解语言中常见的陷阱（所有那些我们警告你不要做的事情）。
  • 不要让函数变得太长。
  • 尽可能优先使用标准库而不是自己编写代码。
  • 大量注释你的代码。
  • 从简单的解决方案开始，然后逐步增加复杂性。
  • 避免使用巧妙/不明显的解决方案。
  • 优先优化可读性和可维护性，而不是性能。

众所周知，调试比一开始编写程序要难两倍。所以如果你在编写代码时极尽巧妙，那你打算如何调试它呢？

重构你的代码

当你向程序添加新功能（“行为变更”）时，你会发现某些函数变得越来越长。随着函数变长，它们变得更复杂，更难理解。

解决这个问题的一种方法是将一个长函数拆分为多个较短的函数。这种在不改变行为的情况下对代码进行结构更改的过程称为 重构。重构的目标是通过增加程序的组织性和模块化来降低其复杂性。

那么一个函数多长才算过长呢？一个占用一屏垂直空间的函数通常被认为过长——如果你需要滚动才能阅读整个函数，函数的可理解性就会显著下降。理想情况下，一个函数应少于十行。少于五行的函数甚至更好。

请记住，这里的目标是最大化可理解性和可维护性，而不是最小化函数长度——放弃最佳实践或使用晦涩的编码技巧来节省一两行代码，对你的代码没有任何好处。

关键提示

在对代码进行更改时，要么进行行为更改，要么进行结构更改，然后重新测试正确性。同时进行行为更改和结构更改往往会导致更多错误，并且错误更难发现。

防御性编程简介

错误不仅可能由你自己造成（例如不正确的逻辑），也可能发生在用户以你未预料到的方式使用应用程序时。例如，如果你要求用户输入一个整数，而他们输入了一个字母，你的程序在这种情况下会如何表现？除非你预料到了这一点，并为这种情况添加了一些错误处理，否则可能表现不佳。

防御性编程 是一种编程实践，程序员试图预见软件可能被误用的所有方式，无论是最终用户还是其他开发者（包括程序员自己）使用代码。这些误用通常可以被检测并缓解（例如，通过要求输入错误输入的用户再试一次）。

我们将在未来的课程中探讨与错误处理相关的话题。

快速发现错误

由于在大型程序中不犯错误很难，次优的选择是快速捕捉到你犯的错误。

做到这一点的最佳方法是每次编写一小段代码，然后测试你的代码，确保它正常工作。

然而，我们还可以使用一些其他技巧。

测试函数简介

帮助发现程序问题的一种常见方法是编写测试函数来“锻炼”你写过的代码。这里有一个原始尝试，更多是出于说明目的：

#include <iostream>

int add(int x, int y)
{
	return x + y;
}

void testadd()
{
	std::cout << "This function should print: 2 0 0 -2\n";
	std::cout << add(1, 1) << ' ';
	std::cout << add(-1, 1) << ' ';
	std::cout << add(1, -1) << ' ';
	std::cout << add(-1, -1) << ' ';
}

int main()
{
	testadd();

	return 0;
}

testadd() 函数通过使用不同的值调用 add() 函数来测试 add() 函数。如果所有值都符合我们的期望，那么我们可以合理地确信该函数正常工作。更好的是，我们可以保留这个函数，并在任何时候更改函数时运行它， add 以确保我们没有意外地破坏它。

这是一种原始形式的 单元测试，这是一种软件测试方法，通过测试源代码的小单元来确定它们是否正确。

与日志框架一样，有许多第三方单元测试框架可以使用。也可以自己编写，尽管我们需要掌握更多的语言特性才能充分讨论这个主题。我们将在未来的课程中再次涉及其中的一些内容。

约束简介

基于约束的技术涉及添加一些额外的代码（如果希望，可以在非调试构建中编译掉这些代码），以检查某些假设或预期是否未被违反。

例如，如果我们要编写一个计算数字阶乘的函数，该函数期望非负参数，那么函数可以在继续之前检查调用者是否传入了非负数。如果调用者传入了负数，那么函数可以立即报错，而不是产生某种不确定的结果，从而帮助确保问题被立即捕获。

一种常见的方法是通过 assert 和 静态断言，我们在课程 9.6 -- Assert 和 static_assert。

对一般问题进行散弹式检查

程序员倾向于犯某些常见错误，其中一些错误可以通过专门寻找这些错误的程序来发现。这些程序通常被称为 静态分析工具 （有时非正式地称为 检查器）是分析你的源代码以识别特定语义问题的程序（在此上下文中， 静态 意味着这些工具在不执行代码的情况下分析源代码）。静态分析工具发现的问题可能是也可能不是你遇到的任何特定问题的原因，但可能有助于指出代码的脆弱区域或在某些情况下可能成为问题的要点。

你已经拥有一个静态分析工具——你的编译器！除了确保你的程序在语法上正确外，大多数现代C++编译器还会进行一些轻量级的静态分析来识别一些常见问题。例如，许多编译器会在你试图使用未初始化的变量时发出警告。如果你还没有这样做，提高编译器的警告和错误级别（参见课程 0.11 -- 配置编译器：警告和错误级别）有助于暴露这些问题。

存在许多静态分析工具，其中一些可以识别超过300种编程错误。在我们的小型学术程序中，使用静态分析工具是可选的，但使用一个可以帮助你发现代码不符合最佳实践的地方。在大型程序中，强烈建议使用静态分析工具，因为它可以揭示数十或数百个潜在问题。

最佳实践

在你的程序上使用静态分析工具，以帮助找到代码不符合最佳实践的地方。

适用于 Visual Studio 用户

Visual Studio 2019 及更高版本内置了静态分析工具。你可以通过以下方式访问它： 生成 > 对解决方案运行代码分析 (Alt+F11)。

提示

一些常用的静态分析工具包括：

免费：

  • clang-tidy
  • cpplint
  • cppcheck （已集成到 Code::Blocks 中）
  • SonarLint

其中大多数都有扩展，可以集成到你的 IDE 中。例如， Clang Power Tools 扩展。

付费（开源项目可能免费）：

  • Coverity
  • SonarQube
