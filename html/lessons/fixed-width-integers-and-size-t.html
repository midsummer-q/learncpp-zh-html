4.6 — 固定宽度整数和 size_t

● 机器译文 课程 4.6 查看英文原文

在之前关于整数的课程中，我们提到 C++ 只保证整数变量有一个最小尺寸——但它们可能更大，取决于目标系统。

例如，一个 int 的最小尺寸是 16 位，但在现代架构上通常是 32 位。

如果你假设 int 是 32 位（因为这是最常见的情况），那么你的程序在 int 实际上是 16 位的架构上可能会表现异常（因为你可能会将需要 32 位存储的值存入只有 16 位存储的变量中，从而导致溢出或未定义行为）。

例如：

#include <iostream>

int main()
{
    int x { 32767 };        // x 可能是 16 位或 32 位
    x = x + 1;              // 如果 int 是 16 位，32768 溢出；如果 int 是 32 位，则正常
    std::cout << x << '\n'; // 这将打印什么？

    return 0;
}

在 int 是 32 位的机器上，值 32768 在 int的范围内，因此可以安全地存入 x 中。在这类机器上，程序将打印 32768。然而，在 int 是 16 位的机器上，值 32768 不在 16 位整数（范围 -32,768 到 32,767）的范围内。在这类机器上， x = x + 1 将导致溢出，值 -32768 会被存入 x 然后打印出来。

相反，如果你假设 int 只有 16 位，以确保你的程序在所有架构上都能正常运行，那么你可以安全存储在一个 int 受到显著限制。而在那些 int 实际上是32位的，你就没有充分利用每个...分配的一半内存 int。

关键提示

在大多数情况下，我们只实例化少量 int 变量，它们通常在其创建的函数结束时被销毁。在这种情况下，每个变量浪费2字节内存并不值得担忧（有限范围才是更大的问题）。然而，当程序分配数百万个 int 变量时，每个变量浪费2字节内存会对程序整体内存使用产生显著影响。

为什么整数类型的大小不是固定的？

简短答案是这要追溯到C语言的早期，当时计算机速度慢，性能是最重要的关注点。C特意将整数的大小留空，以便编译器实现者可以为 int 使其在目标计算机架构上性能最佳。这样，程序员可以直接使用 int 而无需担心是否可以使用性能更高的类型。

按现代标准，各种整数类型缺乏一致的范围很糟糕（尤其在一个旨在可移植的语言中）。

固定宽度整数

为了解决上述问题，C++11提供了一组备选整数类型，保证在任何架构上大小相同。因为这些整数的大小是固定的，它们被称为 固定宽度整数。

固定宽度整数在<cstdint>\ header中定义如下：

名称固定大小固定范围备注
std::int8_t1字节有符号-128 到 127在许多系统上被视为有符号字符。见下面的注释。
std::uint8_t1字节无符号0 到 255在许多系统上被视为unsigned char。参见下面的注释。
std::int16_t2字节有符号-32,768 到 32,767
std::uint16_t2字节无符号0 到 65,535
std::int32_t4字节有符号-2,147,483,648 到 2,147,483,647
std::uint32_t4字节无符号0 到 4,294,967,295
std::int64_t8字节有符号-9,223,372,036,854,775,808 到 9,223,372,036,854,775,807
std::uint64_t8字节无符号0 到 18,446,744,073,709,551,615

下面是一个示例：

#include <cstdint> // for fixed-width integers
#include <iostream>

int main()
{
    std::int32_t x { 32767 }; // x 始终是 32 位整数
    x = x + 1;                // 所以32768始终能容纳
    std::cout << x << '\n';

    return 0;
}

最佳实践

当需要一个具有保证范围的整数类型时，请使用固定宽度整数类型。

警告： std::int8_t 和 std::uint8_t 通常行为类似于char

由于C++规范中的一个疏忽，现代编译器通常将 std::int8_t 和 std::uint8_t （以及相应的fast和least固定宽度类型，我们稍后会介绍）视为与 signed char 和 unsigned char 因此，在大多数现代系统上，8位固定宽度整数类型的行为类似于char类型。

快速预览：

#include <cstdint> // for fixed-width integers
#include <iostream>

int main()
{
    std::int8_t x { 65 };   // 用值65初始化8位整型
    std::cout << x << '\n'; // 你可能期望这会打印65

    return 0;
}

虽然你可能期望上述程序打印 65，但它很可能不会。

我们将在课程4.12中讨论这个例子实际上打印什么（以及如何确保它总是打印 65） 4.12 -- 类型转换与static_cast简介，在我们于课程中介绍char（以及它们如何打印）之后 4.11 -- 字符。

警告

8位固定宽度整数类型通常被视为char而非整数值（这因系统而异）。16位及更宽的整数类型则不受此问题影响。

进阶读者

固定宽度整数实际上并未定义新类型——它们只是对具有所需大小的现有整数类型的别名。对于每个固定宽度类型，实现（编译器和标准库）可以决定别名哪个现有类型。例如，在一个平台上，如果 int 是32位的， std::int32_t 将成为 int的别名。在一个系统上，如果 int 是16位的（且 long 是32位的）， std::int32_t 将成为 long 的别名。

那么8位固定宽度类型呢？

在大多数情况下， std::int8_t 是 signed char 的别名，因为它是唯一可用的8位有符号整数类型（bool 和 char 不被视为有符号整型）。在这种情况下， std::int8_t 将表现得像该平台上的 char 一样。

然而，在极少数情况下，如果某个平台具有实现特定的 8 位有符号整型，那么实现可能会决定将 std::int8_t 作为该类型的别名。在这种情况下， std::int8_t 将表现得像该类型，可能更像 int 而非 char。

std::uint8_t 行为类似。

其他固定宽度整型的缺点

固定宽度整型有一些潜在的缺点：

首先，固定宽度整型并不保证在所有架构上都有定义。它们仅存在于那些具有匹配其宽度且遵循特定二进制表示的基本整型的系统上。如果你的程序使用了某个固定宽度整型，而某个架构不支持它，那么程序将在该架构上编译失败。然而，鉴于现代架构已经标准化为 8/16/32/64 位变量，除非你的程序需要移植到某些奇特的大型机或嵌入式架构，否则这不太可能成为问题。

其次，如果你使用固定宽度整型，在某些架构上它可能比更宽的类型慢。例如，如果你需要一个保证为 32 位的整数，你可能会决定使用 std::int32_t，但你的 CPU 实际上可能处理 64 位整数更快。然而，仅仅因为你的 CPU 能更快地处理某个类型，并不意味着你的程序整体会更快——现代程序通常受内存使用限制而非 CPU，更大的内存占用可能减缓你的程序，其程度超过更快 CPU 处理带来的加速。如果不实际测量，很难知道。

不过这些只是小问题。

快速和最简整型 可选

为帮助解决上述缺点，C++ 还定义了两组保证存在的替代整型。

快速类型（std::int_fast#_t 和 std::uint_fast#_t）提供宽度至少为 # 位（其中 # = 8、16、32 或 64）的最快有符号/无符号整型。例如， std::int_fast32_t 会给你一个至少 32 位的最快有符号整型。所谓最快，是指 CPU 能最快处理的整型。

最简类型（std::int_least#_t 和 std::uint_least#_t）提供宽度至少为 # 位（其中 # = 8、16、32 或 64）的最小有符号/无符号整型。例如， std::uint_least32_t 会给你一个至少 32 位的最小无符号整型。

以下来自作者的 Visual Studio（32位控制台应用程序）示例：

#include <cstdint> // for fast and least types
#include <iostream>

int main()
{
	std::cout << "least 8:  " << sizeof(std::int_least8_t)  * 8 << " bits\n";
	std::cout << "least 16: " << sizeof(std::int_least16_t) * 8 << " bits\n";
	std::cout << "least 32: " << sizeof(std::int_least32_t) * 8 << " bits\n";
	std::cout << '\n';
	std::cout << "fast 8:  "  << sizeof(std::int_fast8_t)   * 8 << " bits\n";
	std::cout << "fast 16: "  << sizeof(std::int_fast16_t)  * 8 << " bits\n";
	std::cout << "fast 32: "  << sizeof(std::int_fast32_t)  * 8 << " bits\n";

	return 0;
}

这产生了结果：

least 8:  8 bits
least 16: 16 bits
least 32: 32 bits

fast 8:  8 bits
fast 16: 32 bits
fast 32: 32 bits

你可以看到 std::int_least16_t 是16位的，而 std::int_fast16_t 实际上是32位的。这是因为在作者的机器上，32位整数的处理速度比16位整数快。

再举一个例子，假设我们使用的架构仅有16位和64位整数类型。 std::int32_t 不存在，而 std::least_int32_t （以及 std::fast_int32_t会是64位。

然而，这些快速和最小整数也有自身的缺点。首先，实际使用它们的程序员不多，缺乏熟悉度会导致错误。其次，快速类型还可能造成内存浪费，因为它们的实际大小可能比名称所显示的大得多。

最严重的是，由于快速/最小整数的大小由实现定义，你的程序在解析为不同大小的架构上可能表现出不同的行为。例如：

#include <cstdint>
#include <iostream>

int main()
{
    std::uint_fast16_t sometype { 0 };
    sometype = sometype - 1; // 故意溢出以触发回绕行为

    std::cout << sometype << '\n';

    return 0;
}

这段代码会根据 std::uint_fast16_t 是16位、32位还是64位而得到不同的结果！这恰恰是我们最初使用固定宽度整数试图避免的情况！

最佳实践

应避免使用快速和最小整数类型，因为它们在不同架构上可能解析为不同大小，从而表现出不同的行为。

整数类型的最佳实践

鉴于基本整数类型、固定宽度整数类型、快速/最小整数类型以及有符号/无符号挑战的各种利弊，关于整数的最佳实践很少有共识。

我们的立场是：正确比快速更重要，编译时失败比运行时失败更好。因此，如果你需要一个具有保证范围的整数类型，我们建议避免使用快速/最小类型，而采用固定宽度类型。如果日后你发现需要支持某个奇特的平台，而该平台上某个特定的固定宽度整数类型无法编译，届时你可以决定如何迁移程序（并全面重新测试）。

最佳实践

  • 优先使用 int 当整数的大小无关紧要时（例如，数字始终能适配2字节有符号整数的范围）。例如，如果你询问用户的年龄，或者从1数到10，那么 int 是16位还是32位并不重要（数字无论哪种情况都能适配）。这将覆盖你可能遇到的大多数情况。
  • 优先使用 std::int#_t 当存储需要保证范围的量时。
  • 优先使用 std::uint#_t 当进行位操作或需要明确定义的环绕行为时（例如用于加密或随机数生成）。

尽可能避免以下情况：

  • short 和 long 整数（优先使用固定宽度整数类型）。
  • 最快和最小整数类型（优先使用固定宽度整数类型）。
  • 用于表示数量的无符号类型（优先使用有符号整数类型）。
  • 8位固定宽度整数类型（优先使用16位固定宽度整数类型）。
  • 任何编译器特定的固定宽度整数（例如，Visual Studio定义了__int8、__int16等……）

什么是std::size_t？

考虑以下代码：

#include <iostream>

int main()
{
    std::cout << sizeof(int) << '\n';

    return 0;
}

在作者的机器上，这会打印：

4

很简单，对吧？我们可以推断出 operator sizeof 返回一个整数值——但该返回值是什么整数类型？是int？是short？答案是 sizeof 返回一个类型为 std::size_t。 std::size_t 是实现在定义的的无符号整数类型的别名。换句话说，编译器决定是 std::size_t 无符号int、无符号long、无符号long long等……

关键提示

std::size_t 是实现在定义的的无符号整数类型的别名。它在标准库中用于表示对象的字节大小或长度。

进阶读者

std::size_t 实际上是一个typedef。我们在第 10.7课——Typedefs和类型别名。

std::size_t 在多个不同的头文件中定义。如果你需要使用 std::size_t，<cstddef>是包含的最佳头文件，因为它包含的其他已定义标识符最少。

例如：

#include <cstddef>  // for std::size_t
#include <iostream>

int main()
{
    int x { 5 };
    std::size_t s { sizeof(x) }; // sizeof返回std::size_t类型的值，因此s的类型应该为std::size_t
    std::cout << s << '\n';

    return 0;
}

最佳实践

如果你使用 std::size_t 显式地在你代码中使用，请#include一个定义了的头文件 std::size_t （我们推荐 <cstddef>）。

使用 sizeof 不需要头文件（尽管它返回一个值的类型是 std::size_t)。

就像整数的大小可能因系统而异， std::size_t 大小也会不同。 std::size_t 保证是无符号且至少为16位，但在大多数系统上，它等于应用程序的地址宽度。也就是说，对于32位应用程序， std::size_t 通常是一个32位无符号整数，而对于64位应用程序， std::size_t 通常是一个64位无符号整数。

浮点类型的 sizeof 运算符返回一个类型为 std::size_t 可选

作者注

以下部分为选读内容。理解后续内容并不关键。

有趣的是，我们可以使用 sizeof 运算符（它返回一个类型为 std::size_t) 来询问 std::size_t 它自身的大小：

#include <cstddef> // for std::size_t
#include <iostream>

int main()
{
	std::cout << sizeof(std::size_t) << '\n';

	return 0;
}

在作者的系统上编译为32位（4字节）控制台应用程序时，这会输出：

4

std::size_t 对对象的大小施加了一个上限 可选

浮点类型的 sizeof 运算符必须能够以类型为 std::size_t。因此，对象的字节大小不能大于 std::size_t 所能容纳的最大值。

浮点类型的 C++20 标准 （[basic.compound] 1.8.2）指出：“构建一个类型，其对象表示中的字节数超过了类型 std::size_t (17.2) 所能表示的最大值，是病式的。”

如果可以创建一个更大的对象， sizeof 将无法返回其字节大小，因为它超出了 std::size_t 所能容纳的范围。因此，创建一个大小（以字节为单位）超过类型为 std::size_t 所能容纳的最大值的对象是无效的（并且会导致编译错误）。

例如，假设 std::size_t 在我们的系统中大小为 4 字节。无符号 4 字节整数类型的范围是 0 到 4,294,967,295。因此，一个 4 字节的 std::size_t 对象可以保存 0 到 4,294,967,295 之间的任何值。任何字节大小在 0 到 4,294,967,295 之间的对象都可以将其大小以类型为 std::size_t的值返回，因此没有问题。但是，如果对象的字节大小超过 4,294,967,295 字节， sizeof 将无法准确返回该对象的大小，因为该值超出了 std::size_t的范围。因此，在此系统上无法创建超过 4,294,967,295 字节的对象。

顺便说一句……

的大小 std::size_t 对对象的大小施加了严格的数学上限。实际上，可创建的最大对象可能小于此值（可能显著小于）。

一些编译器将可创建的最大对象限制为 std::size_t （这个解释可以在 这里)。

其他因素也可能起作用，例如计算机有多少连续内存可用于分配。

当 8 位和 16 位应用程序成为常态时，这个限制对对象的大小造成了重大约束。在 32 位和 64 位时代，这很少成为问题，因此通常不需要担心。
