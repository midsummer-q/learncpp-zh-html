2.12 — 头文件守卫

● 机器译文 课程 2.12 查看英文原文

重复定义问题

在课程 2.7 -- 前向声明和定义，我们注意到变量或函数标识符只能有一个定义（单一定义规则）。因此，如果一个程序多次定义了一个变量标识符，将会导致编译错误：

int main()
{
    int x; // 这是变量x的定义
    int x; // 编译错误：重复定义

    return 0;
}

类似地，多次定义函数的程序也会导致编译错误：

#include <iostream>

int foo() // 这是函数foo的定义
{
    return 5;
}

int foo() // 编译错误：重复定义
{
    return 5;
}

int main()
{
    std::cout << foo();
    return 0;
}

虽然这些程序很容易修复（删除重复定义），但在头文件中，很容易出现头文件中的定义被多次包含的情况。这种情况可能发生在头文件 #includes 另一个头文件时（这很常见）。

作者注

在接下来的示例中，我们将在头文件中定义一些函数。通常你不应该这样做。

我们在这里这样做，因为这是使用我们已经介绍过的功能来展示某些概念的最有效方式。

考虑以下学术示例：

square.h：

int getSquareSides()
{
    return 4;
}

wave.h：

#include "square.h"

main.cpp:

#include "square.h"
#include "wave.h"

int main()
{
    return 0;
}

这个看似无害的程序无法编译！下面是发生的情况。首先， main.cpp #includes square.h，它会复制函数 getSquareSides 到 main.cpp。然后 main.cpp #includes wave.h，它 #includes square.h 自身。这会将内容复制到 square.h （包括函数 getSquareSides）到 wave.h，然后被复制到 main.cpp。

因此，在解析所有 #include 之后， main.cpp 最终看起来像这样：

int getSquareSides()  // 来自square.h
{
    return 4;
}

int getSquareSides() // 来自wave.h（通过square.h）
{
    return 4;
}

int main()
{
    return 0;
}

重复定义和编译错误。每个文件单独来看都没有问题。然而，因为 main.cpp 最终 #include 了 square.h 两次，我们就遇到了问题。如果 wave.h 需要 getSquareSides()、和 main.cpp 都需要 wave.h 和 square.h，你将如何解决这个问题？

头文件卫士

好消息是，我们可以通过一种称为 头文件守卫 （也称为一个 头文件保护）。头文件保护是条件编译指令，其形式如下：

#ifndef SOME_UNIQUE_NAME_HERE
#define SOME_UNIQUE_NAME_HERE

// 此处放置你的声明（以及某些类型的定义）

#endif

当这个头文件被 #include 时，预处理器将检查 SOME_UNIQUE_NAME_HERE 是否之前已在这个翻译单元中定义过。如果这是我们第一次包含这个头文件， SOME_UNIQUE_NAME_HERE 还没有被定义过。因此，它 #define SOME_UNIQUE_NAME_HERE 并包含该文件的内容。如果同一个文件中再次包含此头文件， SOME_UNIQUE_NAME_HERE 那么头文件的内容在第一次包含时就已经被定义了，因此后续的内容会被忽略（得益于 #ifndef 指令）。

你的所有头文件都应该带有头文件保护机制。 SOME_UNIQUE_NAME_HERE 可以是任意你想要的名称，但按照惯例会设置为头文件的完整文件名，全部大写，用下划线代替空格或标点符号。例如， square.h 其头文件保护宏为：

square.h：

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides()
{
    return 4;
}

#endif

即使是标准库头文件也使用头文件保护。如果你查看 Visual Studio 中的 iostream 头文件，你会看到：

#ifndef _IOSTREAM_
#define _IOSTREAM_

// 此处填写内容

#endif

进阶读者

在大型程序中，可能存在两个不同的头文件（来自不同目录）最终具有相同的文件名（例如 directoryA\config.h 和 directoryB\config.h）。如果仅使用文件名作为包含保护宏（例如 CONFIG_H），那么这两个文件可能会使用相同的保护宏名称。如果发生这种情况，任何直接或间接同时包含这两个 config.h 文件的文件，将无法获得第二个包含文件的内容。这很可能会导致编译错误。

由于存在这种保护宏名称冲突的可能性，许多开发者建议在头文件保护中使用更复杂/唯一的名称。一些好的建议是采用 PROJECT_PATH_FILE_H、FILE_LARGE-RANDOM-NUMBER_H 或 FILE_CREATION-DATE_H 的命名约定。

使用头文件保护更新先前的示例

让我们回到 square.h 示例，使用 square.h 并加入头文件保护。为了规范起见，我们也将头文件保护添加到 wave.h。

square.h

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides()
{
    return 4;
}

#endif

wave.h：

#ifndef WAVE_H
#define WAVE_H

#include "square.h"

#endif

main.cpp:

#include "square.h"
#include "wave.h"

int main()
{
    return 0;
}

在预处理器解析完所有 #include 指令后，该程序看起来像这样：

main.cpp:

// Square.h 从 main.cpp 中被包含
#ifndef SQUARE_H // square.h 从 main.cpp 中被包含
#define SQUARE_H // SQUARE_H在此处被定义

// 并且所有这些内容被包含
int getSquareSides()
{
    return 4;
}

#endif // SQUARE_H

#ifndef WAVE_H // wave.h 从 main.cpp 中被包含
#define WAVE_H
#ifndef SQUARE_H // square.h 从 wave.h 中被包含，SQUARE_H 已经在上方被定义了
#define SQUARE_H // 所以这些内容都不会被包含

int getSquareSides()
{
    return 4;
}

#endif // SQUARE_H
#endif // WAVE_H

int main()
{
    return 0;
}

让我们看看它是如何执行的。

首先，预处理器评估 #ifndef SQUARE_H。 SQUARE_H 尚未被定义，因此从 #ifndef 到后续的 #endif 之间的代码被包含进行编译。这段代码定义了 SQUARE_H，并持有 getSquareSides 函数的顶部开始。

之后，下一个 #ifndef SQUARE_H 被求值。这次， SQUARE_H 已定义（因为它在上面被定义了），所以来自 #ifndef 到后续的 #endif 的代码被排除在编译之外。

头文件保护符能防止重复包含，因为当第一次遇到保护符时，保护宏尚未定义，因此被保护的内容会被包含。此后，保护宏已被定义，所以任何后续被保护内容的副本都会被排除。

头文件保护符不会阻止一个头文件被包含一次到不同的代码文件中

注意，头文件保护符的目标是防止一个代码文件收到超过一份被保护的头文件副本。按照设计，头文件保护符确实 不是 阻止一个给定的头文件被包含（一次）到不同的代码文件中。这也可能引起意外问题。考虑：

square.h：

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides()
{
    return 4;
}

int getSquarePerimeter(int sideLength); // getSquarePerimeter 的前向声明

#endif

square.cpp：

#include "square.h"  // square.h is included once here

int getSquarePerimeter(int sideLength)
{
    return sideLength * getSquareSides();
}

main.cpp:

#include "square.h" // square.h is also included once here
#include <iostream>

int main()
{
    std::cout << "a square has " << getSquareSides() << " sides\n";
    std::cout << "a square of length 5 has perimeter length " << getSquarePerimeter(5) << '\n';

    return 0;
}

注意 square.h 同时从 main.cpp 和 square.cpp中被包含。这意味着 square.h 的内容将被包含一次到 square.cpp 以及一次到 main.cpp。

让我们更详细地检查为什么会发生这种情况。当 square.h 从 square.cpp， SQUARE_H 被定义直到 square.cpp结束。这个宏定义防止了 square.h 被第二次包含进 square.cpp （这正是头文件保护符的作用）。然而，一旦 square.cpp 已完成， SQUARE_H 不再被视为已定义。这意味着当预处理器运行于 main.cpp， SQUARE_H 最初未定义于 main.cpp。

最终结果是，两个 square.cpp 和 main.cpp 都获得了定义的一份副本 getSquareSides。这个程序可以编译，但链接器会抱怨你的程序对标识符有多重定义 getSquareSides！

解决这个问题的最佳方法很简单：将函数定义放在一个 .cpp 文件中，这样头文件只包含前向声明：

square.h：

#ifndef SQUARE_H
#define SQUARE_H

int getSquareSides(); // getSquareSides 的前向声明
int getSquarePerimeter(int sideLength); // getSquarePerimeter 的前向声明

#endif

square.cpp：

#include "square.h"

int getSquareSides() // getSquareSides 的实际定义
{
    return 4;
}

int getSquarePerimeter(int sideLength)
{
    return sideLength * getSquareSides();
}

main.cpp:

#include "square.h" // square.h is also included once here
#include <iostream>

int main()
{
    std::cout << "a square has " << getSquareSides() << " sides\n";
    std::cout << "a square of length 5 has perimeter length " << getSquarePerimeter(5) << '\n';

    return 0;
}

现在当程序编译时，函数 getSquareSides 只会有一个定义（通过 square.cpp），所以链接器满意。文件 main.cpp 能够调用这个函数（尽管它位于 square.cpp）因为它包含了 square.h，其中包含了该函数的前向声明（链接器会将调用连接到 getSquareSides 从 main.cpp 到定义 getSquareSides 在 square.cpp)。

难道我们不能完全避免在头文件中定义吗？

我们通常告诉您不要在头文件中包含函数定义。所以您可能会想，如果头文件保护宏保护的是您本就不该做的事，那为什么还要使用它们呢？

未来我们会向你展示不少情况下需要将非函数定义放在头文件中。例如，C++ 允许你创建自己的类型。这些自定义类型通常定义在头文件中，这样类型定义就能传播到需要使用它们的代码文件中。如果没有头文件保护宏，一个代码文件最终可能会包含同一类型定义的多个（相同）副本，编译器会将其视为错误。

因此，尽管在本教程系列的这个阶段并不严格要求使用头文件保护宏，但我们正在养成好习惯，这样你以后就不必改掉坏习惯了。

#pragma once

现代编译器支持一种更简单的头文件保护宏替代形式，使用 #pragma 预处理指令：

#pragma once

// 在此处添加你的代码

#pragma once 与头文件保护符作用相同：避免头文件被多次包含。使用传统头文件保护符时，开发者负责保护头文件（通过使用预处理指令 #ifndef， #define、和 #endif）。使用 #pragma once，我们请求编译器保护头文件。具体如何实现是实现特定的细节。

进阶读者

有一个已知情况，其中 #pragma once 通常会失败。如果头文件被复制到文件系统的多个位置，如果两个副本都被包含，头文件保护符能成功去重相同的头文件，但 #pragma once 不会（因为编译器不会意识到它们实际上是相同的内容）。

对于大多数项目， #pragma once 工作得很好，许多开发者现在更倾向于它，因为它更简单且不易出错。许多IDE还会自动包含 #pragma once 在通过IDE生成的新头文件的顶部。

警告

浮点类型的 #pragma 指令是为编译器实现者设计的，供他们用于任何目的。因此，支持哪些pragma以及这些pragma的含义完全取决于实现。除了 #pragma once，不要期望在一个编译器上能用的pragma在另一个编译器上也支持。

因为 #pragma once 未由C++标准定义，所以某些编译器可能不支持它。因此，一些开发机构（如Google）建议使用传统头文件保护符。在本教程系列中，我们将优先使用头文件保护符，因为这是保护头文件最传统的方式。然而，对 #pragma once 的支持目前已经相当普遍，如果你想使用 #pragma once 代替，这在现代C++中通常是可以接受的。

总结

头文件保护符旨在确保给定头文件的内容不会在单个文件中被复制多次，以防止重复定义。

重复 声明 是没问题的——但即使你的头文件全部由声明组成（没有定义），包含头文件保护符仍然是最佳实践。

注意，头文件守卫确实 不是 防止头文件的内容（被一次）复制到不同的项目文件中。这是一件好事，因为我们经常需要从不同的项目文件中引用给定头文件的内容。
