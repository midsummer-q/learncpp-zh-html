22.1 — 智能指针与移动语义简介

● 机器译文 课程 22.1 查看英文原文

考虑一个函数，我们在其中动态分配一个值：

void someFunction()
{
    Resource* ptr = new Resource(); // Resource 是一个结构体或类

    // 在这里对 ptr 进行操作

    delete ptr;
}

虽然上面的代码看起来相当直接，但很容易忘记释放 ptr。即使你记得在函数末尾删除 ptr，如果函数提前退出，也有无数种方式导致 ptr 未被删除。这可以通过提前返回发生：

#include <iostream>

void someFunction()
{
    Resource* ptr = new Resource();

    int x;
    std::cout << "Enter an integer: ";
    std::cin >> x;

    if (x == 0)
        return; // 函数提前返回，ptr 不会被删除！

    // 在这里对 ptr 进行操作

    delete ptr;
}

或者通过抛出异常：

#include <iostream>

void someFunction()
{
    Resource* ptr = new Resource();

    int x;
    std::cout << "Enter an integer: ";
    std::cin >> x;

    if (x == 0)
        throw 0; // 函数提前返回，ptr 不会被删除！

    // 在这里对 ptr 进行操作

    delete ptr;
}

在上述两个程序中，提前返回或 throw 语句执行，导致函数终止而变量 ptr 未被删除。因此，为变量 ptr 分配的内存现在泄漏了（并且每次调用此函数并提前返回时都会再次泄漏）。

本质上，这类问题的出现是因为指针变量没有内在的机制来自行清理。

智能指针类来拯救？

类最好的特性之一是它们包含析构函数，当类对象离开作用域时会自动执行。因此，如果你在构造函数中分配（或获取）内存，你可以在析构函数中释放它，并保证当类对象被销毁时内存会被释放（无论它是离开作用域、被显式删除等）。这是我们在课程中讨论的 RAII 编程范式的核心。 ，增加了移动构造函数和移动赋值运算符。。

那么我们可以使用一个类来帮助我们管理和清理指针吗？我们可以！

考虑一个类，其唯一的工作是持有并“拥有”一个传递给它的指针，然后当类对象离开作用域时释放该指针。只要该类的对象仅作为局部变量创建，我们就可以保证该类会正确离开作用域（无论我们的函数何时或如何终止），并且拥有的指针会被销毁。

以下是这个想法的初稿：

#include <iostream>

template <typename T>
class Auto_ptr1
{
	T* m_ptr {};
public:
	// 通过构造函数传入一个指针来“拥有”它
	Auto_ptr1(T* ptr=nullptr)
		:m_ptr(ptr)
	{
	}
	
	// 析构函数将确保它被释放
	~Auto_ptr1()
	{
		delete m_ptr;
	}

	// 重载解引用和 operator->，以便我们可以像使用 m_ptr 一样使用 Auto_ptr1。
	T& operator*() const { return *m_ptr; }
	T* operator->() const { return m_ptr; }
};

// 一个示例类，用于证明上述代码有效
class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
	Auto_ptr1<Resource> res(new Resource()); // 注意这里的内存分配

        // ... 但不需要显式 delete

	// 还要注意我们使用 <Resource>，而不是 <Resource*>
        // 这是因为我们将 m_ptr 定义为类型 T*（而不是 T）

	return 0;
} // res 在这里超出作用域，并为我们销毁了分配的 Resource

该程序打印出：

Resource acquired
Resource destroyed

考虑这个程序和类是如何工作的。首先，我们动态创建一个 Resource，并将其作为参数传递给我们的模板类 Auto_ptr1。从那时起，我们的 Auto_ptr1 变量 res 拥有该 Resource 对象（Auto_ptr1 与 m_ptr 具有组合关系）。由于 res 被声明为局部变量并具有块作用域，它将在块结束时离开作用域并被销毁（不用担心忘记释放它）。而且因为它是一个类，当它被销毁时，Auto_ptr1 的析构函数将被调用。该析构函数将确保它持有的 Resource 指针被删除！

只要 Auto_ptr1 被定义为局部变量（具有自动存储期，因此类名中有“Auto”），Resource 将保证在其声明的块结束时被销毁，无论函数如何终止（即使提前终止）。

这样的类称为智能指针。 智能指针 是一个组合类，旨在管理动态分配的内存，并确保当智能指针对象离开作用域时内存被删除。（相关地，内置指针有时被称为“哑指针”，因为它们无法自行清理）。

现在让我们回到上面的 someFunction() 示例，并展示智能指针类如何解决我们的挑战：

#include <iostream>

template <typename T>
class Auto_ptr1
{
	T* m_ptr {};
public:
	// 通过构造函数传入一个指针来“拥有”它
	Auto_ptr1(T* ptr=nullptr)
		:m_ptr(ptr)
	{
	}
	
	// 析构函数将确保它被释放
	~Auto_ptr1()
	{
		delete m_ptr;
	}

	// 重载解引用和 operator->，以便我们可以像使用 m_ptr 一样使用 Auto_ptr1。
	T& operator*() const { return *m_ptr; }
	T* operator->() const { return m_ptr; }
};

// 一个示例类，用于证明上述代码有效
class Resource
{
public:
    Resource() { std::cout << "Resource acquired\n"; }
    ~Resource() { std::cout << "Resource destroyed\n"; }
    void sayHi() { std::cout << "Hi!\n"; }
};

void someFunction()
{
    Auto_ptr1<Resource> ptr(new Resource()); // ptr 现在拥有 Resource
 
    int x;
    std::cout << "Enter an integer: ";
    std::cin >> x;
 
    if (x == 0)
        return; // 函数提前返回
 
    // 在这里对 ptr 进行操作
    ptr->sayHi();
}

int main()
{
    someFunction();

    return 0;
}

如果用户输入非零整数，上述程序将打印：

Resource acquired
Hi!
Resource destroyed

如果用户输入零，上述程序将提前终止，打印：

Resource acquired
Resource destroyed

注意，即使在用户输入零且函数提前终止的情况下，Resource 仍然被正确释放。

因为 ptr 变量是局部变量，当函数终止时（无论以何种方式终止），ptr 将被销毁。并且由于 Auto_ptr1 的析构函数会清理 Resource，我们确信 Resource 会被正确清理。

一个关键缺陷

Auto_ptr1 类有一个隐藏在自动生成的代码中的关键缺陷。在继续阅读之前，看看你是否能找出它。我们等着……

（提示：考虑如果你不提供它们，类的哪些部分会被自动生成）

（危险边缘音乐）

好了，时间到。

与其告诉你，不如展示给你看。考虑以下程序：

#include <iostream>

// 与上面相同
template <typename T>
class Auto_ptr1
{
	T* m_ptr {};
public:
	Auto_ptr1(T* ptr=nullptr)
		:m_ptr(ptr)
	{
	}
	
	~Auto_ptr1()
	{
		delete m_ptr;
	}

	T& operator*() const { return *m_ptr; }
	T* operator->() const { return m_ptr; }
};

class Resource
{
public:
	Resource() { std::cout << "Resource acquired\n"; }
	~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
	Auto_ptr1<Resource> res1(new Resource());
	Auto_ptr1<Resource> res2(res1); // 或者，不初始化 res2，然后赋值 res2 = res1;

	return 0;
} // res1 和 res2 在这里超出作用域

该程序打印出：

Resource acquired
Resource destroyed
Resource destroyed

很可能（但不一定）你的程序会在此时崩溃。现在看到问题了吗？因为我们没有提供拷贝构造函数或赋值运算符，C++ 为我们提供了一个。而它提供的函数执行浅拷贝。所以当我们用 res1 初始化 res2 时，两个 Auto_ptr1 变量都指向同一个 Resource。当 res2 离开作用域时，它删除了资源，使 res1 留下一个悬空指针。当 res1 试图删除其（已被删除的）Resource 时，会导致未定义行为（可能是崩溃）！

你会在像这样的函数中遇到类似的问题：

void passByValue(Auto_ptr1<Resource> res)
{
}

int main()
{
	Auto_ptr1<Resource> res1(new Resource());
	passByValue(res1);

	return 0;
}

在这个程序中， res1 将通过值拷贝到参数 res，因此两者 res1.m_ptr 和 res.m_ptr 将持有相同的地址。

当 res 在函数末尾被销毁， res1.m_ptr 留下悬空。当 res1.m_ptr 稍后被删除时，会导致未定义行为。

所以这显然不好。我们如何解决这个问题？

嗯，我们可以做的一件事是显式定义并删除拷贝构造函数和赋值运算符，从而首先防止任何拷贝的发生。这将防止按值传递的情况（这很好，我们可能不应该按值传递这些）。

但那样我们如何将 Auto_ptr1 从函数返回给调用者？

??? generateResource()
{
     Resource* r{ new Resource() };
     return Auto_ptr1(r);
}

我们不能通过引用返回 Auto_ptr1，因为局部 Auto_ptr1 会在函数末尾被销毁，调用者将得到一个悬空引用。我们可以返回指针 r 作为 Resource*，但之后我们可能会忘记删除 r，而这正是使用智能指针的全部意义所在。所以这行不通。按值返回 Auto_ptr1 是唯一合理的选项——但这样会导致浅拷贝、重复指针和崩溃。

另一种选择是重载拷贝构造函数和赋值运算符以实现深拷贝。这样，我们至少可以保证避免指向同一对象的重复指针。但拷贝可能很昂贵（并且可能不可取甚至不可能），而且我们不想仅仅为了从函数返回 Auto_ptr1 而进行不必要的对象拷贝。此外，赋值或初始化一个普通指针并不会拷贝所指向的对象，那么为什么我们会期望智能指针的行为不同呢？

我们该怎么办？

移动语义

如果我们让拷贝构造函数和赋值运算符不拷贝指针（“拷贝语义”），而是将指针的所有权从源对象转移/移动到目标对象，会怎么样？这就是移动语义背后的核心思想。 移动语义 意味着该类将转移对象的所有权，而不是进行拷贝。

让我们更新 Auto_ptr1 类来展示如何做到这一点：

#include <iostream>

template <typename T>
class Auto_ptr2
{
	T* m_ptr {};
public:
	Auto_ptr2(T* ptr=nullptr)
		:m_ptr(ptr)
	{
	}
	
	~Auto_ptr2()
	{
		delete m_ptr;
	}

	// 一个实现移动语义的拷贝构造函数
	Auto_ptr2(Auto_ptr2& a) // 注意：不是 const
	{
		// 这里不需要删除 m_ptr。此构造函数仅在创建新对象时调用，且在此之前 m_ptr 不可能被设置。
		m_ptr = a.m_ptr; // 将我们的裸指针从源对象转移到本地对象
		a.m_ptr = nullptr; // 确保源对象不再拥有该指针
	}
	
	// 实现移动语义的赋值运算符
	Auto_ptr2& operator=(Auto_ptr2& a) // 注意：不是 const
	{
		if (&a == this)
			return *this;

		delete m_ptr; // 确保首先释放目标对象已持有的任何指针
		m_ptr = a.m_ptr; // 然后将我们的裸指针从源对象转移到本地对象
		a.m_ptr = nullptr; // 确保源对象不再拥有该指针
		return *this;
	}

	T& operator*() const { return *m_ptr; }
	T* operator->() const { return m_ptr; }
	bool isNull() const { return m_ptr == nullptr; }
};

class Resource
{
public:
	Resource() { std::cout << "Resource acquired\n"; }
	~Resource() { std::cout << "Resource destroyed\n"; }
};

int main()
{
	Auto_ptr2<Resource> res1(new Resource());
	Auto_ptr2<Resource> res2; // 初始化为 nullptr

	std::cout << "res1 is " << (res1.isNull() ? "null\n" : "not null\n");
	std::cout << "res2 is " << (res2.isNull() ? "null\n" : "not null\n");

	res2 = res1; // res2 取得所有权，res1 被设置为 null

	std::cout << "Ownership transferred\n";

	std::cout << "res1 is " << (res1.isNull() ? "null\n" : "not null\n");
	std::cout << "res2 is " << (res2.isNull() ? "null\n" : "not null\n");

	return 0;
}

该程序打印出：

Resource acquired
res1 is not null
res2 is null
Ownership transferred
res1 is null
res2 is not null
Resource destroyed

注意，我们重载的 operator= 将 m_ptr 的所有权从 res1 转移到了 res2！因此，我们不会得到重复的指针副本，并且一切都被整洁地清理了。

提醒

删除 nullptr 是安全的，因为它什么也不做。

std::auto_ptr，以及为什么它是一个坏主意

现在是讨论 std::auto_ptr 的合适时机。std::auto_ptr 在 C++98 中引入，在 C++17 中移除，是 C++ 首次尝试标准化智能指针。std::auto_ptr 选择像 Auto_ptr2 类那样实现移动语义。

然而，std::auto_ptr（以及我们的 Auto_ptr2 类）有许多问题，使得使用它很危险。

首先，因为 std::auto_ptr 通过拷贝构造函数和赋值运算符实现移动语义，按值将 std::auto_ptr 传递给函数会导致你的资源被移动到函数参数（并在函数结束时，当函数参数超出作用域时被销毁）。然后当你从调用者那里访问你的 auto_ptr 参数时（没有意识到它已被转移和删除），你突然解引用了一个空指针。崩溃！

其次，std::auto_ptr 总是使用非数组 delete 来删除其内容。这意味着 auto_ptr 不能正确使用动态分配的数组，因为它使用了错误类型的释放。更糟糕的是，它不会阻止你传递一个动态数组，然后它会错误地管理它，导致内存泄漏。

最后，auto_ptr 与标准库中的许多其他类（包括大多数容器和算法）配合不佳。这是因为这些标准库类假设当它们拷贝一个项目时，它实际上进行的是拷贝，而不是移动。

由于上述缺点，std::auto_ptr 在 C++11 中已被弃用，并在 C++17 中移除。

向前迈进

std::auto_ptr 设计的核心问题在于，在 C++11 之前，C++ 语言根本没有机制来区分“拷贝语义”和“移动语义”。重写拷贝语义来实现移动语义会导致奇怪的边缘情况和意外的错误。例如，你可以写 res1 = res2 并且不知道 res2 是否会被改变！

因此，在 C++11 中，“移动”的概念被正式定义，并且“移动语义”被添加到语言中，以正确区分拷贝和移动。既然我们已经为移动语义为何有用奠定了基础，我们将在本章的剩余部分探讨移动语义的主题。我们还将使用移动语义修复我们的 Auto_ptr2 类。

在 C++11 中，std::auto_ptr 已被一系列其他类型的“移动感知”智能指针所取代：std::unique_ptr、std::weak_ptr 和 std::shared_ptr。我们还将探讨其中最流行的两个：unique_ptr（它是 auto_ptr 的直接替代品）和 shared_ptr。
