9.1 — 测试代码简介

● 机器译文 课程 9.1 查看英文原文

那么，你写了一个程序，它编译通过了，甚至看起来能运行！接下来呢？

嗯，这取决于情况。如果你写的程序只运行一次然后丢弃，那么你就完成了。在这种情况下，你的程序不一定需要适用于所有情况——如果它满足了你需要的那个场景，并且你只运行一次，那么你就完成了。

如果你的程序完全是线性的（没有条件语句，比如 if 语句 或 switch 语句），不接受任何输入，并且产生了正确的答案，那么你可能就完成了。在这种情况下，你已经通过运行程序并验证输出来测试了整个程序。你可能希望在不同的系统上编译并运行程序，以确保其行为一致（如果不一致，你可能做了某些产生未定义行为的事情，只是碰巧在你的初始系统上能工作）。

但更有可能的是，你写了一个打算多次运行的程序，它使用了循环和条件逻辑，并接受某种用户输入。你可能编写了一些可以在未来其他程序中重用的函数。你可能经历了一些 范围蔓延，即你添加了一些最初未计划的新功能。也许你甚至打算将这个程序分发给其他人（他们可能会尝试你没想到的事情）。在这种情况下，你真的应该验证你的程序在各种条件下是否如你预期的那样工作——这需要一些主动的测试。

仅仅因为你的程序在一组输入下工作正常，并不意味着它在所有情况下都能正确工作。

软件测试 （也称为 软件验证）是确定软件是否按预期工作的过程。

测试的挑战

在我们讨论一些测试代码的实用方法之前，先谈谈为什么全面测试程序是困难的。

考虑这个简单的程序：

#include <iostream>

void compare(int x, int y)
{
    if (x > y)
        std::cout << x << " is greater than " << y << '\n'; // // 情况1
    else if (x < y)
        std::cout << x << " is less than " << y << '\n'; // // 情况2
    else
        std::cout << x << " is equal to " << y << '\n'; // // 情况3
}

int main()
{
    std::cout << "Enter a number: ";
    int x{};
    std::cin >> x;

    std::cout << "Enter another number: ";
    int y{};
    std::cin >> y;

    compare(x, y);

    return 0;
}

假设一个4字节的整数，显式地用每一种可能的输入组合来测试这个程序，需要运行程序18,446,744,073,709,551,616（约18百亿亿）次。显然，这是不可行的！

每当我们请求用户输入，或者在代码中有条件语句时，程序可能执行的方式数量就会乘以某个因子。对于除了最简单程序之外的所有程序，显式测试每一种输入组合几乎立即变得不可能。

现在，你的直觉应该告诉你，你真的不需要运行上述程序18百亿亿次来确保它工作。你可以合理地得出结论：如果情况1对一对 x 和 y 值（其中 x > y）有效，那么它应该对任何一对 x 和 y 不进行任何清理。 x > y都有效。鉴于此，很明显我们实际上只需要运行这个程序大约三次（每次执行函数 compare()中的三种情况之一）就能高度确信它按预期工作。还有其他类似的技巧可以用来大幅减少测试次数，使测试变得可管理。

关于测试方法论可以写很多——事实上，我们可以写一整章。但由于这不是C++特有的主题，我们将只进行简短和非正式的介绍，从你（作为开发者）测试自己代码的角度来讨论。在接下来的几个小节中，我们将讨论一些你在测试代码时应该考虑的 实用 事项。

小片段测试你的程序

考虑一家汽车制造商正在制造一辆定制概念车。你认为他们会选择以下哪种方式？
a) 在安装每个汽车部件之前，单独构建（或购买）并测试每个部件。一旦部件被证明工作正常，将其集成到汽车中并重新测试以确保集成成功。最后，测试整辆车，作为最终验证一切正常。
b) 一次性用所有部件组装一辆车，然后在最后才第一次测试整个车。

显然选项a)是更好的选择。然而，许多新程序员却像选项b)那样编写代码！

在情况b)中，如果任何汽车部件不能按预期工作，机械师必须诊断整辆车以确定问题所在——问题可能出现在任何地方。一个症状可能有多种原因——例如，汽车无法启动是由于火花塞、电池、燃油泵还是其他问题？这会导致大量时间浪费在试图确定问题具体位置以及如何处理上。而且如果发现问题，后果可能是灾难性的——一个区域的改变可能会在多个其他地方引起“连锁反应”（变化）。例如，一个太小的燃油泵可能导致发动机重新设计，进而导致车架重新设计。在最坏的情况下，你可能最终重新设计汽车的大部分，仅仅是为了适应最初的一个小问题！

在情况a)中，公司边进行边测试。如果任何部件一开始就有问题，他们会立即知道并可以修复/更换。在部件被证明独立工作之前，不会集成到汽车中，并且一旦集成到汽车中，该部件会立即再次测试。这样，任何意外问题都能尽早发现，此时它们还是容易修复的小问题。

到他们组装整车时，他们应该对汽车能正常工作有合理的信心——毕竟，所有部件都已经在隔离和初始集成时测试过。此时仍有可能发现意外问题，但通过之前的所有测试，这种风险已经最小化。

上述类比同样适用于程序，尽管出于某种原因，新程序员常常没有意识到这一点。你最好编写小函数（或类），然后立即编译和测试它们。这样，如果你犯了错误，你会知道它一定在你上次编译/测试后修改的那一小段代码中。这意味着更少的查找位置，以及更少的调试时间。

隔离测试代码的一小部分以确保该“单元”代码正确，称为 单元测试。每个 单元测试 旨在确保该单元的特定行为是正确的。

最佳实践

将你的程序编写成小的、定义良好的单元（函数或类），经常编译，并边进行边测试你的代码。

如果程序很短且接受用户输入，尝试各种用户输入可能就足够了。但随着程序越来越长，这种方法就不太够用了，在将单个函数或类集成到程序的其他部分之前，对其进行测试更有价值。

那么，我们如何对代码进行单元测试呢？

非正式测试

测试代码的一种方法是在编写程序时进行非正式测试。编写完一个代码单元（一个函数、一个类或其他一些离散的“代码包”）后，你可以编写一些代码来测试刚刚添加的单元，然后在测试通过后删除测试。例如，对于下面的 isLowerVowel() 函数，你可以编写如下代码：

#include <iostream>

// // 我们想测试下面的函数
// // 为简单起见，我们忽略 'y' 有时被视为元音
bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

int main()
{
    // // 所以这里是我们的临时测试，以验证它是否有效
    std::cout << isLowerVowel('a') << '\n'; // // 临时测试代码，应产生 1
    std::cout << isLowerVowel('q') << '\n'; // // 临时测试代码，应产生 0

    return 0;
}

如果结果返回 1 和 0，那么就可以继续了。你知道你的函数对一些基本案例有效，并且通过查看代码可以合理推断它对你没有测试的案例（'e'、'i'、'o' 和 'u'）也有效。所以你可以删除那个临时测试代码，继续编程。

保留你的测试

虽然编写临时测试是一种快速简便的测试代码的方法，但它没有考虑到将来你可能需要再次测试同一段代码。也许你修改了一个函数以添加新功能，并希望确保没有破坏已经正常工作的部分。因此，保留你的测试以便将来可以再次运行可能更有意义。例如，与其删除临时测试代码，不如将测试移到一个 testVowel() 函数中：

#include <iostream>

bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

// // 目前没有从任何地方调用
// // 但如果你想以后重新测试，可以放在这里
void testVowel()
{
    std::cout << isLowerVowel('a') << '\n'; // // 临时测试代码，应产生 1
    std::cout << isLowerVowel('q') << '\n'; // // 临时测试代码，应产生 0
}

int main()
{
    return 0;
}

当你创建更多测试时，只需将它们添加到 testVowel() 函数的顶部开始。

自动化你的测试函数

上述测试函数的一个问题是它依赖于你手动验证运行结果。这要求你至少记住预期的答案（假设你没有记录它），并手动将实际结果与预期结果进行比较。

我们可以做得更好，编写一个既包含测试又包含预期答案并比较它们的测试函数，这样我们就不必手动操作了。

#include <iostream>

bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

// // 返回失败的测试编号，如果所有测试通过则返回 0
int testVowel()
{
    if (!isLowerVowel('a')) return 1;
    if (isLowerVowel('q')) return 2;

    return 0;
}

int main()
{
    int result { testVowel() };
    if (result != 0)
        std::cout << "testVowel() test " << result << " failed.\n";
    else
        std::cout << "testVowel() tests passed.\n";

    return 0;
}

现在，你可以随时调用 testVowel() 来重新证明你没有破坏任何东西，测试例程会为你完成所有工作，返回一个“一切正常”信号（返回值 0），或者返回未通过的测试编号，以便你调查它为什么失败。这在回头修改旧代码时特别有用，可以确保你没有意外破坏任何东西！

进阶读者

更好的方法是使用 assert，如果任何测试失败，它将导致程序中止并显示错误消息。这样我们就不必创建和处理测试用例编号了。

#include <cassert> // for assert
#include <cstdlib> // for std::abort
#include <iostream>

bool isLowerVowel(char c)
{
    switch (c)
    {
    case 'a':
    case 'e':
    case 'i':
    case 'o':
    case 'u':
        return true;
    default:
        return false;
    }
}

// // 任何失败的测试用例都会导致程序停止
int testVowel()
{
#ifdef NDEBUG
    // 如果定义了 NDEBUG，断言将被编译掉。
    // 由于此函数要求断言不被编译掉，如果在定义了 NDEBUG 的情况下调用此函数，我们将终止程序。
    std::cerr << "Tests run with NDEBUG defined (asserts compiled out)";
    std::abort();
#endif

    assert(isLowerVowel('a'));
    assert(isLowerVowel('e'));
    assert(isLowerVowel('i'));
    assert(isLowerVowel('o'));
    assert(isLowerVowel('u'));
    assert(!isLowerVowel('b'));
    assert(!isLowerVowel('q'));
    assert(!isLowerVowel('y'));
    assert(!isLowerVowel('z'));

    return 0;
}

int main()
{
    testVowel();

    // 如果执行到这里，所有测试必须已通过。
    std::cout << "All tests succeeded\n";

    return 0;
}

我们介绍 assert 在课程 9.6 -- Assert 和 static_assert。

单元测试框架

因为编写函数来测试其他函数非常常见且有用，所以有整个框架（称为 单元测试框架）旨在帮助简化编写、维护和执行单元测试的过程。由于这些涉及第三方软件，我们在此不进行介绍，但你应该知道它们的存在。

集成测试

一旦每个单元被单独测试，它们就可以集成到你的程序中并重新测试，以确保它们被正确集成。这称为 集成测试。集成测试往往更复杂——目前，运行你的程序几次并抽查集成单元的行为就足够了。
