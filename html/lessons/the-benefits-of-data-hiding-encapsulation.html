14.8 — 数据隐藏（封装）的好处

● 机器译文 课程 14.8 查看英文原文

在之前的课程（14.5 -- 公有和私有成员及访问说明符）中，我们提到类的成员变量通常设为私有。初次学习类的程序员常常难以理解为什么要这样做。毕竟，将变量设为私有意味着它们不能被外部访问。往好了说，这只是在编写类时增加了工作量；往坏了说，这似乎完全没有意义（尤其是当我们提供公共访问函数来访问私有成员数据时）。

这个问题的答案非常基础，以至于我们将用整节课来讨论这个主题！

让我们先从一个类比开始。

在现代生活中，我们可以使用许多机械或电子设备。你用遥控器开关电视；你踩油门让汽车前进；你拨动开关打开灯。所有这些设备都有一个共同点：它们提供了一个简单的用户界面（一组按钮、一个踏板、一个开关等），让你执行关键操作。

这些设备实际如何运作对你来说是隐藏的。当你按下遥控器上的按钮时，你不需要知道遥控器如何与电视通信；当你踩下汽车油门时，你不需要知道内燃机如何使车轮转动；当你拍照时，你不需要知道传感器如何收集光线并将其转化为像素图像。

这种接口与实现的分离非常有用，因为它允许我们在不了解对象工作原理的情况下使用它们——我们只需要知道如何与它们交互。这大大降低了使用这些对象的复杂性，并增加了我们能够交互的对象数量。

类类型中的实现与接口

出于类似的原因，接口与实现的分离在编程中也是有用的。但首先，让我们定义一下在类类型中接口和实现的含义。

浮点类型的 接口 （也称为 类接口）定义了类类型的用户将如何与该类类型的对象交互。由于只有公有成员可以从类类型外部访问，因此类类型的公有成员构成了它的接口。因此，由公有成员组成的接口有时被称为 公有接口。

接口是类作者与类用户之间的隐式契约。如果现有接口发生更改，任何使用它的代码都可能被破坏。因此，确保我们类类型的接口设计良好且稳定（不经常更改）非常重要。

浮点类型的 实现 由实际使类按预期工作的代码组成。这包括存储数据的成员变量，以及包含程序逻辑并操作成员变量的成员函数体。

数据隐藏

在编程中， 数据隐藏 （也称为 信息隐藏 或 数据抽象）是一种通过隐藏（使其不可访问）程序定义数据类型的实现来强制分离接口与实现的技术。

在C++类类型中实现数据隐藏很简单。首先，我们确保类类型的数据成员是私有的（这样用户不能直接访问它们）。成员函数体内的语句已经不能被用户直接访问，所以我们不需要在那里做任何其他事情。接下来，我们确保成员函数是公有的，这样用户就可以调用它们。

通过遵循这些规则，我们强制类类型的用户使用公有接口操作对象，并阻止他们直接访问实现细节。

C++中定义的类应该使用数据隐藏。事实上，标准库提供的所有类都是这样做的。另一方面，结构体不应该使用数据隐藏，因为拥有非公有成员会阻止它们被视为聚合体。

以这种方式定义类需要类作者付出一些额外的工作。要求类的用户使用公有接口似乎比直接提供对成员变量的公有访问更麻烦。但这样做提供了大量有用的好处，有助于提高类的可重用性和可维护性。我们将在本课的剩余部分讨论这些好处。

术语

在编程中，术语 封装 通常指以下两种情况之一：

  • 将一个或多个项目封装在某种容器中。
  • 将数据和操作该数据实例的函数捆绑在一起。

在C++中，一个拥有数据和用于创建及操作该类对象的公有接口的类类型是封装的。由于封装是数据隐藏的前提，并且数据隐藏是如此重要的技术，按照惯例，术语封装通常也包括数据隐藏。

在本教程系列中，我们假设所有封装的类都实现了数据隐藏。

数据隐藏使类更易于使用，并降低复杂性

要使用一个封装的类，你不需要知道它是如何实现的。你只需要理解它的接口：哪些成员函数是公有的，它们接受什么参数，以及返回什么值。

例如：

#include <iostream>
#include <string_view>

int main()
{
    std::string_view sv{ "Hello, world!" };
    std::cout << sv.length();

    return 0;
}

在这个简短的程序中， std::string_view 的实现细节并没有暴露给我们。我们看不到一个 std::string_view 有多少个数据成员，它们叫什么名字，或者是什么类型。我们不知道 length() 成员函数是如何返回所查看字符串的长度的。

而最棒的是，我们不需要知道！程序就是能工作。我们只需要知道如何初始化一个类型为 std::string_view，以及 length() 成员函数返回什么。

不必关心这些细节极大地降低了程序的复杂性，从而减少了错误。这比任何其他原因都更能体现封装的关键优势。

想象一下，如果你必须了解 std::string， std::vector，或 std::cout 是如何实现的才能使用它们，C++ 会变得多么复杂！

数据隐藏允许我们维护不变量

回到关于类的入门课程（14.2 -- 类简介），我们引入了 类不变量的概念，这些条件在对象的整个生命周期中必须为真，以使对象保持有效状态。

考虑以下程序：

#include <iostream>
#include <string>

struct Employee // 成员默认是公有的
{
    std::string name{ "John" };
    char firstInitial{ 'J' }; // 应与名字的首字母匹配

    void print() const
    {
        std::cout << "Employee " << name << " has first initial " << firstInitial << '\n';
    }
};

int main()
{
    Employee e{}; // 默认为 "John" 和 'J'
    e.print();

    e.name = "Mark"; // 将员工姓名改为 "Mark"
    e.print(); // 打印错误的初始值

    return 0;
}

该程序打印出：

John has first initial J
Mark has first initial J

的对象时未提供显式初始化值，则将使用这些默认成员初始化值。我们的 Employee struct 有一个类不变量，即 firstInitial 应始终等于 name的第一个字符。如果这不再成立，那么 print() 函数将出现故障。

由于 name 成员是公有的， main() 中的代码能够设置 e.name 切换到 "Mark"，而 firstInitial 成员未更新。我们的不变量被破坏，第二次调用 print() 没有按预期工作。

当我们允许用户直接访问类的实现时，他们就要负责维护所有不变量——而他们可能不会（正确地或根本不会）这样做。将这一负担强加给用户会增加大量复杂性。

让我们重写这个程序，将成员变量设为私有，并暴露一个成员函数来设置 Employee 的名字：

#include <iostream>
#include <string>
#include <string_view>

class Employee // 成员默认是私有的
{
    std::string m_name{};
    char m_firstInitial{};

public:
    void setName(std::string_view name)
    {
        m_name = name;
        m_firstInitial = name.front(); // 使用 std::string::front() 获取 `name` 的第一个字母
    }

    void print() const
    {
        std::cout << "Employee " << m_name << " has first initial " << m_firstInitial << '\n';
    }
};

int main()
{
    Employee e{};
    e.setName("John");
    e.print();

    e.setName("Mark");
    e.print();

    return 0;
}

这个程序现在按预期工作：

John has first initial J
Mark has first initial M

从用户的角度来看，唯一的变化是，他们不再直接给 name 赋值，而是调用成员函数 setName()，该函数负责同时设置 m_name 和 m_firstInitial。用户不再需要承担维护这个不变量的负担！

数据隐藏允许我们进行更好的错误检测（和处理）

在上面的程序中，不变量 m_firstInitial 必须匹配 m_name 的第一个字符之所以存在，是因为 m_firstInitial 独立于 m_name存在。我们可以通过将数据成员 m_firstInitial 替换为一个返回首字母的成员函数来消除这个特定的不变量：

#include <iostream>
#include <string>

class Employee
{
    std::string m_name{ "John" };

public:
    void setName(std::string_view name)
    {
        m_name = name;
    }

    // 使用 std::string::front() 获取 `m_name` 的第一个字母
    char firstInitial() const { return m_name.front(); }

    void print() const
    {
        std::cout << "Employee " << m_name << " has first initial " << firstInitial() << '\n';
    }
};

int main()
{
    Employee e{}; // 默认为 "John"
    e.setName("Mark");
    e.print();

    return 0;
}

然而，这个程序还有另一个类不变量。花点时间看看你是否能找出它。我们在这里等着，看着油漆变干……

答案是 m_name 不应该是空字符串（因为每个 Employee 都应该有一个名字）。如果 m_name 被设置为空字符串，不会立即发生坏事。但如果随后调用 firstInitial() ， front() 的 std::string 成员将尝试获取空字符串的第一个字母，这会导致未定义行为。

理想情况下，我们希望防止 m_name 永远不会为空。

如果用户对 m_name 成员有公共访问权限，他们可以直接设置 m_name = ""，而我们对此无能为力。

然而，由于我们强制用户通过公共接口函数 m_name 来设置 setName()，我们可以让 setName() 验证用户传入的名称是否有效。如果名称非空，则将其赋值给 m_name。如果名称为空字符串，我们可以采取多种措施：

  • 忽略将名称设置为“”的请求并返回调用者。
  • 触发断言。
  • 抛出异常。
  • 跳个滑稽舞。等等，不是这个。

关键在于，我们可以检测到误用，然后以我们认为最合适的方式处理。如何有效处理这类情况是另一天的主题。

数据隐藏使得在不破坏现有程序的情况下更改实现细节成为可能

考虑这个简单的例子：

#include <iostream>

struct Something
{
    int value1 {};
    int value2 {};
    int value3 {};
};

int main()
{
    Something something;
    something.value1 = 5;
    std::cout << something.value1 << '\n';
}

虽然这个程序运行良好，但如果我们决定更改类的实现细节，比如这样，会发生什么？

#include <iostream>

struct Something
{
    int value[3] {}; // 使用包含 3 个值的数组
};

int main()
{
    Something something;
    something.value1 = 5;
    std::cout << something.value1 << '\n';
}

我们还没有介绍数组，但不用担心。关键在于，这个程序不再编译，因为名为 value1 的成员不再存在，而 main() 中的一条语句仍然在使用该标识符。

数据隐藏使我们能够在不破坏使用它们的程序的情况下更改类的实现方式。

以下是该类原始版本的封装版本，它使用函数来访问 m_value1：

#include <iostream>

class Something
{
private:
    int m_value1 {};
    int m_value2 {};
    int m_value3 {};

public:
    void setValue1(int value) { m_value1 = value; }
    int getValue1() const { return m_value1; }
};

int main()
{
    Something something;
    something.setValue1(5);
    std::cout << something.getValue1() << '\n';
}

现在，让我们将类的实现改回数组：

#include <iostream>

class Something
{
private:
    int m_value[3]; // 注意：我们更改了这个类的实现！

public:
    // 我们必须更新所有成员函数以反映新的实现
    void setValue1(int value) { m_value[0] = value; }
    int getValue1() const { return m_value[0]; }
};

int main()
{
    // 但使用该类的程序不需要更新！
    Something something;
    something.setValue1(5);
    std::cout << something.getValue1() << '\n';
}

由于我们没有更改类的公共接口，使用该接口的程序完全不需要更改，并且功能仍然相同。

打个比方，如果地精在夜间潜入你家，用另一种（但兼容的）技术替换了电视遥控器的内部结构，你可能根本不会注意到！

具有接口的类更容易调试

最后，封装可以在出现问题时帮助你调试程序。通常，程序不能正确运行是因为我们的某个成员变量被赋予了错误的值。如果每个人都能直接设置成员变量，那么追踪到底是哪段代码将成员变量修改为错误的值可能会很困难。这可能需要对每个修改该成员变量的语句设置断点——而且可能有很多这样的语句。

然而，如果一个成员只能通过单个成员函数更改，那么你可以简单地在该函数上设置断点，并观察每个调用者如何更改该值。这可以更容易地确定谁是罪魁祸首。

优先使用非成员函数而非成员函数

在C++中，如果一个函数可以合理地实现为非成员函数，那么优先将其实现为非成员函数，而不是成员函数。

这有很多好处：

  • 非成员函数不是类接口的一部分。因此，类的接口会更小、更直接，使类更容易理解。
  • 非成员函数强制封装，因为此类函数必须通过类的公共接口工作。不会因为方便而直接访问实现。
  • 在更改类的实现时，不需要考虑非成员函数（只要接口没有以不兼容的方式更改）。
  • 非成员函数往往更容易调试。
  • 包含特定于应用程序的数据和逻辑的非成员函数可以与类的可重用部分分离。

如果你有现代面向对象语言（如Java或C#）的经验，这种做法可能会让你感到惊讶。这些语言使用不同的概念模型，其中类是宇宙的中心，一切都围绕它展开。因此，这些语言将成员函数放在首位（实际上，Java和C#甚至不支持非成员函数）。

最佳实践

尽可能优先将函数实现为非成员（尤其是包含特定于应用程序的数据或逻辑的函数）。

提示

以下是一个简化的指南，说明何时将函数设为成员函数与非成员函数：

  • 在必须时使用成员函数。C++要求某些类型的函数必须定义为成员。我们将在下一课中看到一个例子，当我们讨论构造函数时。其他包括析构函数、虚函数和某些运算符。
  • 当函数需要访问不应暴露的私有（或受保护）数据时，优先使用成员函数。
  • 否则优先使用非成员函数（尤其是那些不修改对象状态的函数）。

后两条规则存在例外——我们将在讨论相关主题时介绍其中一些。

一个常见但具有挑战性的情况是，优先使用非成员函数需要添加访问函数来辅助。在这种情况下，你需要权衡利弊。

  • 添加访问函数意味着创建一个或两个新的成员函数（getter 和可能的 setter），这会增加类接口的大小和复杂性。除非你能在多个地方使用这些新的访问函数，否则可能不值得。
  • 不要为不应直接访问的数据（例如，因为它是内部状态）或允许用户违反类不变量的数据添加访问函数。

相关内容

文章 《非成员函数如何改进封装》 由 Scott Meyers 撰写，进一步探讨了优先使用非成员函数的理念。

让我们用三个类似的例子来说明，从最差到最好：

#include <iostream>
#include <string>

class Yogurt
{
    std::string m_flavor{ "vanilla" };

public:
    void setFlavor(std::string_view flavor)
    {
        m_flavor = flavor;
    }

    const std::string& getFlavor() const { return m_flavor; }

    // 最差：成员函数 print() 在有 getter 的情况下直接访问 m_flavor
    void print() const
    {
        std::cout << "The yogurt has flavor " << m_flavor << '\n';
    }
};

int main()
{
    Yogurt y{};
    y.setFlavor("cherry");
    y.print();

    return 0;
}

以上是最差的版本。 print() 成员函数直接访问 m_flavor ，而已经存在一个获取 flavor 的 getter。如果类实现被更新， print() 也可能需要修改。由 print() 打印的字符串是特定于应用程序的（另一个使用此类的应用程序可能想要打印其他内容，这将需要克隆或修改该类）。

#include <iostream>
#include <string>

class Yogurt
{
    std::string m_flavor{ "vanilla" };

public:
    void setFlavor(std::string_view flavor)
    {
        m_flavor = flavor;
    }

    const std::string& getFlavor() const { return m_flavor; }

    // 较好：成员函数 print() 不直接访问成员
    void print(std::string_view prefix) const
    {
        std::cout << prefix << ' ' << getFlavor() << '\n';
    }
};

int main()
{
    Yogurt y{};
    y.setFlavor("cherry");
    y.print("The yogurt has flavor");

    return 0;
}

以上版本更好，但仍然不够好。 print() 仍然是成员函数，但至少它不再直接访问任何数据成员。如果类实现被更新， print() 需要评估是否需要更新（但不需要）。 print() 函数的前缀现在是参数化的，这允许我们将前缀移到非成员函数 main()中。但该函数仍然对打印方式施加了限制（例如，它总是打印为前缀、空格、flavor、换行）。如果这不能满足特定应用程序的需求，则需要添加另一个函数。

#include <iostream>
#include <string>

class Yogurt
{
    std::string m_flavor{ "vanilla" };

public:
    void setFlavor(std::string_view flavor)
    {
        m_flavor = flavor;
    }

    const std::string& getFlavor() const { return m_flavor; }
};

// 最佳：非成员函数 print() 不属于类接口
void print(const Yogurt& y)
{
        std::cout << "The yogurt has flavor " << y.getFlavor() << '\n';
}

int main()
{
    Yogurt y{};
    y.setFlavor("cherry");
    print(y);

    return 0;
}

以上版本是最好的。 print() 现在是一个非成员函数。它不直接访问任何成员。如果类实现发生变化， print() 根本不需要评估。此外，每个应用程序可以提供自己的 print() 函数，以完全按照该应用程序想要的方式打印。

类成员声明的顺序

在类外部编写代码时，我们需要在使用变量和函数之前声明它们。然而，在类内部，这个限制不存在。如课程 14.3 -- 成员函数所述，我们可以按任意顺序排列成员。

那么我们应该如何排列它们呢？

这里有两种思路：

  • 先列出私有成员，然后列出公有成员函数。这遵循了先声明后使用的传统风格。任何查看你类代码的人都会看到你在使用数据成员之前是如何定义它们的，这可以使阅读和理解实现细节更容易。
  • 先列出公有成员，将私有成员放在底部。因为使用你类的人对公有接口感兴趣，将公有成员放在前面可以使他们需要的信息位于顶部，而将实现细节（最不重要的）放在最后。

在现代 C++ 中，第二种方法（公有成员在前）更常被推荐，特别是对于将与其他开发者共享的代码。

最佳实践

先声明公有成员，然后是受保护成员，最后是私有成员。这突出了公有接口，并弱化了实现细节。

作者注

本网站上的大多数示例使用了与推荐顺序相反的顺序。这有一部分是历史原因，但我们也发现这种顺序在学习语言机制时更直观，因为我们关注的是实现细节和剖析工作原理。
