3.2 — 调试过程

● 机器译文 课程 3.2 查看英文原文

假设你写了一个程序，但它运行不正常——代码编译通过，但运行时得到错误结果。某处肯定有一个语义错误。如何找到它？如果你一直遵循最佳实践，写一点点代码就测试一下，你可能对错误位置有比较好的把握。或者你可能完全没头绪。

所有bug都源于一个简单的前提：你认为正确的东西，其实不正确。实际找出错误所在可能很有挑战性。在本课中，我们将概述调试程序的一般过程。

由于我们尚未涵盖那么多C++主题，本章中的示例程序将相当基础。这可能会使我们在此展示的一些技术显得多余。但请记住，这些技术是为更大、更复杂的程序设计的，在这样的环境中会更有用（这也是你最需要它们的地方）。

调试的一般方法

一旦发现问题，调试通常包括六个步骤：

  1. 找到问题的根本原因（通常是有问题的代码行）。我们将在下一课中讨论一些实现此目的的策略。
  2. 确保你理解问题发生的原因。
  3. 确定修复问题的方法。
  4. 修复导致问题的错误。
  5. 重新测试以确保问题已被修复。
  6. 重新测试以确保没有出现新问题。

让我们用现实生活中的类比来说明。假设某天晚上，你去冰箱的制冰机取冰。你把杯子放在制冰器下方，按下杠杆，然后……什么也没出来。哎呀，你发现某种缺陷。你会怎么做？你可能会开始调查，看是否能找到问题的根本原因。

找到根本原因： 由于你听到制冰器试图送冰的声音，可能不是送冰机制本身的问题。于是你打开冰箱，检查冰盘，没有冰。这是问题的根本原因吗？不，这是另一个症状。进一步检查后，你确定制冰机似乎没有在制冰。问题是制冰机还是其他东西？冰箱仍然制冷，水管没有堵塞，其他一切似乎正常，所以你得出结论，根本原因是制冰机坏了。

理解问题： 在这个案例中很简单。坏了的制冰机不会制冰。

确定修复方案： 此刻，你有几种修复方案：你可以绕过问题（从商店买袋装冰）。你可以尝试进一步诊断制冰机，看看是否有可修复的部件。你可以买一个新的制冰机并替换当前的。或者你可以买一个新冰箱。你决定买一个新的制冰机。

修复问题： 一旦制冰机到达，你将其安装好。

重新测试： 在重新接通电源并等待一夜之后，你的新制冰机开始制冰。未发现新问题。

现在，让我们将这个流程应用到上一课的简单程序中：

#include <iostream>

int add(int x, int y) // 此函数本应执行加法运算
{
    return x - y; // 但由于使用了错误的运算符而未实现
}

int main()
{
    std::cout << "5 + 3 = " << add(5, 3) << '\n'; // 本应产生8，但实际产生了2

    return 0;
}

这段代码在一个方面很好：Bug 非常明显，因为第 10 行将错误结果打印到了屏幕。这为我们的调查提供了一个起点。

找到根本原因： 在第 10 行，我们可以看到我们传入的字面量作为实参（5 和 3），因此那里没有出错的空间。由于传入函数 add 是正确的，但输出却不是，那么很明显，函数 add 一定产生了错误的值。函数中唯一的语句是 add 是返回语句，它一定是罪魁祸首。我们已经找到了问题所在的行。现在我们知道应该把注意力集中在哪里，注意到我们是在做减法而不是加法，这很可能是你通过检查能够发现的。

理解问题： 在这种情况下，错误值产生的原因很明显——我们使用了错误的运算符。

确定修复方案： 我们只需将 operator- 切换到 operator+。

修复问题： 这实际上是在修改 operator- 切换到 operator+ 并确保程序重新编译。

重新测试： 实施更改后，重新运行程序将表明我们的程序现在产生了正确的值 8。对于这个简单的程序，这就是所需要的全部测试。

这个例子很简单，但说明了诊断任何程序时你将经历的基本过程。
