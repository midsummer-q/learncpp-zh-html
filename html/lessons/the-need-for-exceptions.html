27.1 — 异常的必要性

● 机器译文 课程 27.1 查看英文原文

在上一节关于 处理错误，我们讨论了使用 assert()、std::cerr 和 exit() 处理错误的方法。然而，我们推迟了一个进一步的话题，现在将进行介绍：异常。

当返回码失败时

在编写可重用代码时，错误处理是必要的。处理潜在错误的最常见方法之一是通过返回码。例如：

#include <string_view>

int findFirstChar(std::string_view string, char ch)
{
    // 遍历字符串中的每个字符
    for (std::size_t index{ 0 }; index < string.length(); ++index)
        // 如果字符匹配 ch，返回其索引
        if (string[index] == ch)
            return index;

    // 如果未找到匹配，返回 -1
    return -1;
}

该函数返回字符串中第一个匹配 ch 的字符的索引。如果找不到该字符，函数返回 -1 作为未找到的指示。

这种方法的主要优点是极其简单。然而，使用返回码有许多缺点，在非平凡情况下会迅速显现：

首先，返回值可能难以理解——如果函数返回 -1，它是在指示错误，还是实际上是一个有效的返回值？通常很难在不深入函数内部或查阅文档的情况下判断。

其次，函数只能返回一个值，那么当需要同时返回函数结果和可能的错误代码时会发生什么？考虑以下函数：

double divide(int x, int y)
{
    return static_cast<double>(x)/y;
}

这个函数迫切需要一些错误处理，因为如果用户为参数 y 传入 0，它会崩溃。然而，它还需要返回 x/y 的结果。它如何同时做到这两点？最常见的答案是，要么结果要么错误处理必须通过引用参数传回，这会导致代码丑陋且使用不便。例如：

#include <iostream>

double divide(int x, int y, bool& outSuccess)
{
    if (y == 0)
    {
        outSuccess = false;
        return 0.0;
    }

    outSuccess = true;
    return static_cast<double>(x)/y;
}

int main()
{
    bool success {}; // 我们现在必须传入一个 bool 值来查看调用是否成功
    double result { divide(5, 3, success) };

    if (!success) // 并在使用结果之前检查它
        std::cerr << "An error occurred" << std::endl;
    else
        std::cout << "The answer is " << result << '\n';
}

第三，在可能出错的代码序列中，必须不断检查错误码。考虑以下解析文本文件以获取预期值的代码片段：

    std::ifstream setupIni { "setup.ini" }; // 打开 setup.ini 进行读取
    // 如果文件无法打开（例如因为文件缺失），返回某个错误枚举
    if (!setupIni)
        return ERROR_OPENING_FILE;

    // 现在从文件中读取一系列值
    if (!readIntegerFromFile(setupIni, m_firstParameter)) // 尝试从文件中读取一个整数
        return ERROR_READING_VALUE; // 返回指示无法读取值的枚举值

    if (!readDoubleFromFile(setupIni, m_secondParameter)) // 尝试从文件中读取一个 double
        return ERROR_READING_VALUE;

    if (!readFloatFromFile(setupIni, m_thirdParameter)) // 尝试从文件中读取一个 float
        return ERROR_READING_VALUE;

我们还没有介绍文件访问，所以如果你不理解上述代码的工作原理，不必担心——只需注意每个调用都需要错误检查并返回给调用者。现在想象一下，如果有二十个不同类型的参数——你基本上要检查错误并返回 ERROR_READING_VALUE 二十次！所有这些错误检查和返回值使得确定 什么 函数试图做什么变得更加困难。

第四，返回码与构造函数不太兼容。如果你正在创建一个对象，而构造函数内部发生了灾难性错误，会发生什么？构造函数没有返回类型来传递状态指示，通过引用参数传递一个状态指示既混乱又必须显式检查。此外，即使你这样做了，对象仍然会被创建，然后必须处理或销毁。

最后，当错误码返回给调用者时，调用者可能并不总是有能力处理该错误。如果调用者不想处理错误，它要么忽略它（在这种情况下错误将永远丢失），要么将错误向上返回给调用它的函数。这可能很混乱，并导致许多与上述相同的问题。

总结一下，返回码的主要问题是错误处理代码最终与正常的控制流紧密耦合。这反过来限制了代码的布局方式以及错误的合理处理方式。

异常

异常处理提供了一种机制，将错误或其他异常情况的处理与代码的典型控制流解耦。这允许更自由地根据特定情况以最有用的方式处理错误，减轻了返回码造成的大部分（如果不是全部）混乱。
