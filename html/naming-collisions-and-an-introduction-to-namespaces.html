2.9 — 命名冲突与命名空间简介

● 机器译文 课程 2.9 查看英文原文

假设你第一次开车去朋友家，地址是米尔城的前街245号。到达米尔城后，你拿出地图，却发现米尔城实际上有两条不同的前街，分布在城镇的两端！你会去哪一个？除非有额外的线索帮助你决定（例如，你记得朋友家靠近河边），否则你不得不打电话给朋友询问更多信息。因为这会令人困惑且效率低下（尤其对于邮递员来说），在大多数国家，一个城市内的所有街道名称和房屋地址都必须唯一。

类似地，C++ 要求所有标识符必须无歧义。如果两个相同的标识符以编译器或链接器无法区分的方式引入同一程序，编译器或链接器将产生错误。这种错误通常称为 名称碰撞 （或 命名冲突)。

如果冲突的标识符被引入同一文件，结果将是一个编译器错误。如果冲突的标识符被引入属于同一程序的不同文件，结果将是一个链接器错误。

名称碰撞的例子

a.cpp：

#include <iostream>

void myFcn(int x)
{
    std::cout << x;
}

main.cpp:

#include <iostream>

void myFcn(int x)
{
    std::cout << 2 * x;
}

int main()
{
    return 0;
}

当编译器编译此程序时，它将独立编译 a.cpp 和 main.cpp 每个文件编译都没有问题。

然而，当链接器执行时，它将链接 a.cpp 和 main.cpp 中所有定义，并发现函数 myFcn()的冲突定义。链接器随后将中止并报错。注意，即使 myFcn() 从未被调用，此错误也会发生！

大多数名称碰撞发生在两种情况下：

  1. 两个（或更多）同名函数（或全局变量）被引入同一程序的不同文件中。这将导致链接器错误，如上所示。
  2. 两个（或更多）同名函数（或全局变量）被引入同一文件中。这将导致编译器错误。

随着程序变得越来越大，使用越来越多的标识符，命名冲突引入的几率显著增加。好消息是 C++ 提供了大量避免命名冲突的机制。局部作用域（将函数内部定义的局部变量彼此分开）就是其中一种机制。但局部作用域对函数名无效。那么，如何防止函数名相互冲突呢？

作用域区域

回到我们的地址比喻一会儿，有两条前街之所以会出问题，是因为这些街道位于同一个城市。另一方面，如果你需要将邮件投递到两个地址——一个是米尔城的245号前街，另一个是琼斯维尔的245号前街——那么就不会有去往何处的混淆。换句话说，城市提供了分组，使我们能够消除可能相互冲突的地址之间的歧义。

一个 作用域区域 是源代码中的一个区域，其中所有声明的标识符都被视为与其他作用域中声明的名称不同（类似于比喻中的城市）。两个同名标识符可以声明在不同的作用域区域中而不会导致命名冲突。然而，在给定的作用域区域内，所有标识符必须是唯一的，否则会导致命名冲突。

函数体是作用域区域的一个例子。可以在不同的函数中定义两个同名的标识符而不会出现问题——因为每个函数提供了单独的作用域区域，所以不会发生冲突。但是，如果你试图在同一个函数中定义两个同名的标识符，就会发生命名冲突，编译器会报错。

命名空间

一个 命名空间 提供了另一种类型的作用域区域（称为 命名空间作用域），允许你为了消除歧义而在此区域内声明或定义名称。命名空间中声明的名称与其他作用域中声明的名称相隔离，使得这些名称可以共存而不冲突。

关键提示

在一个作用域区域（如命名空间）内声明的名称与另一个作用域中声明的任何同名名称是不同的。

例如，两个具有相同声明的函数可以在不同的命名空间中定义，而不会发生命名冲突或歧义。

命名空间只能包含声明和定义（例如变量和函数）。不允许使用可执行语句，除非它们是定义的一部分（例如在函数内部）。

关键提示

一个命名空间只能包含声明和定义。可执行语句只允许作为定义的一部分（例如函数的定义）。

命名空间常用于将大型项目中的相关标识符分组，以帮助确保它们不会意外地与其他标识符冲突。例如，如果你将所有数学函数放入一个名为 math，那么你的数学函数就不会与 math 命名空间之外的同名函数冲突。

我们将在未来的课程中讨论如何创建自己的命名空间。

全局命名空间

在C++中，任何未在类、函数或命名空间内定义的名称都被视为隐式定义的命名空间的一部分，该命名空间称为 全局命名空间 （有时也称为 全局作用域)。

在本课开头的示例中，函数 main() 和两个版本的 myFcn() 都定义在全局命名空间内。示例中遇到命名冲突是因为两个版本的 myFcn() 最终都位于全局命名空间，这违反了作用域区域内所有名称必须唯一的规则。

我们将在课程 7.4 -- 全局变量简介。

目前，你需要了解两件事：

  • 在全局作用域内声明的标识符，其作用域从声明点开始直到文件末尾。
  • 虽然可以在全局命名空间中定义变量，但通常应避免这样做（我们将在课程 7.8 -- 为什么（非常量）全局变量是邪恶的)。

例如：

#include <iostream> // imports the declaration of std::cout into the global scope

// 以下所有语句都是全局命名空间的一部分

void foo();    // 可以：函数前向声明
int x;         // 可编译但强烈不推荐：非常量全局变量定义（无初始化器）
int y { 5 };   // 可编译但强烈不推荐：非常量全局变量定义（有初始化器）
x = 5;         // 编译错误：命名空间中不允许可执行语句

int main()     // 可以：函数定义
{
    return 0;
}

void goo();    // 可以：函数前向声明

std 命名空间

最初设计 C++ 时，C++ 标准库中的所有标识符（包括 std::cin 和 std::cout）都可以不使用 std:: 前缀直接使用（它们属于全局命名空间）。然而，这意味着标准库中的任何标识符都可能与你为自己标识符选择的任何名称（也定义在全局命名空间中）发生冲突。原本正常工作的代码在包含标准库的其他部分时可能会突然出现命名冲突。更糟的是，在一个 C++ 版本下编译的代码可能无法在下一个版本下编译，因为标准库中引入的新标识符可能与已有代码产生命名冲突。因此，C++ 将标准库中的所有功能移到了一个名为 std （'standard' 的缩写）的命名空间中。

事实上， std::cout的名称并非真正的 std::cout它实际上只是 cout、和 std 是标识符所属的命名空间的名称 cout 的一部分。由于 cout 定义在 std 命名空间中，因此名称 cout 不会与任何名为...的对象或函数发生冲突 cout 我们在...之外创建的那些 std 命名空间（例如在全局命名空间中）中的。

关键提示

当你使用在非全局命名空间（例如...）内定义的标识符时 std 命名空间），你需要告知编译器该标识符位于该命名空间内。

有几种不同的方式来实现这一点。

显式命名空间限定符 std::

告诉编译器我们希望使用...的最直接方式 cout 来自... std 命名空间是通过显式使用...前缀 std:: 前缀。例如：

#include <iostream>

int main()
{
    std::cout << "Hello world!"; // 当我们说 cout 时，我们指的是定义在 std 命名空间中的 cout
    return 0;
}

:: 符号是一个运算符，称为 作用域解析运算符位于...左侧的标识符 :: 符号标识了位于...右侧的名称所在的命名空间 :: 符号包含在其中。如果...左侧没有标识符 :: 提供符号，则假定为全局命名空间。

因此，当我们说 std::cout 我们是在说“...在...中声明 cout 在命名空间中声明的那个... std“。

这是最安全的使用方式 cout，因为关于我们在引用哪个 cout 我们在引用（位于 std 命名空间）。

最佳实践

使用显式命名空间前缀来访问命名空间中定义的标识符。

当标识符包含命名空间前缀时，该标识符称为 限定名称。

使用 namespace std（以及为何应避免使用）

另一种访问命名空间内标识符的方法是使用 using 指令语句。以下是我们最初的“Hello world”程序，其中包含一个 using 指令：

#include <iostream>

using namespace std; // 这是一个 using 指令，允许我们在不使用命名空间前缀的情况下访问 std 命名空间中的名称

int main()
{
    cout << "Hello world!";
    return 0;
}

一个 using 指令 允许我们无需使用命名空间前缀即可访问命名空间中的名称。因此在上面的例子中，当编译器要确定标识符 cout 是什么时，它将匹配到 std::cout，由于 using 指令，该标识符可直接作为 cout。

许多文本、教程甚至某些 IDE 都推荐或在程序顶部使用 using 指令。然而，这样使用是一种不良实践，强烈不推荐。

考虑以下程序：

#include <iostream> // imports the declaration of std::cout into the global scope

using namespace std; // 使 std::cout 可以作为 "cout" 访问
 
int cout() // 在全局命名空间中定义我们自己的 "cout" 函数
{
    return 5;
}
 
int main()
{
    cout << "Hello, world!"; // 编译错误！我们这里想要哪个 cout？是 std 命名空间中的那个还是我们上面定义的那个？
 
    return 0;
}

上述程序无法编译，因为编译器现在无法判断我们想要的是 cout 我们自己定义的函数还是 std::cout。

当以这种方式使用 using 指令时， 任何 我们定义的标识符可能与 任何 名称相同的标识符在 std 命名空间中。更糟糕的是，即使某个标识符名称今天不会冲突，将来也可能与语言修订版中添加到 std 命名空间的新标识符冲突。这正是将标准库中所有标识符移入 std 命名空间的初衷！

警告

避免使用 using 指令（例如 using namespace std;）在程序顶部或头文件中。它们违背了引入命名空间的初衷。

相关内容

我们更详细地讨论 using 声明和 using 指令（以及如何负责任地使用它们）在第 7.13 -- 使用声明和 using 指令。

花括号和缩进代码

在 C++ 中，花括号通常用于界定嵌套在另一个作用域区域内部的作用域区域（花括号也用于一些与作用域无关的目的，例如列表初始化）。例如，定义在全局作用域区域内部的函数使用花括号将函数的作用域区域与全局作用域分隔开。

在某些情况下，定义在花括号外部的标识符可能仍然是花括号定义的作用域的一部分，而不是周围的作用域——函数参数就是一个很好的例子。

例如：

#include <iostream> // imports the declaration of std::cout into the global scope

void foo(int x) // foo 定义在全局作用域中，x 定义在 foo() 的作用域内
{ // 花括号用于界定函数 foo() 的嵌套作用域区域
    std::cout << x << '\n';
} // x 在此处离开作用域

int main()
{ // 花括号用于界定函数 main() 的嵌套作用域区域
    foo(5);

    int x { 6 }; // x 定义在 main() 的作用域内
    std::cout << x << '\n';
 
    return 0;
} // x 在此处离开作用域
// foo、main（以及 std::cout）在此处离开作用域（文件末尾）

嵌套作用域区域内的代码通常缩进一级，既是为了可读性，也是为了帮助表明它存在于一个独立的作用域区域内。

浮点类型的 #include 以及函数定义 foo() 和 main() 存在于全局作用域区域，因此它们不缩进。每个函数内部的语句存在于函数的嵌套作用域区域内，因此它们缩进一级。
