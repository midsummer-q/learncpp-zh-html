5.9 — std::string_view（第二部分）

● 机器译文 课程 5.9 查看英文原文

在前面的课程中，我们介绍了两种字符串类型： std::string (5.7 -- std::string 简介）和 std::string_view (5.8 -- std::string_view 简介)。

因为 std::string_view 是我们第一次接触视图类型，我们将花更多时间来进一步讨论它。我们将重点讨论如何安全地使用 std::string_view ，并提供一些示例说明如何错误地使用它。最后，我们将给出一些关于何时使用 std::string vs std::string_view。

所有者与观察者简介

让我们先暂时岔开话题，打个比方。假设你决定画一幅自行车的画。但你没有自行车！你该怎么办？

嗯，你可以去当地的自行车店买一辆。你将拥有那辆自行车。这样做有一些好处：你现在有了一辆可以骑的自行车。你可以保证当你需要时它总是可用的。你可以装饰它，或者移动它。但这种选择也有一些缺点。自行车很贵。而且如果你买了一辆，你现在就要对它负责。你必须定期维护它。当你最终决定不再需要它时，你必须妥善处理它。

所有权可能代价高昂。作为所有者，你有责任获取、管理和妥善处置你所拥有的对象。

在你出门时，你瞥了一眼窗前的景象。你注意到邻居把他们的自行车停在了你的窗户对面。你可以改画你邻居的自行车（从你的窗户看到的景象）。这种选择有很多好处。你省去了自己去买自行车的费用。你不需要维护它。你也不负责处理它。当你观察完毕后，你可以拉上窗帘，继续你的生活。这结束了你对对象的观察，但对象本身不受影响。这种选择也有一些潜在的缺点。你不能给邻居的自行车上色或定制。而且在你观察自行车时，你的邻居可能会决定改变自行车的外观，或者把它移出你的视线。你最终可能会看到意想不到的东西。

观察是廉价的。作为观察者，你对所观察的对象没有责任，但你也无法控制这些对象。

std::string 是（唯一的）所有者

你可能想知道为什么 std::string 会对其初始化值进行昂贵的复制。当对象被实例化时，会为该对象分配内存，以存储其整个生命周期中需要使用的任何数据。这块内存是为该对象保留的，并保证在该对象存在期间一直存在。这是一个安全的空间。 std::string （以及大多数其他对象）将给定的初始化值复制到这块内存中，以便它们拥有自己独立的值，以后可以访问和操作。一旦初始化值被复制，该对象就不再以任何方式依赖于初始化器。

这是一件好事，因为初始化器在初始化完成后通常不可信。如果你把初始化过程想象成一个初始化对象的函数调用，那么是谁传入初始化器的？是调用者。当初始化完成时，控制权返回给调用者。此时，初始化语句完成，通常会发生以下两种情况之一：

  • 如果初始化器是一个临时值或对象，该临时对象将立即被销毁。
  • 如果初始化器是一个变量，调用者仍然可以访问该对象。调用者可以对该对象做任何想做的事情，包括修改或销毁它。

关键提示

初始化后的对象无法控制初始化完成后初始化值会发生什么。

因为 std::string 会创建自己的初始化值副本，因此它不必担心初始化完成后初始化值会发生什么。初始化值可以被销毁或修改，这不会影响 std::string。缺点是这种独立性伴随着制作昂贵副本的成本。

在我们的比喻中， std::string 是一个所有者——它负责从初始化器获取其字符串数据，管理对字符串数据的访问，并在 std::string 对象被销毁时妥善处理字符串数据。

关键提示

在编程中，当我们称一个对象为所有者时，通常意味着它是唯一的所有者（除非另有说明）。唯一所有权（也称为单一所有权）确保谁对该数据负责是明确的。

我们并不总是需要副本

让我们回顾一下上一课中的这个例子：

#include <iostream>
#include <string>

void printString(std::string str) // str 复制其初始化器
{
    std::cout << str << '\n';
}

int main()
{
    std::string s{ "Hello, world!" };
    printString(s);

    return 0;
}

当 printString(s) 被调用时， str 会制作一个昂贵的 s副本。该函数打印复制的字符串，然后销毁它。

注意 s 已经持有我们想要打印的字符串。我们能否直接使用 s 持有的字符串，而不是制作副本？答案是可能——我们需要评估三个条件：

  • 是否可能 s 在 str 仍在使用时被销毁？不， str 在函数结束时消亡，而 s 存在于调用者的作用域中，在函数返回之前不能被销毁。
  • 是否可能 s 在 str 仍在使用时被销毁？不， str 在函数结束时消亡，调用者没有机会在函数返回之前修改 s
  • 是否 str 以某种调用者不期望的方式修改了字符串？不，该函数根本没有修改字符串。

由于这三个条件都不成立，因此使用已有的字符串而不进行复制是没有风险的。 s 而且由于字符串复制代价高昂，为什么要为不需要的复制付出代价呢？

std::string_view 是一个查看器

std::string_view 采用了一种不同的初始化方法。它不会对初始化字符串进行昂贵的复制，而是 std::string_view 创建一个廉价的视图 作为 初始化字符串。 std::string_view 可以在需要访问字符串时使用。

在我们的比喻中， std::string_view 是一个查看器。它查看一个已经存在于别处的对象，并且不能修改该对象。当视图被销毁时，被查看的对象不受影响。同时有多个查看器查看同一个对象是没问题的。

重要的是要注意，一个 std::string_view 在其整个生命周期内都依赖于初始化器。如果在视图仍在使用时修改或销毁被查看的字符串，将导致意外或未定义行为。

每当我们使用视图时，我们有责任确保这些情况不会发生。

警告

视图依赖于被查看的对象。如果在视图仍在使用时修改或销毁被查看的对象，将导致意外或未定义行为。

一个 std::string_view 如果它正在查看一个已被销毁的字符串，有时称为 悬垂 视图。

std::string_view 最适合用作只读函数参数

的最佳用途是作为只读函数参数。 std::string_view 的最佳用途是作为只读函数参数。这允许我们传入C风格字符串、 std::string，或 std::string_view 参数而不进行复制，因为 std::string_view 会创建一个指向参数的视图。

#include <iostream>
#include <string>
#include <string_view>

void printSV(std::string_view str) // 现在是 std::string_view，创建参数的视图
{
    std::cout << str << '\n';
}

int main()
{
    printSV("Hello, world!"); // 使用C风格字符串字面量调用

    std::string s2{ "Hello, world!" };
    printSV(s2); // 使用 std::string 调用

    std::string_view s3 { s2 };
    printSV(s3); // 使用 std::string_view 调用
       
    return 0;
}

由于 str 函数参数在控制权返回调用者之前被创建、初始化、使用和销毁，因此不存在被查看的字符串（函数参数）在我们的 str 参数之前被修改或销毁的风险。

优先使用 std::string_view 在大多数情况下。我们在课程 12.6 -- 通过const左值引用传递。

让我们看几个误用 std::string_view 会给我们带来麻烦的例子。

这是我们的第一个例子：

#include <iostream>
#include <string>
#include <string_view>

int main()
{
    std::string_view sv{};

    { // 创建一个嵌套块
        std::string s{ "Hello, world!" }; // 创建一个局部于该嵌套块的 std::string
        sv = s; // sv 现在正在查看 s
    } // s 在此处被销毁，因此 sv 现在查看的是一个无效字符串

    std::cout << sv << '\n'; // 未定义行为

    return 0;
}

在这个例子中，我们在一个嵌套块中创建 std::string s （先不要担心什么是嵌套块）。然后我们设置 sv 来查看 s。 s 然后在嵌套块结束时被销毁。 sv 不知道 s 已经被销毁。当我们随后使用 sv时，我们访问了一个无效的对象，导致未定义行为。

这是同一个问题的另一个变体，我们用函数的 std::string_view 返回值初始化一个 std::string ：

#include <iostream>
#include <string>
#include <string_view>

std::string getName()
{
    std::string s { "Alex" };
    return s;
}

int main()
{
  std::string_view name { getName() }; // name 用函数的返回值初始化
  std::cout << name << '\n'; // 未定义行为

  return 0;
}

这与前面的例子类似。 getName() 函数返回一个 std::string 包含字符串“Alex”。返回值是临时对象，在包含函数调用的完整表达式结束时被销毁。我们必须立即使用这个返回值，或者复制它以便稍后使用。

但是 std::string_view 不会进行复制。相反，它创建一个指向临时返回值的视图，然后该临时对象被销毁。这使得我们的 std::string_view 悬空（指向一个无效对象），打印该视图会导致未定义行为。

以下是上述情况的一个不太明显的变体：

#include <iostream>
#include <string>
#include <string_view>

int main()
{
    using namespace std::string_literals;
    std::string_view name { "Alex"s }; // "Alex"s 创建一个临时 std::string
    std::cout << name << '\n'; // 未定义行为

    return 0;
}

一个 std::string 字面量（通过 s 字面量后缀创建）创建一个临时的 std::string 对象。因此在这种情况下， "Alex"s 创建一个临时的 std::string，然后我们将其用作 name。此时， name 正在查看临时的 std::string。然后临时的 std::string 被销毁，使得 name 悬空。当我们随后使用 name。

警告

不要用 std::string_view 字面量初始化 std::string ，因为这会使 std::string_view 悬空。

用C风格字符串字面量或 std::string_view 字面量初始化 std::string_view 是可以的。用C风格字符串对象、 std::string_view 对象或 std::string 对象初始化 std::string_view 也是可以的，只要该字符串对象的生命周期超过视图。

当底层字符串被修改时，我们也可能得到未定义行为：

#include <iostream>
#include <string>
#include <string_view>

int main()
{
    std::string s { "Hello, world!" };
    std::string_view sv { s }; // sv 现在正在查看 s

    s = "Hello, a!";    // 修改 s，这会使 sv 失效（s 仍然有效）
    std::cout << sv << '\n';   // 未定义行为

    return 0;
}

在这个例子中， sv 再次被设置为查看 s。 s 然后被修改。当 std::string 被修改时，任何指向该 std::string 的视图都可能被 失效，这意味着这些视图现在无效或不正确。使用无效的视图会导致未定义行为。

进阶读者

  • 如果 std::string 重新分配内存以容纳新的字符串数据时，它会将旧字符串数据使用的内存返回给操作系统。由于 std::string_view 仍在查看旧的字符串数据，它现在悬空了（指向一个无效对象）。
  • 如果 std::string 没有重新分配内存，它会将新的字符串数据复制到旧字符串数据之上（从相同的内存地址开始）。 std::string_view 现在将查看新的字符串数据（因为它被放置在与之前查看的相同内存地址），但它不会意识到 std::string 的长度可能已经改变。如果新字符串比旧字符串长， std::string_view 现在将查看新字符串的一个子串（长度与旧字符串相同）。如果新字符串比旧字符串短， std::string_view 现在将查看新字符串的一个超串（包含整个新字符串，以及字符串末尾之后内存中仍然存在的任何垃圾字符）。

关键提示

修改 std::string 很可能会使所有指向该 std::string。

的视图失效。重新验证一个无效的 std::string_view

失效的对象通常可以通过将其设置回已知的良好状态来重新生效（使其再次有效）。对于一个失效的 std::string_view，我们可以通过给失效的 std::string_view 对象赋予一个有效的字符串来查看。

以下是与前一个相同的示例，但我们将重新生效 sv：

#include <iostream>
#include <string>
#include <string_view>

int main()
{
    std::string s { "Hello, world!" };
    std::string_view sv { s }; // sv 现在正在查看 s

    s = "Hello, universe!";    // 修改 s，这会使 sv 失效（s 仍然有效）
    std::cout << sv << '\n';   // 未定义行为

    sv = s;                    // 重新验证 sv：sv 现在再次查看 s
    std::cout << sv << '\n';   // 打印 "Hello, universe!"

    return 0;
}

在 sv 因修改 s而失效后，我们通过语句 sv 重新生效 sv = s，这使 sv 再次成为 s 的有效视图。当我们第二次打印 sv 时，它输出“Hello, universe!”。

小心返回一个 std::string_view

std::string_view 可以用作函数的返回值。然而，这通常是危险的。

因为局部变量在函数结束时被销毁，返回一个 std::string_view （它正在查看一个局部变量）会导致返回的 std::string_view 失效，并且进一步使用该 std::string_view 将导致未定义行为。例如：

#include <iostream>
#include <string>
#include <string_view>

std::string_view getBoolName(bool b)
{
    std::string t { "true" };  // 局部变量
    std::string f { "false" }; // 局部变量

    if (b)
        return t;  // 返回一个查看 t 的 std::string_view

    return f; // 返回一个查看 f 的 std::string_view
} // t 和 f 在函数结束时被销毁

int main()
{
    std::cout << getBoolName(true) << ' ' << getBoolName(false) << '\n'; // 未定义行为

    return 0;
}

在上面的例子中，当 getBoolName(true) 被调用时，函数返回一个 std::string_view ，它正在查看 t的事实。然而， t 在函数结束时被销毁。这意味着返回的 std::string_view 正在查看一个已被销毁的对象。因此，当返回的 std::string_view 被打印时，会导致未定义行为。

你的编译器可能会也可能不会对此类情况发出警告。

有两种主要情况可以安全地返回一个 std::string_view 首先，因为C风格字符串字面量在整个程序期间存在，所以从返回类型为 std::string_view。

#include <iostream>
#include <string_view>

std::string_view getBoolName(bool b)
{
    if (b)
        return "true";  // 返回一个查看 "true" 的 std::string_view

    return "false"; // 返回一个查看 "false" 的 std::string_view
} // "true" 和 "false" 在函数结束时不会被销毁

int main()
{
    std::cout << getBoolName(true) << ' ' << getBoolName(false) << '\n'; // ok

    return 0;
}

这会打印：

true false

当 getBoolName(true) 被调用时，函数将返回一个 std::string_view ，它查看C风格字符串 "true"。因为 "true" 在整个程序期间存在，因此当我们使用返回的 std::string_view 来打印 "true" 在 main()。

其次，通常可以返回一个类型为 std::string_view：

警告

如果参数是一个临时对象，在包含函数调用的完整表达式结束时被销毁，那么返回的 std::string_view 必须立即使用，否则在临时对象被销毁后它将悬空。

视图修改函数

想象你家的一扇窗户，正看着停在街上的一辆电动汽车。你可以透过窗户看到车，但无法触摸或移动它。你的窗户只是提供了对车的视图，而车是一个完全独立的对象。

许多窗户都有窗帘，允许我们修改视图。我们可以关闭左侧或右侧的窗帘来减少可见范围。我们并没有改变外面的东西，只是减少了可视区域。

因为 std::string_view 是一个视图，它包含一些函数，让我们可以通过“拉上窗帘”来修改视图。这不会以任何方式修改被查看的字符串，只修改视图本身。

  • 浮点类型的 remove_prefix() 成员函数从视图的左侧移除字符。
  • 浮点类型的 remove_suffix() 成员函数从视图的右侧移除字符。
#include <iostream>
#include <string_view>

int main()
{
	std::string_view str{ "Peach" };
	std::cout << str << '\n';

	// 从视图左侧移除 1 个字符
	str.remove_prefix(1);
	std::cout << str << '\n';

	// 从视图右侧移除 2 个字符
	str.remove_suffix(2);
	std::cout << str << '\n';

	str = "Peach"; // 重置视图
	std::cout << str << '\n';

	return 0;
}

该程序产生如下输出：

Peach
each
ea
Peach

与真实的窗帘不同，一旦 remove_prefix() 和 remove_suffix() 被调用后，重置视图的唯一方法是重新将源字符串赋值给它。

std::string_view 可以查看子串

这引出了 std::string_view的一个重要用途。虽然 std::string_view 可用于查看整个字符串而无需复制，但当我们想要查看子串而不复制时，它们也很有用。一个 子串 是现有字符串中连续的一段字符序列。例如，对于字符串“snowball”，一些子串是“snow”、“all”和“now”。“owl”不是“snowball”的子串，因为这些字符在“snowball”中不连续出现。

std::string_view 可能以空字符结尾，也可能不以空字符结尾

仅查看较大字符串的子串的能力带来一个值得注意的后果：一个 std::string_view 可能以空字符结尾，也可能不以空字符结尾。

相关内容

我们在课程 5.2 -- 字面量。

是否以空字符结尾，都能正常工作。注意不要编写任何假设 std::string_view 以空字符结尾的代码。

提示

如果你有一个不以空字符结尾的 std::string_view ，并且由于某种原因需要一个以空字符结尾的字符串，请将 std::string_view 转换为 std::string。

见解

关于 std::string：

  • 初始化和复制 std::string 代价高昂，因此应尽可能避免。
  • 避免传递 std::string 按值传递，因为这会生成一个副本。
  • 如果可能，避免创建短生命周期的 std::string 对象。
  • 修改 std::string 会使该字符串的所有视图失效。
  • 返回局部变量是可以的 std::string 按值的函数调用或运算符。

关于 std::string_view：

  • std::string_view 通常用于传递字符串函数参数和返回字符串字面量。
  • 因为C风格字符串字面量在整个程序期间都存在，所以将 std::string_view 设置为C风格字符串字面量总是安全的。
  • 当字符串被销毁时，该字符串的所有视图都会失效。
  • 使用失效的视图（除了通过赋值重新验证视图）会导致未定义行为。
  • 一个 std::string_view 可能以空字符结尾，也可能不以空字符结尾。
