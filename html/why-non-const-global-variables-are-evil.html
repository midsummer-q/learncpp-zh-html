7.8 — 为什么（非常量）全局变量是邪恶的

● 机器译文 课程 7.8 查看英文原文

如果你问一位资深程序员 一个 关于良好编程实践的建议，经过思考后，最可能的回答是：“避免使用全局变量！”而且理由充分：全局变量是语言历史上被滥用最多的概念之一。虽然它们在小型的学术程序中看似无害，但在大型程序中往往问题重重。

新手程序员常常倾向于使用大量全局变量，因为它们易于使用，尤其是在涉及多次调用不同函数时（通过函数参数传递数据很麻烦）。然而，这通常是个坏主意。许多开发者认为应该完全避免使用非常量全局变量！

但在我们讨论原因之前，需要澄清一点。当开发者告诉你全局变量是邪恶的时，他们通常指的不是 所有 全局变量。他们主要指的是非常量全局变量。

为什么（非常量）全局变量是邪恶的

到目前为止，非常量全局变量危险的最大原因是它们的值可以被 任何 任何被调用的函数改变，而程序员很难知道这种情况会发生。考虑以下程序：

#include <iostream>

int g_mode; // // 声明全局变量（默认会被零初始化）

void doSomething()
{
    g_mode = 2; // // 将全局变量 g_mode 设置为 2
}

int main()
{
    g_mode = 1; // // 注意：这将全局变量 g_mode 设置为 1。它不会声明一个局部变量 g_mode！

    doSomething();

    // // 程序员仍然期望 g_mode 为 1
    // // 但是 doSomething 把它改成了 2！

    if (g_mode == 1)
    {
        std::cout << "No threat detected.\n";
    }
    else
    {
        std::cout << "Launching nuclear missiles...\n";
    }

    return 0;
}

注意，程序员设置了变量 g_mode 切换到 1，然后调用了 doSomething()。除非程序员明确知道 doSomething() 会改变 g_mode的值，否则他或她可能不会预料到 doSomething() 会改变这个值！因此， main() 的其余部分无法按程序员的预期工作（世界被毁灭了）。

简而言之，全局变量使程序的状态变得不可预测。每个函数调用都可能变得危险，而程序员无法轻易知道哪些是危险的，哪些不是！局部变量更安全，因为其他函数不能直接影响它们。

还有很多其他充分的理由不使用非常量全局变量。

使用全局变量时，经常会发现类似这样的代码：

void someFunction()
{
    // // 有用的代码

    if (g_mode == 4)
    {
        // // 做一些好事
    }
}

调试后，你确定程序运行不正确是因为 g_mode 值为 3，而不是 4。如何修复？现在你需要找到所有可能将 g_mode 设置为 3的地方，并追踪它最初是如何被设置的。这可能发生在完全不相关的代码中！

在尽可能靠近使用位置的地方声明局部变量的关键原因之一是，这样做可以最大限度地减少需要查看的代码量，以理解变量的作用。全局变量则处于另一个极端——因为它们可以在任何地方被访问，你可能需要查看整个程序才能理解它们的用法。在小型程序中，这可能不是问题。但在大型程序中，这将是问题。

例如，你可能会发现 g_mode 在程序中被引用了442次。除非 g_mode 有良好的文档，否则你可能需要查看 g_mode 的每一次使用，以理解它在不同情况下如何被使用、它的有效值是什么以及它的整体功能是什么。

全局变量还会使程序变得不那么模块化和灵活。一个只使用其参数且没有副作用的函数是完全模块化的。模块化有助于理解程序的功能，也有助于可重用性。全局变量显著降低了模块化程度。

特别是，避免将全局变量用于重要的“决策点”变量（例如，在条件语句中使用的变量，如上面例子中的变量 g_mode ）。如果保存信息性值的全局变量发生变化（例如用户的名字），程序不太可能崩溃。但如果改变影响 如何 程序实际运行方式的全局变量，则更可能导致崩溃。

最佳实践

尽可能使用局部变量而不是全局变量。

全局变量的初始化顺序问题

静态变量（包括全局变量）的初始化发生在程序启动时，在 main 函数执行之前。这分为两个阶段。

第一阶段称为 静态初始化。静态初始化分为两个阶段：

  • 具有 constexpr 初始化器（包括字面量）的全局变量会被初始化为这些值。这被称为 常量初始化。
  • 没有初始化器的全局变量会被零初始化。零初始化被认为是静态初始化的一种形式，因为 0 是一个 constexpr 值。

第二阶段称为 动态初始化。这个阶段更复杂且微妙，但要点是，具有非 constexpr 初始化器的全局变量会被初始化。

下面是一个非 constexpr 初始化器的例子：

int init()
{
    return 5;
}

int g_something{ init() }; // // 非常量表达式初始化

在单个文件中，对于每个阶段，全局变量通常按照定义顺序初始化（动态初始化阶段有一些例外）。因此，需要注意不要让变量依赖于其他变量的初始化值，而这些变量可能稍后才被初始化。例如：

#include <iostream>

int initX();  // // 前向声明
int initY();  // // 前向声明

int g_x{ initX() }; // // g_x 首先被初始化
int g_y{ initY() };

int initX()
{
    return g_y; // // 调用此函数时 g_y 尚未初始化
}

int initY()
{
    return 5;
}

int main()
{
    std::cout << g_x << ' ' << g_y << '\n';
}

这会打印：

0 5

更大的问题是，不同翻译单元中静态对象的初始化顺序是不确定的。

给定两个文件， a.cpp 和 b.cpp，任何一个都可能先初始化其全局变量。如果某个具有静态存储期的变量在 a.cpp 中被初始化为一个定义在 b.cpp中的静态存储期变量，那么有 50% 的可能性 b.cpp 中的变量尚未初始化。

术语

不同翻译单元中具有静态存储期的对象初始化顺序的不确定性通常被称为 静态初始化顺序问题。

警告

避免使用来自不同翻译单元的其他静态存储期对象来初始化具有静态存储期的对象。

全局变量的动态初始化也容易受到初始化顺序问题的影响，应尽可能避免。

那么，使用非常量全局变量的充分理由是什么？

并不多。在大多数情况下，使用局部变量并将它们作为参数传递给其他函数是更好的选择。但在某些情况下，明智地使用非常量全局变量 可以 实际上可以降低程序的复杂性，在这些罕见的情况下，使用它们可能比替代方案更好。

一个很好的例子是日志文件，你可以将错误或调试信息转储到其中。将其定义为全局变量可能是有意义的，因为程序中可能只有一个这样的日志，并且它可能会在程序的任何地方被使用。另一个好例子是随机数生成器（我们在课程 8.15 -- 全局随机数 (Random.h))。

中展示了一个例子）。值得一提的是，std::cout 和 std::cin 对象是作为全局变量实现的（在 std 命名空间）。

中）。作为经验法则，任何全局变量的使用至少应满足以下两个条件：程序中该变量所代表的事物应该只有一个，并且它的使用应该遍布整个程序。

许多新手程序员错误地认为，因为现在只需要一个，所以某样东西可以作为全局变量来实现 现在。例如，你可能认为因为你在实现一个单人游戏，所以只需要一个玩家。但当你以后想要添加多人模式（对战或热座）时会发生什么？

保护自己免受全局变量的破坏

如果你确实找到了非常量全局变量的好用途，一些有用的建议可以最大限度地减少你可能遇到的麻烦。这些建议不仅适用于非常量全局变量，而且对所有全局变量都有帮助。

首先，给所有非命名空间的全局变量加上前缀“g”或“g_”，或者更好的做法是将它们放在命名空间中（在课程 7.2 -- 用户定义命名空间和作用域解析运算符中讨论），以减少命名冲突的可能性。

例如，不要这样：

#include <iostream>

constexpr double gravity { 9.8 }; // // 可能与名为 gravity 的其他全局变量冲突的风险

int main()
{
    std::cout << gravity << '\n'; // // 从名称上不清楚这是局部变量还是全局变量

    return 0;
}

这样做：

#include <iostream>

namespace constants
{
    constexpr double gravity { 9.8 }; // // 不会与名为 gravity 的其他全局变量冲突
}

int main()
{
    std::cout << constants::gravity << '\n'; // // 明确这是一个全局变量（因为命名空间是全局的）

    return 0;
}

其次，与其允许直接访问全局变量，更好的做法是“封装”该变量。确保变量只能从声明它的文件内部访问，例如通过将变量设为 static 或 const，然后提供外部的全局“访问函数”来操作该变量。这些函数可以确保维护正确的使用方式（例如进行输入验证、范围检查等）。此外，如果你决定更改底层实现（例如从一个数据库迁移到另一个），你只需更新访问函数，而不是直接使用该全局变量的每一段代码。

例如，不要这样：

constants.cpp:

namespace constants
{
    extern const double gravity { 9.8 }; // // 具有外部链接，可以被其他文件访问
}

main.cpp:

#include <iostream>

namespace constants
{
    extern const double gravity; // // 前向声明
}

int main()
{
    std::cout << constants::gravity << '\n'; // // 直接访问全局变量

    return 0;
}

这样做：

contants.cpp:

namespace constants
{
    constexpr double gravity { 9.8 }; // // 具有内部链接，仅在此文件内可访问
}

double getGravity() // // 具有外部链接，可以被其他文件访问
{
    // // 如果需要，我们以后可以在这里添加逻辑
    // // 或者透明地更改实现，对调用者无影响
    return constants::gravity;
}

main.cpp:

#include <iostream>

double getGravity(); // // 前向声明

int main()
{
    std::cout << getGravity() << '\n';

    return 0;
}

提醒

全局 const 变量默认具有内部链接， gravity 不需要 static。

第三，在编写一个使用全局变量的独立函数时，不要直接在函数体中使用该变量。而是将其作为参数传入。这样，如果函数将来需要在某种情况下使用不同的值，只需改变参数即可。这有助于保持模块化。

不要这样写：

#include <iostream>

namespace constants
{
    constexpr double gravity { 9.8 };
}

// // 此函数仅用于基于全局重力计算瞬时速度
double instantVelocity(int time)
{
    return constants::gravity * time;
}

int main()
{
    std::cout << instantVelocity(5) << '\n';

    return 0;

}

这样做：

#include <iostream>

namespace constants
{
    constexpr double gravity { 9.8 };
}

// // 此函数可以计算任意重力值的瞬时速度（更有用）
double instantVelocity(int time, double gravity)
{
    return gravity * time;
}

int main()
{
    std::cout << instantVelocity(5, constants::gravity) << '\n'; // // 将我们的常量作为参数传递给函数

    return 0;
}
